# 聊天应用级接线契约

本说明固定客户端与 MyServer chat-server 的首版协议边界。首版不包含可见聊天窗口，只交付稳定的 typed state/command/event 和邮件通知桥接。`ChatPlugin` 持有受控的 `ChatRuntimeOwner`；`MyServerSession` 只保存经验证的 endpoint、错误和 generation，不持有 runtime 或 ticket 的诊断副本。

## Endpoint

- 生产 descriptor 为 auth 或签票响应的 `services.chat`，正式公网入口是 `wss://chat.bevy.zergzerg.cn/`（Caddy `443`）。客户端不得从 service registry 或 chat-server 内部监听端口推导 production endpoint。
- 本地调试可由响应显式给出 `ws://127.0.0.1:9001/`；它不会由客户端自行拼接或回退。
- `services.chat = null` 表示 chat 不可用，不回退到内部 `9001`、`9011` 或其他地址。
- 会话在登录、选角和补票响应中通过同一入口更新 game/chat/mail descriptor。`chat_endpoint_generation` 会在 endpoint、ticket、环境、账号、角色或 Logout 变化时推进，使后续 runtime 忽略旧 generation 的事件。
- Production 只接受 `wss://chat.bevy.zergzerg.cn:443/` descriptor；Local profile 可接受响应显式下发的 `ws`。桌面 Debug 如需在 Production profile 调试明文本地入口，必须显式设置 `MYSERVER_ALLOW_INSECURE_CHAT_WS=true`，Release/Android 不接受该覆盖。

## 生命周期、补票和前后台

- WebSocket transport connected、`Authenticating` 和业务 `Ready` 是三个不同状态。只有收到并验证 `ChatAuthRes(ok=true)` 后才进入 `Ready`；首包鉴权失败会写入稳定分类错误码。
- `TICKET_EXPIRED`、`TICKET_REVOKED`、`INVALID_TICKET` 和 `AUTH_TICKET_INVALID` 只会触发一次 `RefreshTicket { reconnect_game: false }`。补票响应更新 ticket 与 endpoint generation 后，旧 runtime 被关闭，新 runtime 使用最新 ticket 重新鉴权；补票失败进入 `CHAT_TICKET_REFRESH_FAILED`，不会阻塞游戏连接或页面路由。
- 网络断开按受上限、确定性 jitter 的退避重连。`Backoff { attempt }` 和 `reconnect_attempt` 描述持续重连；重回前台会按当前 session 的 endpoint、ticket 和 generation 重新评估，而不是复用旧身份。
- 进入后台会暂停 transport，并取消 pre-auth 队列和尚未完成的请求，事件错误码为 `CHAT_REQUEST_CANCELLED_BACKGROUND`。恢复后不会发送后台遗留请求；仍由新的鉴权周期决定后续请求。
- Logout、切环境、切账号、切角色、ticket 或 endpoint 变化都会推进 generation。旧 runtime 的 connected、packet 和 disconnected 事件会在 drain 前被隔离并关闭；应用退出只尝试非阻塞 disconnect，不等待网络线程。

## Wire Protocol

- TCP 与 WSS 共用 14-byte header 和 Protobuf body。一个 WebSocket binary frame 必须恰好承载一个完整 `14 + body_len` packet；不接受 text frame、raw protobuf、分片 packet 或多 packet frame。
- 服务端默认 `MAX_BODY_LEN` 为 4096 bytes，故客户端默认最大 frame 为 4110 bytes（14 + 4096）。服务端可在部署时降低该边界；应用层不得假设超过 descriptor/服务端配置的容量可用。
- 连接建立后的首个业务包必须是 `ChatAuthReq(20001)`。character-bound ticket 只可写入首个 binary frame 的 `ChatAuthReq.token`，不可进入 URL、query、subprotocol、cookie 或日志。
- 只有 `ChatAuthRes(ok=true, 20002)` 后才允许正常业务请求。request/response 必须以 `(message_type, seq)` 关联；`ChatPush` 与 `MailNotifyPush` 是异步 push，使用 `seq=0`，不消费 pending 请求。

| msgType | Protobuf |
| --- | --- |
| 20001 / 20002 | ChatAuthReq / ChatAuthRes |
| 20101 / 20102 | ChatPrivateReq / ChatPrivateRes |
| 20103 / 20104 | ChatGroupReq / ChatGroupRes |
| 20105 | ChatPush |
| 20201 / 20202 | GroupCreateReq / GroupCreateRes |
| 20203 / 20204 | GroupJoinReq / GroupJoinRes |
| 20205 / 20206 | GroupLeaveReq / GroupLeaveRes |
| 20207 / 20208 | GroupDismissReq / GroupDismissRes |
| 20209 / 20210 | GroupListReq / GroupListRes |
| 20211 / 20212 | ChatHistoryReq / ChatHistoryRes |
| 20301 | MailNotifyPush |
| 9000 | ErrorRes |

`MailNotifyPush` 只表示邮件列表可能已变化。后续邮件桥接只应请求权威 HTTPS 邮件列表，不可把 push 的标题或摘要写为本地权威邮件事实。

## 邮件桥接与灰度边界

- `ChatEvent::MailNotifyPush` 不携带 packet body。`MailPlugin` 仅接受当前 chat generation 的事件，并将同一批重复通知合并成一条 `MailClientCommand::MailNotifyPush`。
- 该命令只标记邮件列表过期并请求 `GET /api/v1/mails`。重复、乱序或丢失通知不会修改邮件缓存事实；邮箱面板每次打开或刷新仍走 HTTPS 权威查询。
- 功能灰度关闭的受控状态是 `services.chat=null`、无 character-bound ticket 或 chat endpoint 校验失败。此时 chat 进入 `Unavailable` 或 `Disconnected` 且不启动 runtime；账号登录、game proxy、主世界、设置和邮件 HTTPS 查询不依赖 chat ready，继续独立工作。

## 诊断与安全

`ChatClientState` 是本地可观察快照，只记录以下非敏感字段：

- `status`、`endpoint_generation`、脱敏 `endpoint_fingerprint`、`foreground`；
- `reconnect_attempt`、`pending_request_count`、`preauth_queue_depth`、`ticket_refresh_in_flight`；
- `last_error_code` 和 `ChatEvent` 中的稳定错误分类、message type 或 seq。

不得将 ticket、WebSocket URL 明文、聊天正文、邮件标题、邮件摘要或服务端原始错误文本写入该快照、typed event 或日志。稳定诊断字段包括：`CHAT_ENDPOINT_UNAVAILABLE`（`services.chat=null` 或 descriptor 无效）、`CHAT_TLS_FAILED`（TLS/证书/握手失败）、`CHAT_AUTH_*`（鉴权拒绝）、`CHAT_RATE_LIMITED` / `CHAT_AUTH_RATE_LIMITED`（限流）、`CHAT_TRANSPORT_DISCONNECTED` 和 `Backoff { attempt }`（持续重连）。

## 离线协议一致性核对

本地核对以相邻 MyServer checkout 的 `docs/协议与客户端/协议设计.md` 第 5 节、`apps/chat-server/src/chat_server.rs` 的 `MessageType` 和本仓库 `CHAT_PROTOCOL_MESSAGE_TYPES` 为准。当前核对结果：14-byte header、4096-byte body/4110-byte frame、`20001..20301` 聊天消息号及 `9000/ErrorRes` 一致；`cargo test chat::tests --lib` 中的协议常量和 frame 测试用于防止客户端漂移。本核对不替代已部署 WSS 的真实连通性、安全或跨实例 push 验收。

## 非目标

本 清单 不负责聊天审核后台、复杂好友或社交图谱、离线消息产品策略，以及运营管理工具。这些能力需要独立产品和服务端设计后再接入。
