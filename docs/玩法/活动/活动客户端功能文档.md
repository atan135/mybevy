# 活动客户端功能文档

## 文档定位

本文定义 MyBevy 客户端对 MyServer 活动系统的功能边界、玩家流程、数据消费方式和客户端运行时职责。活动属于客户端游戏玩法模块，页面入口和交互属于游戏层；网络协议复用 `project/src/game/myserver/`，不把活动规则下沉到 UI 或本地玩法逻辑。

服务端活动事实来源为 `../MyServer` 当前代码和文档。本文参考服务端提交 `13b1d9e019553400ea94cbf5d69f5ff4bbdb9677`，覆盖首期 `login_reward` 和 `lottery` 两类活动。服务端规则、资格、时间、次数、消耗、随机结果和奖励交付始终拥有最终决定权。

## 当前边界

服务端阶段一已经具备：

- 活动列表、详情、进度、阶段领取和通用动作玩家协议。
- 登录奖励的服务端 game-entry 周期推进、阶段资格和手动/自动领取。
- 抽奖的免费次数/道具券资格、每日/总次数限制、安全随机、结果持久化和奖励交付。
- 活动版本不可变、character scope、时间窗、领取宽限、幂等、并发、防重放、恢复和审计。
- 活动后台发布/下线和 PostgreSQL 事实存储；Redis 仅作为缓存、限流和刷新通知。

客户端已完成的首期范围：

- 主世界 HUD 的“活动”入口、活动列表、受控详情页、登录奖励与抽奖动作适配均位于 `project/src/game/screens/activity/` 与 `project/src/game/myserver/activity.rs`。
- 活动列表的“我的领取记录”入口使用独立 approved `UiDocument`、typed 页面状态和固定 host；关闭记录页返回既有列表，不重建主世界会话或重载列表。
- 领取、抽奖、重试、重连、重复请求、服务端能力不可用、人工核对和活动 scope 变化均由客户端受控状态与适配层处理；奖励、资格、消耗和随机结果继续只以服务端响应为准。
- 客户端 protocol snapshot 已包含 `ActivityClaimHistoryReq` / `ActivityClaimHistoryRes`（1445 / 1446），对应服务端参考提交为 `13b1d9e019553400ea94cbf5d69f5ff4bbdb9677`；历史记录页面的客户端实现提交为 `6f696fb`。

以下现实环境验收尚未执行：未启动 MyServer/dev-stack，未对接真实 character-bound 会话；未运行固定窗口 `scripts/run_fast.ps1`，也未执行 Android、前后台或断网恢复验收。相关结论必须以实际服务端和设备证据补齐，不能由本地 mock 或单元测试替代。

当前服务端路由的一个兼容现状必须保留：`ActivityDetailRes.progress_json` 会提供类型 player view，但成功的 `ActivityProgressRes.progress_json` 仍固定为 `{}`，`state_revision` 固定为 `0`。客户端不得把该 `{}` 解释为无进度；在服务端补齐 progress 路由前，以最近一次可信 detail 为展示来源。

## 玩家体验

### 主世界活动入口

活动入口固定放在主世界 HUD 的游戏层导航中。主世界 HUD 必须提供一个“活动”按钮；按钮只负责打开活动列表页并触发 `ActivityListReq`，不直接打开某个活动玩法页，也不在 HUD 中复制活动规则。

点击“活动”后进入活动列表页。列表只展示当前角色可读的有效活动：已发布或运行中的活动，以及仍处于领取宽限期、允许查看的已结束活动；草稿、归档、下线和未知类型不得展示为活动项。列表项显示活动类型、活动时间、状态和领取截止时间。时间展示可以使用服务端 `server_time_ms` 校准本地时钟，但本地时间不得决定按钮是否可用。

活动列表页必须提供“我的领取记录”按钮。点击后打开当前角色自己的历史领取记录页，记录由服务端查询结果驱动，不得从本地动作日志或客户端缓存拼装；记录页关闭后返回活动列表，并保留列表滚动位置和已加载状态。账号 ID、其他角色的记录和未通过服务端授权的记录不得出现在页面中。

### 活动列表到玩法详情

活动列表和具体活动玩法是两个独立页面。打开列表时只请求列表摘要，不自动请求或展示任意活动的详情。只有玩家点击某个列表项后，客户端才以该项的 `activity_id` 和 `version` 请求详情并打开具体活动玩法界面。

详情页根据 `activity_type` 选择受控的登录奖励或抽奖视图，不把任意 JSON 字段直接当作 UI 节点、富文本或资源路径。详情页返回活动列表时不得重新创建主世界会话；必要时只刷新列表摘要。

详情、进度和动作响应必须校验 `activity_id` 与 `version`，旧活动版本的响应不能覆盖当前版本状态。切换角色、登出、切换环境或连接代际变化时清空活动状态。

### 登录奖励

登录奖励页展示服务端返回的周期、连续/累计计数、今日状态和阶段列表。每个阶段使用服务端字段 `achieved`、`claimable`、`claimed` 控制状态：

- `achieved=false`：显示未达成，不显示可领取动作。
- `claimable=true`：允许发送阶段领取。
- `claimed=true`：显示已领取，禁止再次发送。
- `claim_mode=automatic`：不显示手动领取按钮，等待服务端状态刷新。

阶段请求的 `stage_id` 是服务端 `stage_no` 转换出的字符串，不是客户端数组下标。登录天数由服务端可信 `game_entry` 事件推进，客户端没有“上报登录天数”的功能。

### 随机抽奖

抽奖页展示免费次数、券库存、每日/总次数和最近一次服务端结果状态。按钮只发送 `ActivityActionReq(action_type="draw")`：

- 客户端不选择免费或券模式。
- 客户端不提交 item UID、数量、货币、奖品、概率、权重或随机数。
- 服务端决定抽奖成本、奖品和奖励交付结果。
- 当前没有独立抽奖结果查询消息；动作完成后重新请求详情/进度。

`result_item_id` 只能作为服务端结果引用，展示名称、图标和数量必须从客户端受控物品定义或背包刷新状态解析。客户端不从奖池权重反推概率，也不自行生成抽奖动画结果；动画结束后以服务器确认状态为准。

## 网络协议

活动请求在已通过 character-bound game ticket 鉴权的 game 连接上发送，使用现有 14-byte 包头、Protobuf body、`seq` 和 `PendingRequest` 生命周期。

| 请求 | 响应 | msgType |
| --- | --- | ---: |
| `ActivityListReq` | `ActivityListRes` | 1435 / 1436 |
| `ActivityDetailReq` | `ActivityDetailRes` | 1437 / 1438 |
| `ActivityProgressReq` | `ActivityProgressRes` | 1439 / 1440 |
| `ActivityClaimReq` | `ActivityClaimRes` | 1441 / 1442 |
| `ActivityActionReq` | `ActivityActionRes` | 1443 / 1444 |
| `ActivityClaimHistoryReq` | `ActivityClaimHistoryRes` | 1445 / 1446 |

### 活动摘要

`ActivitySummary`：

| 字段 | 语义 |
| --- | --- |
| `activity_id` | 稳定活动 ID，仅作为路由键 |
| `version` | 发布版本；非零值必须来自服务端快照 |
| `activity_type` | `login_reward` 或 `lottery` |
| `status` | `published`、`running`、`ended`、`offline` 等 |
| `start_at_ms` / `end_at_ms` | UTC 毫秒时间，仅用于展示 |
| `claim_deadline_ms` | 已产生资格的最晚领取时间 |
| `timezone` | 活动规则使用的 IANA 时区 |

### 读取请求

```text
ActivityListReq {}
ActivityDetailReq { activity_id, version }
ActivityProgressReq { activity_id, version }
```

读取响应包含 `ok`、`error_code`；列表还包含 `server_time_ms` 和 `activities`；详情包含 `activity`、`progress_json`、`state_revision`；进度包含 `activity_id`、`version`、`progress_json`、`state_revision`。

### 历史领取记录

历史领取记录必须走 character-bound 的服务端查询，不能使用活动详情中的当前进度代替。`ActivityClaimHistoryReq { cursor, limit }` 使用服务端签名且绑定当前角色的 opaque cursor；请求不得携带账号或角色 ID，`limit=0` 由服务端使用默认值，最大值为 50。`ActivityClaimHistoryRes` 返回 `records`、`next_cursor` 和 `has_more`；`has_more=true` 时必须携带非空的下一页 cursor。`ActivityClaimHistoryRecord` 只公开活动 ID/版本、活动和动作类型、可选阶段、创建/完成时间、公开状态与受限奖励摘要；奖励摘要仅适用于 `granted` 记录，每条记录最多 16 项。

历史记录响应支持 cursor 分页，并返回活动 ID/版本、阶段或动作标识、领取时间、结果状态和服务端可展示的奖励摘要。客户端只展示当前角色有权读取的服务端记录，支持加载更多、空状态、加载失败和重试；不得因为本地请求超时、重复请求或断线而新增一条历史记录。

客户端使用每页默认 20 条请求，但不将分页结果无限累积：`ActivityClientState` 最多保留并渲染 60 条历史记录。此值小于 UI repeat 的 64 项上限，且在 512 个展开节点预算内；当后续页面会超过 60 条时，客户端只保留可显示部分、清除下一页 opaque cursor、停止 `has_more`，并将“加载更多”保留为禁用状态。host、UI action 和网络响应写入均有同一上限防御，避免无效 binding 写入或越界缓存。刷新首屏仍会重置该分页显示窗口，正常未达上限的加载更多、失败重试和去重行为不变。

### 写入请求

```text
ActivityClaimReq {
  activity_id,
  version,
  stage_id,
  client_request_id
}

ActivityActionReq {
  activity_id,
  version,
  stage_id,
  action_type,
  client_request_id
}
```

写入响应返回动作上下文、`ok`、`error_code`、`processing`、`duplicate` 和 `state_revision`。`client_request_id` 长度不超过 128 bytes，表示一次客户端逻辑操作的重试键：超时、断线和处理中状态必须复用原值；同值重放返回 `duplicate=true` 时不重复弹奖励、不重复扣券。

### 身份与安全边界

活动请求不包含账号 ID、角色 ID、ticket、奖励、进度、服务器时间、概率、权重、随机结果、券 UID 或数量。角色身份由已鉴权连接上下文取得。客户端日志和诊断快照不得记录 ticket、密码、完整 request ID、角色 ID 或奖励内容。

## 客户端运行时结构

活动页面的具体代码必须放在新建目录 `project/src/game/screens/activity/` 下，不得继续堆入 `gameplay`、`lobby` 或 `main.rs`。该目录至少负责活动列表页、活动详情页、历史领取记录页、页面 host、路由生命周期和 UI action 到活动命令的适配；建议按职责拆分为 `mod.rs`、`host.rs`、`list.rs`、`detail.rs` 和 `claim_history.rs`。主世界 HUD 只保留“活动”按钮及打开列表的桥接动作。

网络和业务状态仍放在 `project/src/game/myserver/activity.rs`，由 `ActivityPlugin` 提供以下职责：

- `ActivityClientState`：列表、选中活动、详情、进度、当前版本、连接代际和最后错误。
- `ActivityRequestTracker`：以 `seq`、`client_request_id`、活动 ID 和版本跟踪请求生命周期。
- Protobuf 到业务模型的 adapter：限制 JSON 大小，校验 `type`/`schema_version`，兼容未知字段。
- 发送系统：复用 `send_request_with_seq`，把 request/response 类型写入 `PendingRequest`。
- 接收系统：解码 1436、1438、1440、1442、1444、1446，校验 seq、连接 ID、活动 ID、版本和历史分页字段。
- 事件系统：向页面和游戏层发布成功、失败、处理中、重复和需要重新读取的事件，包括历史记录查询结果。

`project/src/game/screens/activity/` 下的页面结构使用 approved `UiDocument`；Rust 只提供活动 adapter、状态绑定、动作命令和路由生命周期。活动页面不得绕过 MyServer 网络模块直接创建 socket 或拼装 protobuf。页面路由至少区分活动列表、具体活动玩法和历史领取记录三个状态，列表项点击是从列表进入玩法详情的唯一入口。

已批准的活动文档包含列表、通用详情、登录奖励详情、抽奖详情和历史领取记录页面；历史记录页面的运行时 binding 与 promotion 契约都声明 `activity_claim_history.items.max_items = 60`，必须与 Rust schema 和客户端缓存上限保持一致。

## `progress_json` 消费契约

### `login_reward`

当前 player view 至少包含：

```text
type, schema_version, contract_only,
event_source, cycle_unit, progression, miss_policy, claim_mode,
stages, current_stage_id, last_period_key,
consecutive_days, cumulative_days, today_status
```

每个 `stages` 项至少包含 `stage_no`、`required_count`、`reward_group_key`、`achieved`、`claimable`、`claimed`。客户端只消费这些状态，不复制服务端周期或领取语义。

### `lottery`

当前 player view 至少包含：

```text
type, schema_version, contract_only,
draw_source, pool_version, free_draw_count,
daily_draw_limit, total_draw_limit, pool_total_weight, state
```

`state` 可能包含 `free_draws_remaining`、`voucher_count`、`daily_draw_count`、`total_draw_count`、`last_draw_period_key`、`pool_version`、`draw_request_id`、`result_item_id` 和 `result_state`。服务端可以新增字段，客户端必须忽略未知字段并保留整体刷新能力。

## 生命周期与错误行为

客户端按服务端状态处理：

| 状态/错误 | 客户端行为 |
| --- | --- |
| `published` / `not started` | 可查看，不可参与 |
| `running` | 按资格字段显示参与动作 |
| `ended` | 禁止新参与；按截止时间允许已产生资格领取 |
| `offline` | 禁止领取和参与，可保留查询 |
| `ACTIVITY_ENGINE_UNAVAILABLE` | 能力不可用，显示可重试状态 |
| `ACTIVITY_QUALIFICATION_NOT_MET` | 刷新详情/进度，不循环重试 |
| `ACTIVITY_ALREADY_CLAIMED` | 按已领取处理并刷新 |
| `ACTIVITY_VERSION_CONFLICT` / `ACTIVITY_INVALID_VERSION` | 重新 list/detail，替换本地版本 |
| `ACTIVITY_PROCESSING` | 原 request ID 延迟重放或刷新，不新建请求 |
| `ACTIVITY_RETRYABLE_FAILURE` / `ACTIVITY_STORAGE_UNAVAILABLE` | 有界重试原 request ID |
| `ACTIVITY_RECONCILIATION_PENDING` / `ACTIVITY_MANUAL_REVIEW` | 显示待核对，不自行补发/重抽 |
| 未知 `ACTIVITY_*` | 按失败处理，保留脱敏错误码 |

连接断开、ticket 刷新、切换角色、切换环境和登出会推进连接代际。旧连接的响应和 push 在隔离后不得覆盖新角色或新版本活动状态。

## 功能完成标准

功能完成必须同时满足：

1. 主世界 HUD 有活动按钮；点击后只打开活动列表并读取当前有效活动。
2. 活动页面具体代码位于 `project/src/game/screens/activity/`，页面结构使用 approved `UiDocument`。
3. 活动列表项只有在玩家点击后才打开对应的活动玩法详情；列表页不自动打开详情。
4. 活动列表有“我的领取记录”按钮，能打开当前角色的服务端历史领取记录并处理分页、空状态、失败和重试。
5. 客户端能读取活动列表、详情和服务端类型视图；登录奖励阶段领取和随机抽奖动作能正确发送并刷新服务器状态。
6. 重复 request、超时、处理中、断线重连、版本冲突和服务端 disabled 均有明确 UI 行为。
7. 客户端不提交服务端拥有的身份、资格、奖励、概率、消耗和结果字段。
8. 协议快照、运行时 adapter、UI 文档、测试和联调证据同步维护；本地测试与实服/跨端验收必须分别记录，不互相替代。
