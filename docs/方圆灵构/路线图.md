# 方圆灵构路线图

本文由原《方圆对象资源构建与渲染技术路线》的阶段开发路线及后续章节迁移而来。本轮仅调整文档结构，不修正阶段状态或实现口径。

## 阶段开发路线

### 阶段 1：方圆玩家外观最小闭环

目标：

- 稳定读取 `project/assets/fangyuan/avatars/minimal_player.ron` 或等价本地 RON。
- 生成一个玩家逻辑 Entity，并把 RON primitive 编译为该玩家 Entity 内部的 `FangyuanPrimitiveSet`。
- 在当前 Bevy 场景中显示一个最小方圆玩家：一个 cube 身体和一个 sphere 头部。
- 验证“玩家是 Entity，primitive 不是玩法 Entity”的对象边界。
- 验证方圆系统只依赖移动、scale 缩放和 primitive 生命周期，不引入旋转。

技术做法：

- 生成 `PlayerEntity` 逻辑对象，并挂载玩家身份、运行状态、`FangyuanAvatar` 和 `FangyuanPrimitiveSet`。
- 蓝图 primitives 存入玩家 Entity 的 `FangyuanPrimitiveSet`，位置作为玩家根节点下的 local position。
- unit cube 和 unit sphere 作为基础模板或共享 mesh 源数据。
- 按颜色缓存复用材质。
- 渲染适配层可生成 render-only 子实体或等价显示对象，但这些对象不挂输入、移动、血量、技能、authority 或业务状态。
- 每个 primitive 不作为玩法 Entity，不拥有独立玩法 Transform、Visibility、Material 或逐帧逻辑。
- 方圆蓝图和 runtime 数据不包含 rotation，Bevy `Transform` 的 rotation 只保留默认值。
- RON 仍作为开发期源格式，但不把它视为长期运行期格式。
- 非法 primitive 跳过并记录日志。

验收标准：

- RON 语法错误不会导致游戏崩溃。
- 最小玩家 RON 默认包含 2 个 primitive，且不超过 `max_primitives`。
- 所有 kind 只允许 `cube` 和 `sphere`。
- 不生成地面以下主体结构。
- 场景中能看到一个 cube 身体和一个 sphere 头部组成的玩家。
- 移动玩家根 Entity 时，身体和头部整体跟随。
- 修改 RON 中的 position、size 或 color 后，可视结果对应变化。
- 蓝图、runtime 类型和渲染适配代码中不新增方圆 rotation 能力。
- `cargo fmt` 和 `cargo check` 通过。

主要风险：

- render-only 子实体被误接入玩法逻辑，导致 primitive 泄漏为玩法 Entity。
- 为了表现角色方向而引入旋转字段，破坏方圆系统约束。
- 过早做 mesh 合并、GPU instancing 或动态 VFX，拖慢最小闭环验证。

控制方式：

- 第一版固定只做 cube 身体和 sphere 头部，不扩展复杂角色建模。
- code review 时重点检查 primitive 子实体是否只承担渲染职责。
- 所有朝向和动作表现后续通过位移、局部分布、scale、生成和消失表达。

### 阶段 2：统一方圆数据模型

目标：

- 角色、家园、装备、技能、NPC、天道自演都能共享统一 primitive 结构。

技术做法：

- 已增加 `FangyuanPrimitive`、`FangyuanPrimitiveSet` 和 `FangyuanPrimitiveSetStats`。
- 已区分蓝图 primitive 和 runtime primitive。
- 已落地 role、alpha、emissive、material_profile_id、lifecycle 的数据位置。
- 当前 RON v1 仍可只填 kind、position、size、color，也可按需填写 role、alpha、emissive、material_profile_id、lifecycle。
- 明确 runtime primitive 只包含 kind、local position、scale、颜色、role、alpha、emissive、material profile 和生命周期数据，不包含 rotation。
- 玩家预览可为标准 Bevy 渲染派生 render-only 子实体，但这些子实体不是玩法 primitive Entity，不能挂输入、移动、血量、技能、authority 或业务状态。

验收标准：

- 当前玩家外观蓝图可以编译为统一 runtime primitive。
- 后续家园、装备和技能不用重新定义一套几何基础。
- 文档和代码命名能区分 blueprint、runtime、render instance。
- 数据结构中没有 rotation、quaternion、euler 或 angular velocity。

主要风险：

- 过度抽象导致第一阶段开发变慢。
- 字段一次性设计过多但没人使用。
- 玩家外观、静态场景和 VFX 的 runtime 结构过早分叉。

控制方式：

- 结构允许扩展，但实现只落地当前必要字段。
- 先用玩家最小蓝图验证模型，再接入家园和静态场景。

### 阶段 3：静态对象和家园蓝图预览

目标：

- 在玩家外观最小闭环稳定后，恢复或扩展本地静态方圆内容预览。
- 稳定读取 `project/assets/fangyuan/home_preview.ron` 或后续静态对象蓝图。
- 在当前 Bevy 场景中显示静态 cube / sphere 家园、装饰或阵法预览。

技术做法：

- 已生成 `FangyuanHomeObject` 逻辑根，并挂载 `FangyuanPrimitiveSet` 和 `FangyuanObjectState`。
- 已通过 `FangyuanBlueprint` 统一读取 RON v1 蓝图，并使用 `compile_skipping_invalid_primitives()` 编译到 `FangyuanPrimitiveSet`。
- 已通过 `FangyuanBlueprintCompileReport` 记录 authored、generated、skipped 和跳过原因。
- 已复用阶段 1 的 unit cube、unit sphere、`FangyuanRenderAssetCache` 和 render-only 子实体渲染适配层。
- 已控制 runtime primitive 数量在 1000 以内，默认家园蓝图 505 authored、493 generated、12 skipped below-ground。
- 已让 Reload、Clear 和 Exit 生命周期清理家园逻辑根及其 render-only 子实体。
- HUD 已使用 `FangyuanPrimitiveSetStats` 显示 primitive、cube、sphere、skipped、material 和 path，不从 render-only 子实体统计业务数据。

验收标准：

- 当前家园蓝图可以编译为统一 runtime primitive。
- `primitives.len()` 不超过 1000。
- 所有 kind 只允许 `cube` 和 `sphere`。
- 地面以下非法 primitive 被跳过并进入 compile report。
- 默认蓝图能清楚表达静态对象或家园主题。
- 蓝图、runtime 类型、家园逻辑根和 render-only 适配层都不新增 rotation、quaternion、euler、angular_velocity、rotate 或 spin 能力。
- `cargo fmt`、`cargo test fangyuan -- --nocapture`、`cargo test fangyuan_home -- --nocapture` 和 `cargo check` 通过。

本阶段明确不包含：

- Prefab 或 Scene Layout 拆分。
- Chunk、流式加载或 AOI。
- Bake 或发布期二进制格式。
- 静态 CPU mesh merge 或 GPU Instancing。
- LOD、热点降级或联网同步。
- 正式家园编辑器、蓝图持久化、装备挂点正式接入或技能规则层。

主要风险：

- 蓝图生成随机噪音太多，缺少造型可读性。
- 颜色材质过多导致 batch 分裂，但该阶段可以接受。
- 过早做复杂渲染会拖慢世界观验证。

### 阶段 4：Prefab 和场景布局拆分

目标：

- 已落地开发期 Prefab / Palette 和 Scene Layout 拆分，避免大型家园、场景和宗门工程把所有 primitive 写进一个大文件。

技术做法：

- 已增加 prefab / palette 源格式，用于定义可复用方圆组件，默认路径为 `project/assets/fangyuan/palettes/home_prefabs.ron`。
- 已增加 scene layout 源格式，只记录 prefab id、position、scale 和少量实例参数，默认路径为 `project/assets/fangyuan/layouts/home_layout.ron`。
- 保留 `minimal_player.ron` 和 `home_preview.ron` 作为简单样例；家园运行时默认读取 layout/palette，不再 fallback 到 simple blueprint。
- 编译时把 scene layout instance 展开为逻辑 Entity 的 `FangyuanPrimitiveSet`。
- 检查缺失 prefab、非法 instance、越界 primitive 和预算超限；顶层错误结构化返回，单个展开后非法 primitive 可跳过并 warning。
- report 记录 palette、prefab、used prefab、instance、generated、skipped、material、top-level/layout/palette valid，以及 `code`、`field_path`、`reason`。

验收标准：

- 同一个 prefab 可以在场景中复用多次。
- 场景布局文件不再重复记录大量相同 primitive。
- 一个复杂家园可以由多个家园物件或 prefab instance 组合出来。
- prefab 展开后仍通过统一 validator。
- expanded primitive 数量不超过 `1000`。
- 家园 HUD 可显示 `layout loaded gen 138/1000 skip 0`、`pal 1 pf 5 used 5 inst 40 mat 15`；Reload、Clear、Exit 行为无回退。

主要风险：

- prefab 层级过深导致定位问题困难。
- prefab 被滥用成绕过预算的隐藏容器。

控制方式：

- 初期只允许一层 prefab 引用。
- prefab 和展开后的 primitive 都计入预算。
- bake report 或调试面板显示 prefab 展开后的真实成本。
- 第四阶段不实现 Chunk、Bake、mesh merge、GPU Instancing、LOD、AOI、联网同步、正式家园编辑器、蓝图持久化、装备挂点或技能规则层。

### 阶段 5：蓝图审核和预算系统

目标：

- 已把世界观限制和技术限制统一成可执行审核。

技术做法：

- 已实现统一 `FangyuanAuditReport`，包含 `summary`、`status`、`finding`、`suggestion` 和 source 定位信息。
- 已实现 `FangyuanAuditBudgetProfile` 默认预算：`1000` hard primitive、`800` recommended primitive、bounds、体积、透明、发光和 material profile 限制。
- 已实现 primitive 数量、bounds、单体尺寸 / 体积、总量体积、alpha、emissive、material profile 的预算 finding。
- 已保留角色、四属性、职业和世界层级额度入口，但当前默认 profile 不依赖玩法数据。
- 已在 blueprint、prefab/palette、scene layout 和 runtime primitive set 预算面接入审核。
- 审核结果返回结构化 `code`、`field_path`、`reason`，并可返回 `ReducePrimitives`、`ShrinkBounds`、`RemoveAlpha`、`LowerEmissive`、`ReplaceMaterialProfile`、`ReduceWarningRole` 等降级建议。
- 家园预览已接入审核 HUD 和日志，Reload 时重新审核 layout/palette，Clear 保留最近审核状态，审核失败不生成展开内容。

验收标准：

- 非法蓝图、非法 prefab/palette、非法 layout 或硬预算失败不会生成非法内容。
- 审核失败能说明原因，并能通过 HUD 主 code 和日志 finding 定位。
- Warning 可继续生成内容，但 HUD 和日志必须暴露 warning 数量和主 code。
- 未来可以按角色、四属性、职业和世界层级接入灵构额度。
- `cargo fmt --check`、`cargo test fangyuan -- --nocapture`、`cargo test fangyuan_home -- --nocapture`、`cargo test fangyuan_player_preview -- --nocapture` 和 `cargo check` 已通过。

主要风险：

- 审核只做技术校验，无法约束战斗可读性。

控制方式：

- 从阶段 2 开始引入 `role`，为后续规则层和个性层分离做准备。
- 第五阶段只落地审核和预算，不落地 Chunk、Bake、mesh merge、GPU Instancing、LOD、AOI、联网同步、正式家园编辑器、蓝图持久化、装备挂点或技能规则层。

### 阶段 6：静态 CPU 合并渲染原型

目标：

- 已在不接入自定义 GPU instancing 的前提下，先降低大量静态 primitive 的 draw call。

技术做法：

- 已保留家园物件、宗门设施、天道装饰等逻辑 Entity；primitive 仍是 `FangyuanPrimitiveSet` 内部数据，不升级为玩法 Entity。
- 已新增静态合并输入、source 定位、稳定 merge group key 和统计报告，按区域占位、primitive kind、material profile、透明路径、颜色、发光和 debug label 分组。
- 已在加载或蓝图变更时把可合并静态 primitive 构建为一个或少量 Bevy `Mesh`，继续使用 Bevy 标准 mesh、`StandardMaterial` 和渲染路径。
- 已实现 cube 合并和低成本 sphere 合并。sphere 当前使用固定低多边形基模，作为移动端预算内的静态内容原型。
- 已跳过非空 lifecycle、`warning` / `trail` / `impact` / `socket` 等不适合静态合并的 role，以及非法 transform、scale、color、alpha、emissive 或 material profile。
- 玩家、技能和短生命周期动态 primitive 不走静态合并路径。
- 家园预览已有 `cpu_merge` 渲染模式，默认仍是 `standard`。

验收标准：

- 静态场景不需要为每个 primitive 创建玩法 Entity。
- 默认家园或测试场景可以在 `cpu_merge` 模式下合并为少量 mesh 并正常显示。
- Reload、Clear、场景退出和 layout 变更后可以释放旧合并 mesh、material handle 和统计状态，再重建对应静态 mesh。
- 合并路径不引入 rotation 字段。
- 合并报告能记录 authored、expanded、merged group、cube、sphere、skipped、material profile、estimated vertex 和 estimated index 数。

主要风险：

- 大型 mesh 初始化或重建造成加载卡顿。
- 合并后单个 primitive 的调试定位变难。
- 不同透明状态、材质 profile、颜色或发光被错误合并后会产生错误表现。
- 过大单 mesh 可能影响移动端内存、上传时间和局部更新效率。

控制方式：

- 当前按区域占位和 batch key 分组，不生成无限大的单一 mesh；后续真正 Chunk / AOI 接入前，不能把该占位理解为已实现流式 Chunk。
- 保留标准渲染子实体路径作为调试和失败 fallback。CPU merge 构建失败时，家园预览默认回退到 `standard` 并清理旧 merge 资源。
- 通过 source range、source ref、bounds 和 debug name 保留定位信息。
- 透明与不透明分组，不把透明路径混入不透明合并路径。

### 阶段 7：静态实例化渲染原型

目标：

- 已建立静态实例化渲染原型，用于验证大量静态方圆 primitive 的 shared mesh + instance data 数据路径。

技术做法：

- 保留家园物件、宗门设施、天道装饰等逻辑 Entity。
- 已新增 `FangyuanStaticInstance`、batch key、buffer source、bounds、source refs、hash 和 cache dirty 判断。
- instance 数据包含 position、scale、color、alpha、emissive、material_profile_id 和 source 定位。
- batch key 按 primitive kind、material profile 和透明路径分组；颜色和发光作为 per-instance 数据进入 buffer hash，不进入 batch key。
- 家园 `static_instance` 模式当前是 shared-mesh prototype：复用 cube / sphere shared mesh handle，并为每个 instance 生成 render-only 可视实体，用于验证模式、生命周期、HUD stats、fallback 和资源清理。
- 当前还不是正式 GPU instance buffer / custom render pipeline。正式 GPU instancing 仍是后续渲染管线工作。

验收标准：

- instance report 可以消费万级静态 primitive 数据并输出 batch、instance、buffer bytes、hash 和 pressure summary。
- 家园 `static_instance` 模式可以显示默认 layout，并在 HUD / 日志中显示 mode、batch count、instance count、buffer bytes 和 fallback reason。
- 不同颜色、尺寸、透明、发光和 material profile 可以在同一实例数据路径中表达。
- Reload、Clear、场景退出、重复进入和 mode 切换后可以清理旧 runtime state。
- 蓝图变更后可以重建实例数据；同内容不应无意义重建。

主要风险：

- Bevy 自定义渲染管线接入复杂。
- 调试难度上升。
- shared-mesh prototype 仍有 per-instance render-only 实体，不能用来证明最终 GPU instancing 的 draw call 成本。
- buffer bytes 和透明 / 发光组合增加后，移动端内存和排序压力仍需后续真机评估。

控制方式：

- 先保留第一阶段标准渲染适配和阶段 6 静态 CPU 合并作为 fallback。
- 只对静态家园或测试场景启用实例化路径。
- static instance prototype 失败时，家园预览默认 fallback 到 `standard`，并在 HUD / 日志记录 fallback reason。
- 后续接入正式 GPU instance buffer 前，不把该原型扩展到动态 VFX、技能表现或联网同步路径。

### 阶段 8：统一方圆材质

目标：

- 已建立统一 `FangyuanMaterialProfile` 和 profile table，用于支持多颜色、多发光、多基础材质感，同时尽量不打碎渲染批次。

技术做法：

- 已定义 `FangyuanMaterialProfile`，包含 stable id、version、base params、alpha policy、emissive policy 和 debug label。
- profile table / registry 内置默认 profile `material:default`，缺省 `material_profile_id` 使用默认 profile。
- primitive 字段仍是 per-instance 输入；profile 提供 base color / alpha / emissive 与 alpha、emissive 合成策略。
- `material_profile_id` 已贯通 simple blueprint、prefab、layout compile output、CPU merge、static mesh、static instance 和 standard 渲染路径。
- Standard / StaticInstance 路径使用 profile 合成后的材质参数；CPU merge 继续用顶点色承载多颜色并复用少量材质。
- 默认不透明；透明走单独预算和路径，发光使用 emissive 统计和预算，不引入大量动态灯光。

验收标准：

- 同屏大量不同颜色 primitive 不需要创建线性增长的材质资源。
- 发光强度可以按实例变化，并被 stats / audit / HUD / debug log 统计。
- 材质 profile 可以表达基础视觉差异，并在 blueprint、prefab、layout、merge 和 instance 路径中保留。
- 缺省、非法或未知 profile 有默认 profile fallback；非法 profile id 在蓝图审核中暴露为 `invalid_primitive_material_profile`。

主要风险：

- 半透明和不透明混在一起导致排序和性能问题。
- profile 数量膨胀会重新切碎 batch，抵消 CPU merge 或 static instance 的收益。
- profile policy 过度复杂后会变成变相任意材质系统，增加审核和移动端兼容风险。

控制方式：

- 不透明和透明分通道。
- 透明 primitive 数量设硬预算。
- material profile 数量设推荐和硬预算；默认审核 profile 推荐不超过 `8`，硬限制 `24`。
- `material_profile_id` 只允许受控 ASCII id，不允许脚本、shader、外部资源引用或玩家任意材质程序。
- 统一 profile fallback 只能用于安全显示和诊断，不能掩盖审核失败或预算超限。

### 阶段 8.5：规模、fallback 和开发期验收

阶段 6 至 8 已补充规模和失败路径验证：

- 测试侧使用万级静态 primitive 生成器验证 standard、CPU merge 和 static instance 的 primitives、entities、meshes、batches、materials、profiles、buffer bytes 和 pressure summary。
- CPU merge、static instance 和 material profile 均覆盖 fallback / failed budget / unsupported kind / render initialization failure 等失败路径。
- 默认家园统计可解释：standard、CPU merge 和 static instance 的 primitive 总数、material profile 数和压力趋势必须一致或差异可说明。
- 家园预览开发期环境变量 `MYBEVY_FANGYUAN_HOME_RENDER_MODE=standard|cpu_merge|static_instance` 可显式切换三种模式；未设置或非法值回到 `standard`。
- Windows 桌面可视验收如默认图形后端不稳定，可临时设置 `WGPU_BACKEND=dx12` 后用 `phone-small` 窗口复验三种模式。

阶段 6 至 8 仍不包含动态 VFX、技能规则层、正式 Chunk / LOD / AOI、发布期 Bake、蓝图缓存继承、正式 GPU instance buffer / custom render pipeline、联网同步或任意 shader。

### 阶段 9：程序 VFX 播放器

目标：

- 已支持技能和短生命周期表现，从第一版开始就不创建动态 primitive Entity。

技术做法：

- 已新增 `FangyuanVfxRecipe`，包含 id、version、duration、seed policy、emitters、curves 和 budget hints。
- 已支持 spawn、move、scale、fade、color_shift、emissive_pulse、trail、impact_expand 等受控 operator。
- 已新增离散 `FangyuanVfxClock`、`FangyuanVfxReplayEvent` 和 `compose_fangyuan_vfx_seed()`，seed 合成覆盖 recipe id、version、caster id、event id、start tick 和 emitter index。
- `evaluate_fangyuan_vfx_recipe()` 是纯函数入口，同一 recipe、start tick、replay event 和 seed 能生成稳定 dynamic primitive state。
- 一个 `FangyuanVfxRuntime` 管理多个 VFX instance，结束、Clear、Reload 时释放 active state、fallback primitive 和统计状态。
- 当前动态结果先输出 `FangyuanVfxDynamicPrimitiveState` 和标准 Mesh fallback primitive，用于数据验证、试炼场和回放测试；正式动态 GPU instance buffer / custom render pipeline 仍是后续渲染管线工作。
- VFX recipe 已接入 audit、budget estimate、budget pressure degrade 和 primitive state hash。

验收标准：

- 投射物、范围、护盾、命中扩散、拖尾和淡出可用方圆 primitive state 表达。
- 同一个 start tick、seed 和 replay event 可稳定回放，并有 hash 测试覆盖。
- 单技能和默认 showcase 可在试炼场预算汇总中显示 VFX 成本。

主要风险：

- 表现容易像工程调试效果。
- Windows / MSVC 增量链接缓存偶发失败会影响定向测试稳定性。

控制方式：

- 用颜色曲线、发光、拖尾、命中反馈和残留层增加表现厚度。
- 遇到增量链接缓存错误时，关闭 `CARGO_INCREMENTAL` 复跑定向测试。

### 阶段 10：技能规则层和个性层

目标：

- 已建立技能模板和视觉蓝图分层，玩家自定义技能视觉不能破坏战斗可读性。

技术做法：

- 已新增 `FangyuanSkillTemplate`，表达 rule layer、range shape、direction、danger boundary、cast / impact timing、forced visible element 和 authority behavior。
- 已新增 `FangyuanSkillVisualBlueprint`，引用 skill template，并定义颜色、material profile、VFX recipe、trail、decor、impact residue、emissive 和装备 socket binding 等个性层字段。
- 已新增字段权限策略，规则层字段由系统锁定，玩家只调整受控个性层，部分个性层字段只能通过审核建议降级。
- 默认模板覆盖 projectile、circle area、cone 和 shield。
- 已新增技能可读性审核，检查视觉范围误导、规则层遮挡、颜色冲突、透明和发光预算。
- 已新增 runtime presentation，将 template + visual blueprint 编译为规则层 VFX state 与个性层 VFX state，并保证规则层播放顺序、可见性和生命周期不被个性层覆盖。
- 已定义表现降级等级，优先移除装饰、残影、透明、发光和长 trail，规则层不随个性层降级而消失。

验收标准：

- 同一技能模板在不同玩家皮肤下仍能识别真实范围、方向和危险边界。
- 审核能发现视觉范围过小、形状误导、规则层遮挡、颜色冲突和个性层超预算。
- 降级后规则层 hash 和播放状态保持稳定。

主要风险：

- 玩家追求个性导致遮挡和误导。
- 如果后续把完整战斗数值、职业技能库或服务端结算塞进视觉蓝图，会破坏当前分层。

控制方式：

- 审核遮挡面积、发光强度、颜色冲突和规则层可见性。
- 完整战斗结算、职业技能库、真实伤害、控制时间、冷却和消耗仍归技能规则 / 服务端系统，不属于本阶段视觉蓝图能力。

### 阶段 11：装备、NPC 和天道自演接入

目标：

- 已让非家园内容复用方圆渲染底座，并保持纯数据、可审核、可预算、可降级。

技术做法：

- 已新增 `FangyuanEquipmentBlueprint`，可编译为 `FangyuanEquipmentRuntime` 和 `FangyuanPrimitiveSet`。
- 装备提供 grip、tip、core、guard、aura 语义 socket，socket 记录位置、语义、引用规则和 fallback。
- 技能 visual blueprint 可声明装备 socket binding，把 socket 用作 emitter origin、move from / to 或 decor anchor；缺失 socket 会生成明确 fallback diagnostic。
- 已新增 `FangyuanNpcBlueprint` / profile，使用 body、core、marker、aura、nameplate 等低成本 primitive 表达 NPC。
- NPC 支持 idle、moving、casting、damaged 等少量状态的 scale、alpha、emissive 和 lifecycle 表现变化，并可降级为 silhouette、marker 或 nameplate。
- 已新增 `FangyuanTiandaoManifestation` 和生命周期 FSM，覆盖 manifest、decay、solidify、recycle 四类状态，记录 cause、region、budget cost、ttl、solidify score 和预算回收结果。
- VFX、技能、装备、NPC 和天道生成物已接入统一 `FangyuanObjectBudgetProfile`、object budget audit、object class 优先级和试炼场 showcase。

验收标准：

- 技能可以引用装备 socket，缺失 socket 不会静默失败。
- 天道生成物可以显化、衰退、固化和回收，并释放预算。
- NPC 和天道临时内容可以按预算降级，优先保留规则层、交互核心和低成本 marker。
- 试炼入口可同时展示 projectile、range、shield、impact、装备、NPC 和天道生成物，并输出对象预算摘要。

主要风险：

- 装备和 NPC 需求逼迫引入传统模型复杂度。
- 天道生成物如果默认永久存在，会造成内容和性能预算堆积。

控制方式：

- 关键角色模型和方圆抽象 NPC 分层处理，不把所有对象都推向同一美术成本。
- 天道生成物默认临时，必须通过因果值、固化条件和审核后才能长期保留。
- 第九至第十一阶段仍不包含完整战斗结算、职业技能库、传统骨骼模型、正式 Chunk / AOI、发布期 Bake 或纪元继承；这些仍按阶段 12 至 14 或独立系统处理。

### 阶段 12：空间 Chunk、LOD、AOI 和热点降级

目标：

- 支撑大世界局部加载、多人同屏和天道灵压。

技术做法：

- 增加 chunk 作为方圆内容的空间加载单元。
- 按 AOI 异步加载玩家周围 chunk，远离后卸载或降级。
- chunk 内记录 prefab instance、天道生成物引用、静态装饰和区域元数据。
- 实现 L0 到 L4 表现档位。
- 接入距离、屏幕占比、重要性、队伍关系和灵压等级。
- AOI 决定加载和同步范围。
- 热点优先降低装饰层、透明、发光和拖尾。

验收标准：

- 客户端不需要一次性加载完整世界。
- 玩家移动时 chunk 加载和卸载不会造成明显卡顿。
- 多技能叠加时帧率可控。
- 远处玩家不会完整播放高成本技能。
- 热点区域降级后仍保留规则可读性。

主要风险：

- 玩家感觉系统粗暴削弱表现。

控制方式：

- 用天道灵压做预警和包装。
- 保留自身完整表现或较高优先级表现。

当前已落地的第 12 阶段工作流边界：

- `FangyuanChunkManifest` / `FangyuanChunkSource` 已覆盖 chunk id、bounds、region metadata、prefab instance refs、tiandao refs、static decoration refs、budget summary，以及未来 artifact 的 bin/hash/data version 字段。
- 方圆家园接入本地 chunk runtime，支持按调试位置或玩家位置选择附近 chunk、加载、卸载、reload、失败 fallback 和场景退出 clear；HUD 输出 loaded chunks、visible objects、load state 和失败原因。
- `FangyuanLodLevel` 固定 L0-L4 表现层级，AOI selector 输出 load/keep/unload/marker chunk 和 object decision；hysteresis、自身优先级和规则层保留均有测试覆盖。
- 热点灵压模型把 active skill、dynamic primitive、transparent、emissive、trail 和 chunk load pressure 转成可解释的天道灵压摘要；降级 plan 保证规则层压缩排在最后。
- 渲染集成已生成 static merge、static instancing、VFX、skill layer、equipment、NPC 和 tiandao 的 render path decision，并用 100、300、1000 级压力场景记录瓶颈和降级结果。
- 该阶段没有把方圆 chunk 提升为通用 `framework/scene` streaming 实现；场景框架文档中的 scene chunk 仍是 framework manifest 元数据和预留接口。

### 阶段 13：发布期二进制 Bake 和运行时加载

目标：

- 避免上线后移动端运行期解析大量 RON，并为 CDN、首包和后续下载资源做准备。

技术做法：

- 增加 `fangyuan_bake` 工具或仓库脚本。
- 开发期继续使用 RON 作为源格式。
- 打包期把 prefab、scene layout、chunk 和蓝图编译为 `.bin`。
- 二进制格式可评估 `bincode` 或 `postcard`。
- bake 阶段执行 validator、版本升级、hash 计算和依赖表生成。
- 输出 bake report，记录 primitive 数、prefab 数、chunk 数、预算和警告。
- 运行期优先读取二进制发布格式，RON 仅用于开发和调试。

验收标准：

- 发布构建不需要解析大体量 RON。
- 同一份源 RON 能稳定 bake 出可加载二进制。
- bake 失败能准确指出源文件、prefab、chunk 或 primitive 的问题。
- 移动端加载峰值和加载时间可控。

主要风险：

- 开发期 RON 和发布期 bin 语义不一致。
- bake 工具和游戏运行时使用了两套校验逻辑。

控制方式：

- bake 工具和游戏共用核心数据结构、validator 和版本升级代码。
- CI 或提交前检查可以增加 bake dry-run。
- 保留小规模 RON debug 加载入口，但不作为正式运行路径。

当前已落地的第 13 阶段工作流边界：

- 开发期一键 dry-run 从仓库根目录执行：`.\scripts\run-fangyuan-bake-dry-run.ps1`。
- 脚本默认读取 `project/assets/fangyuan`，调用 `cargo run --quiet --bin fangyuan_bake -- --input <dir> --output <dir> --dry-run --report <path>`，report 写入 `artifacts/fangyuan-bake/dry-run/report.txt`。
- `artifacts/` 已被 Git 忽略；dry-run 只写 report，不写 `.fyb` 输出目录。正式本地 bake 如需清理旧产物，可以使用 `--clean-output`，该参数只在非 dry-run 下清理 output 目录。
- 当前仓库没有 `.github` CI workflow，也没有通用本地检查脚本；后续接入点是在 CI 或提交前脚本中追加 `.\scripts\run-fangyuan-bake-dry-run.ps1`，并把 `artifacts/fangyuan-bake/dry-run/report.txt` 作为构建 artifact。
- 当前 `.fyb` 是 `FYBAKE` 自定义 header + typed payload 的 artifact；payload 仍使用可解析的 RON typed payload，用于先固定 schema、hash、依赖表和 runtime loader 语义。它不是最终压缩二进制编码性能承诺。
- bake report 每条 entry 输出 `source_bytes`、`artifact_size`、`peak_resource_count`、`ron_load_us`、`bin_load_us`、hash、warning/error 和依赖缺失数量。`ron_load_us` 统计源 RON 的 parse / upgrade / validate / payload compile，`bin_load_us` 统计内存中 artifact 的 header / schema / kind / hash / typed payload decode；这些是开发机 dry-run 诊断字段，不代表手机真机性能数据。
- RON 路径的错误处理侧重 parse、版本升级、validator 和依赖发现；bin 路径额外先校验 header magic、schema version、artifact kind、content/source hash 和 payload version。debug loader 可以在 bin 失败后 fallback 到 RON，release loader 默认不允许 RON fallback。
- 手机比例窗口的首包场景验证命令仍是 `Set-Location project; $env:MYBEVY_START_SCENE="dev.fangyuan_home"; cargo run -- --window-profile phone-small --window-scale 50%`。当前验证边界是确认新增 bake 工具和 `.fyb` 产物策略不改变 RON 首包加载；只有把 `.fyb` 放入 `project/assets` 并接入具体 manifest 后，才声称验证了发布二进制首包加载。
- Android 构建边界：当前 Gradle 会打包整个 `project/assets`，所以只有明确决定发布的 `.fyb` 才能放入 `project/assets`。需要验证 APK 构建时，先运行 dry-run，再执行 `cargo ndk -t arm64-v8a -P 26 -o ..\android\app\src\main\jniLibs rustc --release --lib --crate-type cdylib` 和 `.\gradlew.bat assembleDebug`；本流程不要求每次第 13 阶段文档改动都长时间跑完整 APK。

### 阶段 14：蓝图缓存、流式加载和纪元继承

目标：

- 支撑长期 MMO 内容积累和线上资源更新。

技术做法：

- 蓝图审核后生成 id、version、hash。
- 客户端缓存常用蓝图。
- 缺失蓝图时显示降级默认表现。
- prefab、chunk 和 bake 产物都带 version 与 hash。
- 线上更新可以下发二进制 chunk、prefab 或蓝图包。
- 家园、装备和技能蓝图可随纪元继承，但进入新世界重新校准预算。
- 天道自演固化内容进入区域或纪元档案。

验收标准：

- 不需要每次同步完整视觉蓝图。
- 不需要每次更新都重新下载整个世界资源。
- 纪元迁移不会清空玩家视觉资产。
- 新世界能按当地规则降级旧蓝图。

主要风险：

- 历史蓝图版本过多，兼容复杂。

控制方式：

- 蓝图版本化。
- 编译器提供旧版本升级或兼容路径。
- 客户端缓存不是权威数据，服务端审核蓝图和设计源数据才是权威来源。

当前已落地的第 14 阶段工作流边界：

- `FangyuanBlueprintIdentity` 统一记录 resource kind、id、version、content hash、schema hash、source hash、dependency hash 和 source kind，资源类型覆盖 blueprint、prefab、chunk、material profile、skill visual 和 bake artifact。
- `FangyuanBlueprintCacheManifest` / cache runtime 记录 root、capacity、used bytes、entry identity、hash、version、size、last_used、use_count、dependencies 和 source kind；读取时校验版本、内容 hash、dependency 和文件 hash，损坏或不兼容内容会 miss 或失效。
- 缺失蓝图 fallback 已区分 home、equipment、skill、NPC 和 generic，分别落到 marker、default appearance、rule-only、pending 或 hidden，避免用视觉 fallback 误导规则范围。
- Streaming update manifest 支持针对 chunk、prefab、blueprint、material profile 和 skill visual 的 Install/Replace/Keep 计划，只更新受影响资源，并带 rollback key。
- 更新包安装前校验 manifest/version/hash/dependency/budget/signature placeholder/permission placeholder；当前签名和权限是占位模型，不是完整生产级签名加密或运营权限系统。
- 纪元继承迁移会对旧蓝图重新走版本升级、blueprint audit、object budget audit 和降级建议；输出 kept、degraded 或 rejected 结果，不默认把历史视觉资产原样带入新世界。
- Cache authority manifest 明确服务端 audit result、override 标记和审计日志；客户端缓存命中只能提供 bytes，不能覆盖服务端审核、预算、权限和资产归属判断。
- 该阶段不包含真实 CDN 下载器、商业发布后台、账号资产交易、跨服资源分发、最终云压测平台或完整服务器集群。

### 阶段 15：试炼场和完整调试工具

目标：

- 让玩家理解预算，让开发者定位性能。

技术做法：

- 灵构试炼场展示审核和预算结果。
- 开发调试面板展示实例数量、batch、buffer 更新、LOD 和灵压。
- 压力测试场景模拟 100、300、1000 人技能释放。

验收标准：

- 玩家能看到蓝图为什么被降级。
- 开发者能定位性能瓶颈。
- authority 回放下视觉一致性可验证。

主要风险：

- 没有工具时，后续每次优化都靠猜。

控制方式：

- 试炼场和调试面板不应拖到最后才做，至少从阶段 6 开始逐步建设。

当前已落地的第 15 阶段调试工具边界：

- 方圆 debug metrics bus 已统一 primitive、render、LOD、AOI、pressure、cache、bake、audit 和 trial 等指标口径，支持采样间隔、滚动窗口、峰值、平均值和 reset，避免 HUD 直接读取散落模块内部状态。
- 玩家灵构试炼场已接入默认家园、装备、技能和外观样例，能展示审核状态、预算档位、降级前后对比、kept / degraded / rejected 结果、fallback 和通俗降级原因。
- 开发者 debug panel 默认隐藏详细指标，可按模块查看 render、LOD、AOI、热点灵压、cache、bake、audit 和 trial 摘要；该面板是开发期定位工具，不是玩家常驻 HUD。
- Pressure simulation 已提供本地 deterministic 100 / 300 / 1000 人技能释放模拟，记录 seed、人数、技能模板、触发频率、场景大小、chunk 数、预算 profile、压力曲线和降级摘要，不依赖外部联网服务。
- Visual replay consistency 已能在 authority replay 下生成视觉摘要 hash，覆盖 VFX state、规则层、个性层、LOD、降级、cache / fallback 和关键材质参数；hash 不一致时报告 tick、frame、event、recipe、object 和差异字段。
- Debug report / baseline 已定义本地报告 schema、输出策略和 pressure baseline 比较格式，覆盖 audit、budget、render、LOD、AOI、cache、bake、pressure 和 replay 摘要；运行产物默认放入被忽略的 `artifacts/fangyuan-debug/`。
- 该阶段只完成本地试炼、开发调试、压测模拟、报告 schema / baseline 和回放一致性验证，不包含运营后台、云压测平台、商业监控系统、线上告警、商业观测计费或生产级监控数据管线。

## 推荐优先级

如果只看近期开发，建议优先顺序是：

1. 方圆玩家外观最小闭环。
2. 统一方圆 primitive 数据模型。
3. 静态对象和家园蓝图预览。
4. Prefab 和场景布局拆分。
5. 蓝图审核和预算。
6. 静态 CPU 合并渲染原型。
7. 静态实例化原型。
8. 统一方圆材质。
9. 程序 VFX 播放器。
10. 技能规则层和个性层。
11. 装备、NPC、天道自演全面接入。
12. Chunk、LOD、AOI 和热点降级。
13. 发布期二进制 Bake 和运行时加载。
14. 蓝图缓存、流式加载和纪元继承。
15. 大规模压力测试和长期调优。

原因：

- 玩家外观最小闭环能最快验证“逻辑 Entity 持有 primitive set，primitive 不是玩法 Entity”的核心边界。
- 统一数据模型越早做，后续返工越少。
- 家园和静态对象随后用于验证较大规模静态内容、颜色复用和造型可读性。
- Prefab 和布局拆分越早做，越不容易把数据写成无法维护的大文件。
- 审核和预算是 AI 生成内容的底线。
- 静态 CPU 合并比自定义实例化实现成本低，适合作为中期过渡和 fallback。
- 静态实例化先于动态 VFX，风险更低，但不应在最小玩家 Demo 阶段提前引入。
- Chunk 和二进制 Bake 属于规模化前置能力，应在大世界和移动端压力出现前建设。
- 技能和多人热点最复杂，应等底座稳定后推进。

## 关键风险

### 风险一：过早追求自定义渲染

自定义渲染管线会提高性能上限，但也会带来复杂度。

控制方式：

- 第一阶段先用 Bevy 标准渲染验证玩法。
- 实例化渲染先做独立原型。
- 保留第一阶段批量 mesh 或标准渲染适配 fallback，直到实例化路径稳定。

### 风险二：primitive 泄漏为玩法 Entity

正式架构如果出现一个 primitive 对应一个玩法 Entity，就会破坏从第一阶段确立的逻辑对象边界，并且很快变成 ECS、Extract 和可见性计算的性能债。

控制方式：

- 从第一阶段开始禁止把 primitive 作为玩法 Entity。
- 家园、技能、装备、NPC、天道生成物都只能持有 primitive 数据集或其 handle。
- 如果为了调试临时生成 primitive 可视对象，必须隔离在 debug-only 路径，不纳入正式架构。
- code review 时重点检查是否新增了 primitive 粒度的 Transform、Visibility、Material 和逐帧系统。

### 风险三：材质自由导致批次爆炸

玩家想要丰富颜色和材质，但底层不能为每种视觉差异创建独立材质。

控制方式：

- 实例数据携带颜色和 profile。
- 材质 profile 数量受控。
- 纹理能力后置。

### 风险四：大 RON 文件导致加载和内存峰值失控

如果把大型家园、地图或宗门工程的所有 primitive 全部写进一个文本文件，开发期会难以维护，运行期也会被文本解析、内存分配和一次性加载拖垮。

控制方式：

- 从中期开始使用 prefab / palette 复用结构。
- 场景布局只记录 prefab instance，不重复记录所有 primitive。
- 大世界内容按 chunk 拆分和异步加载。
- 开发期保留 RON，发布期通过 bake 工具转换为二进制包。
- bake report 必须显示展开后的 primitive 数、文件体积、chunk 数和预算。

### 风险五：透明和发光失控

透明和发光最容易造成视觉遮挡和性能问题。

控制方式：

- 默认不透明。
- 透明单独预算。
- 发光强度总量预算。
- 热点优先压制透明和发光。

### 风险六：技能自定义破坏可读性

玩家可能把危险技能做成不明显，或把无害装饰做成强危险提示。

控制方式：

- 系统固定规则层。
- 玩家只控制个性层。
- 审核真实范围和视觉范围一致性。
- 试炼场检查多技能叠加。

### 风险七：天道自演内容永久堆积

如果生成物没有生命周期，世界会越来越重。

控制方式：

- 默认临时。
- 因果值决定固化。
- 衰退和回收释放预算。
- 固化内容也需要按区域和距离加载。

## 决策口径

方圆灵构长期渲染方向是：

```text
受控几何实例动画
而不是任意模型和任意特效资源系统
```

家园、装备、技能、NPC、场景道具和天道自演都应尽量收敛到：

```text
cube / sphere
position / scale
color / alpha / emissive
material profile
role
budget
LOD
```

1000 人热点场景的可行前提是：

```text
服务端只模拟规则模板
网络只同步语义事件
客户端只渲染 AOI 内且预算内的表现
自定义只影响可降级视觉层
规则层永远清楚
```

这条路线牺牲了传统美术资产的自由度，但换来：

- 世界观统一。
- AI 生成可审核。
- 玩家创作可继承。
- 渲染底层可扩展。
- 多人热点可降级。
- 移动端有优化空间。

## 动态表现阶段建议

第一阶段：静态与低频动态验证。

- 复用方圆灵构蓝图规则。
- 支持 cube / sphere。
- 支持创建、消失、移动、缩放和颜色变化。
- 不支持旋转。
- 不支持服务端判定接入。
- 支持单技能预览。

第二阶段：技能模板与表现映射。

- 增加投射物、范围、护盾等基础模板。
- 增加 `SkillVisualBlueprint`。
- 增加规则层和个性层。
- 增加本地试炼场。

第三阶段：性能预算与 LOD。

- 增加 primitive 预算。
- 增加自身、近处、远处和拥挤区域 LOD。
- 增加渲染批处理或 instancing。
- 增加预算调试面板。

第四阶段：authority 回放。

- 技能释放事件只同步模板、蓝图 id、tick、方向和 seed。
- 客户端按起始 tick 还原表现。
- 对比多客户端回放一致性。

第五阶段：热点场景验证。

- 构造 100、300、1000 人压力测试。
- 分别验证服务端事件吞吐、客户端渲染帧率、网络下行和 LOD 降级。
- 将天道灵压接入热点提示、特效降级和分流规则。

当前第九至第十一阶段已经完成第一至第四阶段中的纯数据与测试闭环：VFX recipe、技能模板、视觉蓝图、装备 socket、NPC profile、天道 FSM、authority replay event 对齐和统一对象预算。第三阶段中的正式 LOD、多距离表现档位、正式动态 GPU instancing，以及第五阶段中的大规模热点压测仍未完成。

## 动态表现风险

主要风险：

- 1000 人场景如果全量同步，网络先成为瓶颈。
- 每个 primitive 一个 Entity 会带来明显 ECS 和调度压力。
- 大量透明叠加和动态光源会比 primitive 数量更早击穿客户端性能。
- 玩家自定义如果不分可读层和个性层，会破坏战斗可读性。
- 如果视觉 primitive 参与服务端判定，复杂度会迅速失控。
- 如果没有试炼场和预算反馈，玩家无法理解为什么蓝图被降级。
- 如果把当前视觉模板误当完整战斗系统，会导致职业技能库、数值结算和表现审核混在一起。

## 动态表现决策口径

方圆灵构程序动画的长期方向是：

```text
受控几何实例动画
而不是任意动画资源系统
```

1000 人场景的可行前提是：

```text
服务端只模拟规则模板
网络只同步语义事件
客户端只渲染可见且预算内的表现
自定义只影响可降级视觉层
```

球体、正方体、移动、缩放、颜色和发光足以形成清晰风格，但必须依赖材质、节奏、拖尾、命中反馈和 LOD 才能避免表现单薄。

当前文档只承诺受控动态表现和对象接入底座。完整战斗结算、职业技能库、传统骨骼模型、正式 Chunk / AOI、发布期 Bake、蓝图缓存和纪元继承仍需要独立阶段设计和验证。
