# 方圆灵构资源构建与加载

本文由原《方圆对象资源构建与渲染技术路线》的资源层次、发布格式和加载章节迁移而来。本轮仅调整文档结构，不改变规则语义。

对象模型和渲染架构见 [运行时与渲染架构](./运行时与渲染架构.md)，AI 生成与图集材质资源合同见 [AI 生成与图集材质渲染](./AI生成与图集材质渲染.md)，阶段记录见 [路线图](../路线图.md)。

## 数据层次化与发布格式

### 为什么不能把所有 primitive 写进一个大 RON

方圆灵构会天然走向数据配置化，但配置化不等于把几十万 primitive 的位置、大小、颜色全部写进一个巨大 `.ron` 文件。

这种做法会带来几个直接问题：

- 文件体积可能达到几十 MB 甚至上百 MB。
- 游戏启动时文本解析会造成明显卡顿。
- 手机端可能因为一次性读取、解析和分配大量对象导致内存峰值过高。
- 每次小改动都需要重新加载大文件，编辑和热重载体验很差。
- 蓝图继承、版本升级、局部下载和 CDN 更新都会变得笨重。

因此，方圆灵构的数据路线必须从一开始就考虑：

```text
结构拆分
-> 空间分块
-> 开发期文本
-> 发布期二进制
-> 运行时异步加载和缓存
```

简化口径：

```text
RON 是开发期人类可读格式
二进制包是运行期加载格式
```

### 结构拆分：Prefab 和 Scene Layout

不要让一个配置文件描述整个世界的所有 primitive。更合理的是把数据拆成两层。前三阶段只验证 simple blueprint 和统一 primitive；第四阶段已经落地开发期 Prefab / Palette 与 Scene Layout 拆分，当前仍不涉及 chunk、bake 或发布期二进制格式。

第一层是组件预制体配置，也可以称为 palette 或 prefab。它定义可复用的基础物件：

```ron
(
  version: "1",
  prefabs: {
    "oak_tree": (
      primitives: [
        (
          kind: "cube",
          position: [0.0, 1.5, 0.0],
          size: [1.0, 3.0, 1.0],
          color: [0.50, 0.30, 0.10, 1.0],
        ),
        (
          kind: "sphere",
          position: [0.0, 3.2, 0.0],
          size: [3.0, 3.0, 3.0],
          color: [0.10, 0.80, 0.10, 1.0],
        ),
      ],
    ),
    "stone_wall": (
      primitives: [
        // ...
      ],
    ),
  },
)
```

第二层是场景实例配置。它不再重复描述树干、树冠、墙体这些 primitive，而是记录“哪个 prefab 放在什么位置”：

```ron
(
  version: "1",
  instances: [
    (prefab: "oak_tree", position: [10.0, 0.0, 5.0], scale: [1.0, 1.0, 1.0]),
    (prefab: "oak_tree", position: [12.0, 0.0, -2.0], scale: [1.2, 1.2, 1.2]),
    (prefab: "stone_wall", position: [0.0, 0.0, 0.0], scale: [1.0, 1.0, 1.0]),
  ],
)
```

这样可以把大量重复 primitive 压缩成少量 prefab 定义和实例引用。一个由几万个 primitive 组成的场景，可能只需要几十个 prefab 和几百到几千条 instance 记录。

第四阶段默认首包资源路径：

```text
project/assets/fangyuan/palettes/home_prefabs.ron
project/assets/fangyuan/layouts/home_layout.ron
```

首包路径必须位于 `fangyuan/` 根下；校验应拒绝父级目录、绝对路径、Windows drive、反斜杠和非 `fangyuan/` 根路径。新增 RON 样例是文本资源，按普通 Git 文本处理。

这和“primitive 不是玩法 Entity”的原则一致：

```text
SceneLayoutInstance
-> 引用 Prefab
-> 编译为 HomeObjectEntity / SceneObjectEntity
-> 内部持有 FangyuanPrimitiveSet
```

### Prefab 的边界

Prefab 不应变成不可控的万能脚本。

推荐 prefab 只描述：

- primitive 组合。
- 默认 bounds。
- 默认 pivot。
- 默认 material profile。
- 可选语义挂点。
- 默认预算。
- 可继承和可编辑标签。

不应在 prefab 中描述：

- 战斗强度。
- 资源产出。
- 任意脚本。
- 任意 shader。
- 服务端判定逻辑。
- 外部资源引用。
- 嵌套 prefab。
- rotation、quaternion、euler、angular_velocity、rotate、spin 等旋转字段。
- 绕过预算的隐藏 primitive。

当前第四阶段的 Scene Layout 也保持窄边界：只描述 prefab id、position、scale 和少量元数据，不支持 rotation、material_override、嵌套 layout 或把 layout 当作另一个 layout 的输入。

技能、装备和家园都可以使用 prefab 思路，但边界不同：

- 家园 prefab 主要复用结构和装饰。
- 装备 prefab 需要提供 grip、tip、core、guard、aura 等挂点。
- 技能 prefab 更接近 visual recipe 片段，必须受技能模板和规则层约束。
- 天道自演 prefab 需要生命周期、因果值和回收策略。

### 空间分块：Chunk 不是体素网格，而是加载单元

即使引入 prefab，大世界、宗门工程和天道自演内容仍然不能放进单个地图文件。

这里可以借用 chunk 思路，但它不是 Minecraft 式体素 chunk meshing，而是方圆内容的空间加载单元。

推荐：

- 按 X/Z 平面划分 `32 x 32`、`64 x 64` 或更大尺寸的逻辑 chunk。
- 一个 chunk 对应一个小型布局文件或二进制包。
- chunk 内记录 prefab instance、天道生成物引用、静态装饰和区域元数据。
- 玩家移动时异步加载 AOI 范围内 chunk。
- 玩家远离时卸载或降级 chunk。

示例目录：

```text
project/assets/fangyuan/worlds/main_world/
  palettes/
    common_prefabs.ron
    fire_region_prefabs.ron
  chunks/
    chunk_0_0.ron
    chunk_0_1.ron
    chunk_1_0.ron
```

后续发布期可对应为：

```text
project/assets/fangyuan_baked/main_world/
  palettes/
    common_prefabs.bin
    fire_region_prefabs.bin
  chunks/
    chunk_0_0.bin
    chunk_0_1.bin
    chunk_1_0.bin
```

chunk 尺寸不应只按几何大小决定，还要考虑：

- 同屏 primitive 数量。
- prefab instance 数量。
- 天道自演生成物数量。
- 交互对象数量。
- 蓝图依赖数量。
- 移动端内存峰值。
- 网络下载粒度。

### 图集与材质目录是独立资源依赖

当前开发期方圆材质资源拆成：

```text
fangyuan/atlases/base/surface_color.png
fangyuan/atlases/base/surface_normal.png
fangyuan/atlases/base/surface_atlas.json
fangyuan/atlases/base/surface_material_presets.json
fangyuan/atlases/noise/procedural_noise.png
fangyuan/atlases/noise/noise_atlas.json
```

PNG 是 Git LFS 二进制资源，JSON 是普通 Git 文本。运行时接入后，blueprint、prefab、chunk 或 material binding 只引用稳定 ID，不直接引用图集 UV 或任意文件路径。

图集图片、语义目录和材质预设构成同一个依赖闭包。任何一个文件变更都应触发版本/hash 校验和相关缓存失效；发布期应把解析后的 catalog 编译进受控 bake artifact，而不是让每个 primitive 重复解析 JSON。

### 开发期用 RON，发布期用二进制

RON、JSON、TOML 这类文本格式适合开发期：

- 人类可读。
- 便于 diff。
- 便于手工修正。
- 便于 AI 生成和审查。
- 便于热重载。

但上线运行期不应依赖大量文本解析。运行期更适合使用二进制格式，例如 `bincode` 或 `postcard`。

推荐流程：

```text
开发期：
  .ron 蓝图 / prefab / chunk
  -> 热重载
  -> 人工和 AI 审查

打包期：
  bake 工具读取 .ron
  -> 审核
  -> 版本升级
  -> 编译为紧凑结构
  -> 序列化为 .bin
  -> 可选压缩和加密

运行期：
  加载 .bin
  -> 快速反序列化
  -> 编译或直接转 runtime primitive set
  -> 进入实例池或渲染适配层
```

二进制发布格式的收益：

- 去掉字段名、括号、空格和注释。
- `f32`、`u16`、`u32` 等数值用固定宽度保存。
- 反序列化速度远快于文本解析。
- 更容易做压缩、加密和 CDN 分发。
- 更适合移动端控制加载时间和内存峰值。

文本格式和二进制格式必须共用同一套 Rust 数据结构或清晰的中间结构，避免开发期和运行期语义分叉。

### Bake 工具

后续应增加专门的 bake 工具，而不是让游戏运行期承担所有转换成本。

工具职责：

- 扫描 `project/assets/fangyuan/` 下的 RON 源文件。
- 解析 prefab、scene layout 和 chunk。
- 执行和游戏一致的 validator。
- 展开 prefab 引用并计算预算。
- 检查循环引用、缺失 prefab、越界 instance、非法颜色和非法材质。
- 生成 hash、版本号和依赖表。
- 输出 `.fyb` 或其他发布格式。
- 输出 bake report，记录 primitive 数、prefab 数、chunk 数、预算和警告。

示例命令可以后续设计为：

```powershell
cargo run --bin fangyuan_bake -- --input project/assets/fangyuan --output project/assets/fangyuan_baked
```

或者放入仓库脚本：

```powershell
.\scripts\bake-fangyuan-assets.ps1
```

### 运行时加载策略

运行时加载不应一次性读取全世界数据。

推荐：

- 启动时只加载基础 palette、当前场景入口和必要 UI 资源。
- 进入场景后按 AOI 异步加载周围 chunk。
- chunk 加载完成后再编译为 runtime primitive set。
- 缺失或未完成加载的 chunk 使用占位、远景代理或空表现。
- 玩家移动时预加载前方 chunk，卸载远离 chunk。
- 移动端限制同时驻留 chunk 数量。
- 热点区域可以优先加载规则层和交互核心，再补装饰层。

缓存策略：

- 常用 prefab palette 常驻。
- 大型家园和宗门工程按访问频率缓存。
- 天道自演临时生成物按生命周期缓存。
- 纪元档案类内容可延迟加载。

### 与蓝图继承和更新的关系

家园、装备和技能蓝图需要跨纪元继承。二进制发布格式不能破坏这一点。

建议：

- 玩家资产保存为逻辑蓝图或服务端记录，不只保存客户端 bake 后的二进制。
- bake 产物是运行期加速格式，不是唯一权威数据。
- 每个蓝图、prefab 和 chunk 都带 version 和 hash。
- 旧版本蓝图进入新纪元时先升级和重新审核，再生成新 runtime 数据。
- 线上热更新可以下发新的 `.fyb` 或后续正式二进制包，但必须保留版本兼容策略。

权威关系：

```text
服务端审核蓝图 / 设计源 RON
-> bake 产物
-> 客户端运行期缓存
```

不要反过来把客户端缓存当权威源。

当前第 12 至第 14 阶段已落地的资源和加载边界：

- Chunk 数据模型已作为方圆内容的空间加载单位，记录 prefab instance、天道引用、静态装饰、region metadata、bounds 和预算摘要；chunk 仍引用 prefab、blueprint 或 bake 占位，不复制大体量 primitive 数据。
- 本地 chunk runtime 支持 load、unload、reload、附近位置选择、失败 fallback、场景退出清理和 HUD/debug 摘要；这属于 `framework/fangyuan` 内部加载模型，不代表 `framework/scene` 已实现通用大世界 streaming。
- LOD 已固定为 L0 到 L4：full、reduced、silhouette、marker、hidden rule-only；对象默认映射覆盖 static object、home decoration、equipment、NPC、skill VFX 和 tiandao object。
- AOI selector 输出 load、keep、unload、marker chunk 集合和 object LOD decision；当前是本地选择与测试模型，不等同于服务端同步范围实现。
- 热点降级按 active skill、dynamic primitive、transparent count、emissive total、trail count 和 chunk load pressure 评估，并用天道灵压解释原因；降级顺序优先装饰、透明、发光、拖尾、残留和远处个性层，规则层最后压缩。
- Bake 已提供 `fangyuan_bake` cargo bin 和 `.\scripts\run-fangyuan-bake-dry-run.ps1`，开发期 RON 经共享 validator、版本升级、hash、依赖表和 audit 逻辑生成 `FYBAKE` header + typed payload 的 `.fyb` artifact。
- Runtime artifact loader 按 manifest、artifact kind、schema version、source/content hash、payload version 和依赖读取 `.fyb`；debug loader 可以 fallback 到 RON，release loader 默认不允许 RON fallback。
- Identity、cache 和 fallback 已覆盖 blueprint、prefab、chunk、material profile、skill visual 和 bake artifact；缓存 manifest 记录 version、hash、size、last_used、dependency、source kind，并通过 LRU/use_count 淘汰。
- Streaming update manifest 支持 chunk、prefab、blueprint、material profile 和 skill visual 的部分更新，安装前校验 hash、version、依赖、预算摘要、签名占位和权限占位，并记录 rollback key。
- 纪元继承输入覆盖旧世界 blueprint refs、玩家家园、装备、技能 visual 和天道固化档案；新纪元加载旧蓝图时重新执行版本升级、审核、预算校准和 kept/degraded/rejected 建议。
- 权威边界已固定：客户端缓存只提供 bytes 和性能优化，不能作为审核、预算、权限或资产归属的权威结果；服务端或 authority manifest 可以覆盖本地 stale cache，并输出审计日志。
- 本 清单 只完成客户端本地模型、工具链、文档和测试边界，不包含完整服务器集群、商业 CDN、运营后台、账号资产交易、最终云压测平台或真实签名加密体系。
