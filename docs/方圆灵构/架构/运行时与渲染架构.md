# 方圆灵构运行时与渲染架构

## 文档定位

本文记录方圆灵构体系下的对象模型、运行时表现、渲染、LOD、同步、审核安全和调试工具架构。资源构建与加载、阶段记录已经拆分为独立文档。

本文不是某个单点功能的实现说明，而是用于约束后续家园、装备、技能、NPC、天道自演、场景道具、宗门工程、多人热点和纪元长期内容的对象资源与渲染方向。

本文基于这些前提：

- 当前项目使用 Rust stable 和 Bevy `0.18.1`。
- 当前世界观采用赛博修仙和方圆二相。
- 游戏内可生成、可继承、可审核的视觉内容，应尽量由正方体和球体组合而成。
- 已归档的家园原型通过本地 RON 蓝图生成静态方块和球体预览。
- 当前下一阶段最小闭环改为方圆玩家外观 Demo：通过本地 RON 定义一个玩家 Entity 内部的 `FangyuanPrimitiveSet`，默认只包含一个 cube 身体和一个 sphere 头部。
- 从初始设计开始，游戏 Entity 的粒度就是角色、技能实例、家园物件、装备物件、天道生成物等逻辑对象；方圆 primitive 是这些逻辑对象内部的渲染数据，不是玩法层 Entity。
- 方圆系统的运行时变化只支持移动、scale 缩放、primitive 生成和 primitive 消失，不把旋转作为对象、primitive、动画或蓝图能力。
- 后续长期功能需要覆盖家园、装备、技能、NPC、场景装饰、天道自演和多人热点场景。
- 长期目标是符合世界观并支撑持续扩展，而不是只让当前 demo 能跑。

## 核心结论

方圆灵构不适合走 Minecraft 式 Chunk Meshing 作为长期主路线。

Minecraft 式 Chunk Meshing 适合大量规则网格方块构成的连续地形。当前项目的核心限制不同：

- 基础可见元素只有方相和圆相。
- primitive 可以有不同位置和大小。
- 不存在旋转。
- 颜色、材质、发光和透明需要多样化。
- 家园、装备、技能、NPC 和天道自演都需要复用同一种视觉语法。
- 内容需要由 AI 或系统生成，并经过审核、预算和降级。

因此长期路线应是：

```text
方圆 primitive 数据化
-> 统一蓝图审核和预算
-> 统一 runtime primitive 表达
-> 静态实例池和动态 VFX 实例池
-> cube / sphere 两条渲染批
-> 材质参数实例化
-> LOD、AOI 和天道灵压降级
```

简化口径：

```text
世界观看起来是万物方圆
技术底层是少量 mesh + 海量实例数据
```

## 总体原则

### primitive 从一开始就不是玩法 Entity

本路线明确采用：

```text
Entity = 角色、技能、家园物件、装备物件、天道生成物、场景交互物
Primitive = 逻辑 Entity 内部的方圆渲染数据
```

也就是说，正式架构从第一阶段开始就不把一个方块或一个球体设计成玩法 Entity。

推荐初始结构：

```text
CharacterEntity
  CharacterState
  EquipmentVisualSet

SkillInstanceEntity
  SkillRuleState
  VfxRuntime

HomeObjectEntity
  HomeObjectState
  FangyuanPrimitiveSet

TiandaoManifestationEntity
  ManifestationLifecycle
  FangyuanPrimitiveSet
```

渲染适配层可以在内部生成批量 mesh、实例数据或渲染 draw item，但这些都不应暴露为玩法层 primitive Entity。

危险形态：

```text
一个方块 = 一个玩法 Entity
一个球体 = 一个玩法 Entity
一个技能里 100 个 primitive = 100 个动态玩法 Entity
1000 个玩家同时释放技能 = 100000 个动态玩法 Entity
```

这个结构会让 CPU 端 ECS 遍历、Transform 更新、可见性计算、Extract 阶段和渲染世界同步成为瓶颈。

目标结构应是：

```text
一个角色 = 一个角色逻辑 Entity
一个家园物件 = 一个家园物件逻辑 Entity
一个技能表现 = 一个 VFX 运行时实例
一个天道生成物 = 一个生命周期对象
这些对象内部持有 primitive 数组
渲染层按 cube / sphere 批量提交实例数据
```

### 方圆变换只包含移动、缩放和生命周期

方圆系统不把旋转作为基础能力。蓝图、runtime primitive、动画 recipe 和渲染适配层都不应暴露这些字段：

```text
rotation
quaternion
euler
angular_velocity
rotating animation
```

允许的变化只有：

- 逻辑对象整体移动。
- primitive 的局部位置变化。
- 逻辑对象或 primitive 的 scale 缩放。
- primitive 按生命周期生成、显化、淡出和消失。
- color、alpha、emissive 等材质参数变化。

如果 Bevy `Transform` 必须携带 rotation 字段，方圆系统也只把它作为引擎内部默认值处理，不把它纳入方圆数据模型和可配置能力。

角色朝向、技能方向和表现偏向后续应通过语义方向、局部 primitive 分布、前向 marker、生成节奏和颜色变化表达，而不是通过旋转 cube、sphere 或角色根对象表达。

### mesh 极少，实例极多

全局基础 mesh 应尽量少：

- unit cube。
- low sphere。
- medium sphere。
- high sphere。

cube 不需要多套精度。sphere 需要按平台和距离切换精度：

- 近处高表现：中高精度球。
- 普通场景：中精度球。
- 远处、移动端、热点区域：低精度球。
- 极端热点：可退化为 billboard、点光感或规则轮廓。

不建议早期引入太多基础形状。圆柱、圆环、文字、自由 mesh、粒子系统和玩家自定义 shader 都会增加审核和渲染复杂度，削弱方圆二相的统一风格。

### 材质合一优先于材质自由

颜色和材质多样化不能通过创建大量 `StandardMaterial` 来解决。

如果每种颜色、每种发光、每种粗糙度都创建一个独立材质，渲染批次会被切碎。长期应尽量让实例共享同一套方圆材质，通过实例数据表达差异。

推荐方向：

```text
同一个 cube mesh
同一个 sphere mesh
同一个或少量 FangyuanMaterial
每个实例携带 color / emissive / alpha / material_profile_id / texture_index
```

这样可以让视觉上多彩、多材质，底层仍保持高批处理效率。

### 颜色先行，质感后置

渲染路线应分阶段增加表现力：

1. 第一阶段只支持颜色。
2. 第二阶段支持发光强度和 alpha。
3. 第三阶段支持材质 profile，例如玉石、金属、灵木、石质、火核、水膜。
4. 第四阶段再考虑 texture atlas 或 texture array。
5. 最后才考虑更复杂的屏幕空间效果、溶解、噪声和特殊边缘光。

不要一开始就把材质系统设计成完整 PBR 资产管线。当前世界观的优势是抽象几何和程序表现，不是传统美术资产堆叠。

### 透明和动态光是预算资源

大量透明排序、半透明叠加、动态阴影和动态点光源会比 primitive 数量更早击穿性能。

默认规则：

- 静态家园和场景道具默认不透明。
- 透明只用于护盾、水膜、残影、淡出和特殊预警。
- 动态光源数量必须严格限制。
- 发光优先使用 emissive + bloom，而不是大量真实灯光。
- 热点区域优先降级透明和发光，再降低普通不透明 primitive。

世界观包装：

```text
区域灵压升高
-> 非关键灵光被天道压制
-> 装饰层显化变弱
-> 远处灵构只保留规则轮廓
```

### 服务端只同步语义事件

服务端不应模拟和同步每个视觉 primitive。

服务端关心：

```text
caster_id
skill_template_id
visual_blueprint_id
start_tick
position
direction 或 target
seed
```

客户端根据这些语义事件、本地缓存的视觉蓝图和确定性 seed 还原表现。

禁止长期依赖：

```text
同步每个 primitive 的每帧 position
同步每个 primitive 的每帧 scale
同步每个 primitive 的每帧 alpha
同步视觉播放器内部状态
```

### 规则层和个性层必须分离

技能、陷阱、护盾、范围效果等战斗表现必须分层。

规则层：

- 真实作用范围。
- 投射物方向和速度。
- 护盾边界。
- 陷阱触发区域。
- 危险提示。
- 友敌可读性。

个性层：

- 颜色倾向。
- 方相和圆相比例。
- 拖尾形态。
- 显化节奏。
- 命中扩散。
- 残留余辉。
- 装饰 primitive 分布。

玩家蓝图主要影响个性层。规则层由系统模板控制，不能被玩家隐藏、缩小、伪装或扩大。

## 推荐架构

### 总体数据流

推荐长期数据流：

```text
玩家输入 / 天道触发 / 系统模板
-> AI 或规则生成蓝图
-> 蓝图审核
-> 预算计算
-> 蓝图编译
-> runtime primitive set
-> 绑定到角色 / 技能 / 家园物件 / 天道生成物等逻辑 Entity
-> 静态实例池 / 动态 VFX 实例池
-> 渲染提交
-> LOD / 热点降级 / 调试统计
```

其中 AI 只能生成表现蓝图，不能生成最终强度。强度来自系统模板、角色权限、四属性、职业、称号、世界层级和服务端规则。

这些名字不要求一次性落地，但应作为长期职责边界参考。

### 方圆 primitive 统一结构

后续不要让家园、装备、技能、NPC 各自定义一套几何结构。

建议收敛到统一的运行时表达：

```text
FangyuanPrimitive:
  kind: cube | sphere
  local_position: Vec3
  scale: Vec3
  color: LinearRgba
  role: PrimitiveRole
  alpha: f32
  emissive: f32
  material_profile_id: Option<MaterialProfileId>
  lifecycle: PrimitiveLifecycle
```

`role` 用于表达语义：

- structure：结构层。
- core：灵核。
- boundary：规则边界。
- warning：预警范围。
- trail：拖尾。
- impact：命中反馈。
- decoration：装饰。
- socket：装备挂点辅助。
- archive：纪元档案展示。

这个 role 对渲染、审核、LOD 和战斗可读性都很重要。

例如热点降级时可以优先丢弃：

```text
decoration -> trail -> impact -> 非关键 core
```

但应保留：

```text
warning -> boundary -> 规则 core
```

### 蓝图和 runtime 分离

蓝图适合存储、审核、继承和网络引用。

runtime primitive 适合渲染、LOD 和运行时播放。

不要把蓝图结构直接当运行时结构长期使用。蓝图需要可读、稳定、可版本化；runtime 需要紧凑、连续、适合批量处理。

推荐关系：

```text
BlueprintPrimitive
-> 审核
-> 编译
-> RuntimePrimitive
-> InstanceData
```

蓝图字段可以保留描述性信息：

- name。
- description。
- author。
- version。
- bounds。
- tags。
- budget。
- primitives。

runtime 字段应尽量紧凑：

- mesh_kind。
- local_position。
- scale。
- color。
- role。
- alpha。
- emissive。
- material_profile_id。
- lifecycle 或 packed flags。

当前第二阶段已落地的代码边界：

- `project/src/framework/fangyuan/blueprint.rs`：读取和校验 RON v1 蓝图，将 blueprint primitive 编译为 runtime primitive。
- `project/src/framework/fangyuan/primitive.rs`：定义统一 runtime primitive，字段为 `kind`、`local_position`、`scale`、`color`、`role`、`alpha`、`emissive`、`material_profile_id`、`lifecycle`，不包含 rotation、quaternion、euler、angular_velocity、rotate 或 spin。
- `project/src/framework/fangyuan/object.rs`：逻辑对象持有 `FangyuanPrimitiveSet` 和对象状态，primitive 仍只是对象内部数据。
- `project/src/framework/fangyuan/stats.rs`：统计基于 `FangyuanPrimitiveSet` 计算 cube、sphere、role、颜色、透明、发光和材质 profile 数量，不读取 render-only 子实体。
- `project/src/game/features/fangyuan_player_preview/`：玩家预览页面把玩家对象的 primitive set 派生为 render-only 子实体，仅用于显示 cube 身体和 sphere 头部。

第二阶段没有实现 Prefab、Bake、mesh merge、GPU Instancing、VFX、LOD 或 AOI；这些仍保留在后续阶段设计中。

当前第三阶段已落地的统一模型接入边界：

- 玩家外观、家园预览和静态对象蓝图共用 RON v1 primitive 字段：`kind`、`position`、`size`、`color`，以及可选的 `role`、`alpha`、`emissive`、`material_profile_id`、`lifecycle`。
- `FangyuanBlueprint` 是当前蓝图读取入口，编译后统一进入 `FangyuanPrimitiveSet`；家园预览使用 `compile_skipping_invalid_primitives()`，非法 primitive 不进入 runtime set，而是通过 `FangyuanBlueprintCompileReport` 记录跳过数量和原因。
- `project/src/game/scenes/fangyuan_home.rs` 生成家园逻辑根 `FangyuanHomeObject`，根实体持有 `FangyuanPrimitiveSet` 和 `FangyuanObjectState`；cube / sphere 可见实体仍只是从 primitive set 派生的 render-only 子实体。
- 家园预览复用 `project/src/framework/fangyuan/render_assets.rs` 中的 `FangyuanRenderAssetCache`，继续共享 unit cube、unit sphere 和按颜色缓存的标准材质，不新增独立家园材质或静态批处理路径。
- Reload、Clear 和 Exit 生命周期收敛到逻辑根和 render-only 子实体清理；HUD 只读取 `FangyuanPrimitiveSetStats` 和 compile report，不从渲染子实体反推业务状态。
- 默认 `project/assets/fangyuan/home_preview.ron` 编译结果为 505 authored primitives、493 generated、12 skipped below-ground；HUD 显示 `primitive 493/1000 loaded`、`cube 127 sphere 366 skipped 12`、`mat 12`、`path fangyuan/home_preview.ron`。

第三阶段仍没有实现 Prefab、Scene Layout 拆分、Chunk、Bake、静态 CPU mesh merge、GPU Instancing、LOD、AOI、联网同步、正式家园编辑器、蓝图持久化、装备挂点正式接入或技能规则层；这些仍保留在后续阶段设计中。

当前第四阶段已落地的开发期 Prefab、Palette 和 Scene Layout 边界：

- 新增开发期 `FangyuanPrefabPalette` / `FangyuanPrefabDefinition` RON v1 源格式，用于描述可复用的 primitive 组合；默认首包路径为 `project/assets/fangyuan/palettes/home_prefabs.ron`，代码常量为 `FANGYUAN_HOME_PREFAB_PALETTE_PATH`。
- 新增开发期 `FangyuanSceneLayout` RON v1 源格式，只记录 prefab id、position、scale 和少量实例元数据；默认首包路径为 `project/assets/fangyuan/layouts/home_layout.ron`，代码常量为 `FANGYUAN_HOME_SCENE_LAYOUT_PATH`。
- layout + palette 通过 `compile_with_palette()` 展开为 `FangyuanPrimitiveSet`，仍使用统一 primitive validator；展开后的 render-only 子实体不成为玩法 Entity。
- 预算和 report 已区分 palette 数、prefab 数、used prefab 数、instance 数、generated primitive 数、skipped 数、material 数，以及 top-level、layout、palette 校验状态。
- expanded primitive 硬限制仍为 `1000`；缺失 prefab、非法 instance、预算超限和顶层非法数据返回结构化 error，单个展开后非法 primitive 可跳过并记录 warning。
- error / warning 可携带 `code`、`field_path`、`reason`，warning 还可定位 instance id 或 index、prefab id 和 prefab primitive index。
- 家园预览默认读取 layout/palette 展开内容；`project/assets/fangyuan/home_preview.ron` 和 `project/assets/fangyuan/avatars/minimal_player.ron` 仍保留兼容样例，但运行时家园默认不 fallback 到 simple blueprint。
- 当前默认手动验收 HUD 为 `layout loaded gen 138/1000 skip 0`、`pal 1 pf 5 used 5 inst 40 mat 15`，Reload 会重新读取 layout/palette，Clear 只清空展开内容并保留基础空间，Exit 清理当前 session 内容。
- 第四阶段仍不包含 Chunk、Bake、静态 CPU mesh merge、GPU Instancing、LOD、AOI、联网同步、正式家园编辑器、蓝图持久化、装备挂点正式接入或技能规则层。

当前第五阶段已落地的蓝图审核和预算系统边界：

- 新增统一审核入口 `project/src/framework/fangyuan/audit.rs`，提供 `FangyuanAuditReport`、`FangyuanAuditSummary`、`FangyuanAuditStatus`、`FangyuanAuditSeverity`、`FangyuanAuditFinding`、`FangyuanAuditSuggestion`、预算 profile / stats 和 debug formatter。
- `FangyuanAuditReport` 记录 `source_kind`、`source_path`、`status`、`summary`、`findings` 和 `suggestions`；`status` 当前只有 `Passed`、`PassedWithWarnings`、`Failed` 三种。
- `FangyuanAuditFinding` 记录 `severity`、`code`、`field_path`、`reason`、`source_kind`、`source_path`，并可定位 `primitive_index`、`prefab_id`、`instance_id`、`instance_index`、`prefab_primitive_index`。
- `FangyuanAuditSuggestion` 记录降级动作、字段路径、原因和预估效果；当前动作为 `ReducePrimitives`、`ShrinkBounds`、`RemoveAlpha`、`LowerEmissive`、`ReplaceMaterialProfile`、`ReduceWarningRole`。
- 默认 `FangyuanAuditBudgetProfile` 保持 `1000` primitive 硬限制，并新增 `800` recommended primitive、`64 x 64 x 64` bounds、单 primitive 最大 extent `16`、单 primitive volume `4096`、总 volume `32768`、透明/发光/material profile 推荐和硬限制等预算入口。
- 预算统计覆盖 authored、generated、skipped、expanded、runtime primitive、cube、sphere、颜色、material profile、alpha、emissive、lifecycle、role distribution、bounds、最大 primitive 尺寸和体积。
- `project/src/framework/fangyuan/blueprint.rs`、`prefab.rs`、`layout.rs` 已接入审核；simple blueprint、Prefab / Palette、Scene Layout 和展开后的 runtime primitive set 都能生成统一 report。
- 家园预览 `project/src/game/scenes/fangyuan_home.rs` 在读取 layout/palette 后先执行 `audit_with_default_budget()`；审核失败不生成误导性成功内容，审核 warning 可继续生成并记录主 warning code。

## 渲染管线路线

### 当前最小闭环：方圆玩家外观 Demo

当前下一阶段优先验证角色对象边界，而不是继续扩大静态家园内容。

目标结构：

```text
PlayerEntity
  PlayerIdentity / PlayerState
  FangyuanAvatar
  FangyuanPrimitiveSet
  Transform 或等价 position 组件
```

默认 RON 只定义一个最小玩家外观：

```text
cube 身体
sphere 头部
```

关键约束：

- `PlayerEntity` 是玩法 Entity。
- cube 和 sphere 是 `FangyuanPrimitiveSet` 内部数据，不是玩法 Entity。
- 玩家移动只改变玩家根对象的位置。
- primitive 局部变化只允许 local position、scale、color、alpha、emissive、alive/lifetime。
- 蓝图和 runtime 数据都不包含 rotation。

第一版渲染适配可以为了接入 Bevy 标准渲染而生成 render-only 子实体，例如 cube body 和 sphere head。它们只允许承载 mesh、material、visibility 和 transform 等显示组件，不挂载输入、移动、血量、技能、authority 或业务状态。

这个选择只是标准渲染适配的实现细节，不改变“primitive 不是玩法 Entity”的架构约束。后续可以把 render-only 子实体替换为批量 mesh、静态实例池或动态 instance buffer，而不改变玩家对象和 `FangyuanPrimitiveSet` 的数据边界。

### 第一阶段：逻辑 Entity + 标准渲染适配

第一阶段可以继续使用 Bevy 标准 mesh、材质和渲染资源，但 Entity 粒度仍然必须是逻辑对象，而不是 primitive。

推荐第一阶段结构：

- `PlayerEntity`、`HomeObjectEntity` 或 `FangyuanObjectEntity` 表示角色、家园物件、装饰物、阵法节点或预览对象。
- `FangyuanPrimitiveSet` 保存该逻辑对象内部的 cube / sphere 数据。
- `Transform` 或等价 position 组件只表达逻辑对象整体位置；方圆模型不使用旋转。
- 渲染适配层根据 `FangyuanPrimitiveSet` 生成一个或少量 `Mesh` / render batch / 简化 instance 数据。
- `Mesh3d`、`MeshMaterial3d<StandardMaterial>` 或项目当前材质组件只挂在批量渲染对象上，不按 primitive 粒度挂载。

第一阶段渲染适配层可以采用两种保守方式：

- 标准渲染子实体：为每个 primitive 生成 render-only 子实体，快速验证 RON、对象层和可视化链路。该方式只适合小规模对象和调试阶段，不能把子实体接入玩法逻辑。
- 批量 mesh：把一个逻辑对象内的 primitive 烘成一个或少量 mesh。颜色可以优先用顶点色；如果标准材质路径限制较多，则临时按颜色或材质分组。
- 简化实例数据：如果实现成本可控，直接让逻辑对象生成 cube / sphere instance 数据，为后续实例池铺路。

这个阶段重点不是极限性能，而是验证：

- RON 蓝图能稳定读取。
- cube / sphere 显示正确。
- 坐标和尺寸符合世界观规则。
- 颜色和材质复用可行。
- 第一批玩家外观、家园物件或场景对象有可读性。

短期优化：

- unit cube 和 unit sphere 作为基础模板或共享 mesh 源数据。
- 颜色相同的 primitive 复用材质。
- 单个 primitive 不拥有 ECS Transform、Visibility、Material 或逐帧逻辑。
- 所有 primitive 数据归属到对应逻辑 Entity 的 `FangyuanPrimitiveSet`。

### 第二阶段：静态 CPU 合并和场景分组

在静态地图、洞府、宗门工程和场景装饰扩大时，优先处理静态内容的 draw call，而不是直接为所有内容引入 GPU instancing。

推荐过渡路线：

```text
静态方圆内容
-> 按 chunk / 场景区域 / 逻辑对象类型分组
-> CPU 合并为少量 mesh
-> 使用 Bevy 标准材质和渲染路径
```

适合内容：

- 地面、墙体、台阶和固定阵基。
- 静态洞府结构。
- 静态宗门工程。
- 区域装饰和碑林。
- 低频变化的天道自演固化物。

这种方式的优点是实现成本低、调试直观、能继续使用 Bevy 标准渲染路径。缺点是当静态 primitive 数量达到几万或十几万，或地图需要频繁局部热更新时，CPU 合并和 mesh 重建成本会变高。

### 第三阶段：静态实例池

当家园、宗门工程、天道装饰开始增长后，需要把第一阶段的批量 mesh 或标准渲染适配替换为静态实例池。

目标：

```text
大量静态 primitive
-> 按 cube / sphere 分组
-> 写入静态 instance buffer
-> 一批或少量 draw call 渲染
```

静态内容包括：

- 家园主体结构。
- 宗门工程。
- 方块碑林。
- 浮空灯。
- 区域装饰。
- 纪元档案展示物。
- 低频变化的天道自演装饰。

静态实例池特点：

- 构建后很少变化。
- 修改蓝图时重建局部或整组 instance 数据。
- primitive 不参与逐帧 ECS Transform 更新。
- 可按空间块、逻辑对象 root 或蓝图 id 管理。

静态实例池主要服务大规模静态内容和热更新后的快速重建。它不要求在最小玩家 Demo 阶段实现。

### 第四阶段：动态 primitive 和 VFX 实例池

技能、护盾、投射物、命中反馈和拖尾需要动态播放。

动态 primitive 同样不成为玩法 Entity。从第一版 VFX 开始就应使用 VFX 实例池：

```text
一个技能释放事件
-> 一个 VFX runtime instance
-> 内部持有 recipe、start_tick、seed、caster、target
-> 每帧批量计算当前可见 primitive
-> 写入动态 instance buffer
```

动态实例池特点：

- 生命周期短。
- 数量波动大。
- 需要按距离和热点快速降级。
- 需要支持确定性回放。
- 需要和 authority tick 对齐。

### 第四阶段：统一 FangyuanMaterial

当颜色、发光、透明和材质 profile 增多后，需要统一方圆材质。

推荐实例数据：

```text
InstanceData:
  position: vec3
  scale: vec3
  color: vec4
  emissive: f32
  alpha: f32
  material_profile_id: u32
  flags: u32
```

如果后续确认所有 primitive 永远无旋转，可以不传完整 transform matrix，而是传 position + scale。这样实例数据更小，shader 中顶点位置也更简单：

```text
world_position = instance_position + local_vertex_position * instance_scale
```

材质 profile 可以表达：

- 普通实体。
- 金属。
- 石质。
- 玉石。
- 灵木。
- 火核。
- 水膜。
- 风灵。
- 天道碑。
- 纪元档案。

早期 profile 可以只是参数表，不必马上接 texture array。

### 第五阶段：texture atlas 或 texture array

当单纯颜色和 profile 参数不足以表达材质时，再考虑纹理。

候选：

- texture atlas：实现较直接，但 UV 边界和采样出血需要处理。
- texture array：更适合按材质层采样，但管线和资源管理更复杂。

在方圆灵构中，纹理不应成为主要识别来源。纹理适合做轻微质感：

- 石纹。
- 金属噪声。
- 火核脉动。
- 水膜细波。
- 风灵流线。
- 纪元档案符纹。

不建议允许玩家上传任意纹理作为早期能力。任意纹理会带来审核、版权、包体、缓存和性能问题。

## 各功能渲染路线

### 方圆玩家和角色外观

当前下一阶段优先用最小玩家外观 Demo 验证对象层边界。

短期路线：

- 读取 `project/assets/fangyuan/avatars/minimal_player.ron`。
- 生成一个 `PlayerEntity`。
- 玩家 Entity 持有 `FangyuanAvatar` 和 `FangyuanPrimitiveSet`。
- 默认 primitive 只有一个 cube 身体和一个 sphere 头部。
- primitive 坐标作为玩家根 Entity 下的 local position。
- 渲染适配层可以生成 render-only 子实体，但这些子实体不参与玩法、输入、authority、移动状态或技能状态。

中期路线：

- 增加更多 role，例如 body、head、core、marker、decoration。
- 用 scale、local position、颜色和生成/消失表达动作变化。
- 为角色外观接入统一 validator 和预算。
- 可按角色距离和重要性减少装饰 primitive。

长期路线：

- 玩家角色、NPC、装备挂点和技能表现共享同一套 runtime primitive。
- 大量角色同屏时，动态 primitive 进入动态 instance buffer 或等价批量路径。
- 角色外观蓝图可缓存、继承和重新审核。

渲染重点：

- 玩家是玩法 Entity。
- primitive 是玩家内部的渲染数据。
- 方圆角色不使用旋转表达朝向和动作。
- 最小闭环不做 mesh 合并、GPU instancing 或复杂 VFX。

### 方圆洞府和家园

家园适合作为玩家外观最小闭环之后的静态内容验证场景。

短期路线：

- 读取本地 RON 蓝图。
- 生成一个或少量 `HomeObjectEntity` / `FangyuanObjectEntity`。
- 蓝图 primitive 存入逻辑 Entity 的 `FangyuanPrimitiveSet`。
- 渲染适配层生成批量 mesh 或简化 instance 数据。
- 复用 mesh 和颜色材质。
- 控制 primitive 数量在 1000 以内。
- 保证坐标、尺寸、颜色合法。

中期路线：

- 家园蓝图进入统一 validator。
- 家园内容编译为 runtime primitive。
- 静态 primitive 进入静态实例池。
- 家园逻辑 Entity 只保留状态、交互、选择和 primitive set handle。
- 编辑或重新生成后局部重建实例数据。

长期路线：

- 家园支持跨纪元继承和重新落位。
- 大型家园按空间块或楼层拆分实例池。
- 远处家园显示低精度代理。
- 访问他人家园时按权限和距离流式加载。
- 家园访客、天道自演 NPC 和互动装饰使用独立生命周期。

渲染重点：

- 主结构清楚。
- 方相承担承载和边界。
- 圆相承担炉心、灵核、阵眼和流动感。
- 不靠真实建筑模型堆细节，而靠方圆组合形成身份。

### 宗门工程和公共设施

宗门工程比个人家园更大，不能简单提高 primitive 上限。

推荐：

- 宗门工程按设施拆分：界碑、传送阵、法会场、公共须弥锚点、工坊、分舵。
- 每个设施有独立蓝图和预算。
- 同屏只加载附近设施完整表现。
- 远处显示轮廓或地标核心。
- 人群热点时优先保留可交互核心和导航识别。

宗门工程适合使用更稳定、更厚重的方相结构，圆相作为核心节点、能量连线和传送标记。

### 装备外观

装备是自由度中等的方圆灵构对象。

装备渲染需要解决两个问题：

1. 外观看起来可自定义。
2. 技能能稳定从装备上发出或附着。

推荐装备蓝图提供语义挂点：

- `grip`：握持点。
- `tip`：发射或指向点。
- `core`：圆相核心。
- `guard`：防护结构。
- `aura`：灵气附着区域。

装备本体仍由 cube / sphere 组合。挂点不是骨骼，而是从蓝图或编译结果中计算出的语义位置。

短期可以将装备作为角色附近的独立方圆结构显示。长期如果需要绑定角色动作，需要谨慎处理，因为当前基础规则不支持 primitive 旋转。

如果角色动画后续使用传统模型，装备方圆结构可以绑定到角色手部或背部 root，但装备内部 primitive 仍不旋转，只跟随装备 root 的整体位姿。这个方向需要后续单独评估，因为它会引入“装备 root 旋转”和“primitive 不旋转”的边界。

### 技能和程序 VFX

技能表现必须以模板为边界。

服务端识别技能模板：

- 投射物。
- 范围效果。
- 持续区域。
- 护盾。
- 治疗。
- 控制。
- 位移。
- 召唤物。
- 陷阱。

客户端视觉由 `SkillVisualBlueprint` 和程序动画 recipe 还原。

推荐技能表现拆成四层：

```text
规则层：真实范围、方向、命中区域
结构层：方块阵列、球形核心
能量层：小球、小方块、拖尾、闪烁、扩散、收束
残留层：命中后的淡出、碎散、余辉、地面短暂标记
```

基础动画能力：

- spawn。
- move。
- scale。
- fade。
- color_shift。
- emissive_pulse。
- trail。
- impact_expand。
- dissolve。
- attach_to_entity。

不作为基础能力：

- primitive 自由旋转。
- 骨骼动画。
- mesh deformation。
- 玩家上传 shader。
- 任意脚本。

无旋转限制下，斩击和扇形技能可以这样表达：

```text
不用旋转刀光
改用一串球体或方块沿弧线依次显化、膨胀、淡出
```

### NPC 和天道访客

方圆灵构世界中的 NPC 不必一开始走传统角色模型路线。

天道自演 NPC 可以先采用方圆抽象体：

- 方相表达身体、衣摆、护甲、身份结构。
- 圆相表达头部、灵核、眼目、法器核心。
- 发光和颜色表达四属性。
- 小幅移动、缩放、显隐和脉冲表达生命感。

这类 NPC 更适合纯表现层和弱互动层：

- 闲聊。
- 传闻。
- 纪元记录。
- 家园访客评论。
- 区域提示。

如果后续要引入高表现角色模型，应明确分层：

- 主角和关键角色可以使用传统角色渲染。
- 天道自演、大量访客、低成本 NPC 继续使用方圆抽象体。
- 大规模场景下优先保留方圆 NPC，因为它们更可审核、可降级、可批处理。

### 天道自演生成物

天道自演生成物必须从第一天就考虑生命周期和预算。

推荐状态：

- 灵感期：只有生成意图，不渲染。
- 显化期：蓝图审核通过后出现。
- 活跃期：玩家可查看、点赞、收藏、举报或轻互动。
- 衰退期：低因果值内容逐渐淡出或隐藏。
- 固化期：高因果值内容转为长期世界记忆。
- 归档期：保留记录，不一定继续渲染。

渲染层需要支持：

- 生成物显化。
- 发光脉冲。
- 因果值提升时增强表现。
- 衰退时淡出或降级。
- 固化后转入静态实例池。
- 举报或预算回收后清理。

天道自演内容不应默认永久存在。否则长期世界会被生成物堆满，渲染和内容管理都会失控。

### 世界事件和纪元异象

纪元更替、天门开启、火脉复苏、地脉稳固、风门大开、水泽归元等事件需要高识别度。

推荐做法：

- 大型异象由少数高语义 primitive 组成。
- 远处可见核心轮廓。
- 近处补充能量层和残留层。
- 事件边界和危险区域必须清楚。
- 大型异象不能使用无限粒子和无限透明叠加。

例如天门裂隙可以表达为：

- 方相阵基构成门框和界碑。
- 圆相核心沿门缝排列。
- 发光强度随纪元倒计时变化。
- 远处只显示门框轮廓和中心圆核。

### 须弥空间和背包表现

背包和须弥空间本质是 UI 与道具系统，但也可以有世界观渲染表达。

建议：

- 背包 UI 保持清晰、实用，不要过度装饰。
- 须弥空间打开时可以用方圆灵构做背景表现。
- 地属性容量可表现为厚重方相格架。
- 火属性可表现为炉心和转化圆核。
- 水属性可表现为柔和圆相保存层。
- 风属性可表现为远程调度节点和轻量悬浮方块。

这些表现不应影响道具操作效率。UI 可读性优先于视觉炫技。

### 灵名溯源和纪元档案

灵名溯源、因果名录和纪元档案主要是 UI 和信息展示，但也可以使用方圆视觉语言：

- 称号和纪元记录可显示为小型方圆徽记。
- 高关注角色可有天道记录标记。
- 同名风险提示必须清楚，不能只靠美术符号。
- 纪元档案可以在家园或宗门空间中显示为方相碑和圆相记忆核心。

渲染原则：

- 信息真实性优先。
- 装饰不能遮挡身份字段。
- 可交互资料卡不应过度动态化。

## LOD 和预算路线

### LOD 分层

推荐表现档位：

```text
L0 自身完整表现：100 到 300 primitives
L1 队友或目标重点表现：40 到 100 primitives
L2 普通附近表现：10 到 40 primitives
L3 远处表现：1 到 8 primitives
L4 极端热点表现：只显示规则轮廓或范围提示
```

家园和场景也应有类似档位：

```text
近处完整结构
中距离保留主体和核心
远处保留剪影、地标和发光核心
极远只保留地图标记或不渲染
```

### 预算类型

灵构额度应同时承担世界观预算和技术预算。

推荐预算项：

- primitive 数量。
- cube 数量。
- sphere 数量。
- 动态 primitive 数量。
- 透明 primitive 数量。
- 发光 primitive 数量。
- 发光强度总量。
- 生命周期长度。
- 同屏技能数量。
- 遮挡面积。
- 规则层可读性。
- 材质 profile 复杂度。
- 更新频率。
- 网络蓝图引用数量。

技术预算不应在 UI 中完全裸露为工程术语。可以包装为：

- 灵构额度。
- 天道算力。
- 显化稳定度。
- 灵压占用。
- 阵列负载。

但调试面板需要保留真实指标。

### 热点区域降级

当天道灵压升高时，渲染降级应按顺序执行：

1. 降低远处装饰层。
2. 降低透明和发光强度。
3. 降低技能拖尾和残留。
4. 降低非关键天道自演生成物表现。
5. 降低普通玩家装备外观细节。
6. 保留技能规则层、危险边界和交互核心。
7. 必要时隐藏非关键展示实体。

不能优先移除：

- 敌方技能真实范围。
- 重要交互提示。
- 传送门、出口、任务核心。
- 安全区边界。
- 同名身份和交易风险提示。

## 多人和网络同步

### AOI 是必须项

长期多人场景不能全量同步、全量渲染。

需要 AOI 和兴趣管理：

- 只同步附近玩家。
- 只同步相关技能事件。
- 远处玩家低频同步。
- 远处家园和宗门工程只同步代理信息。
- 天道自演生成物按区域和可见性加载。

客户端不应知道也不应渲染整个世界所有蓝图。

### 蓝图缓存和哈希

玩家自定义蓝图和天道生成蓝图需要缓存。

推荐：

- 服务端审核后生成 `visual_blueprint_id`。
- 蓝图内容带版本和 hash。
- 客户端本地缓存蓝图。
- 技能释放只同步蓝图 id。
- 客户端缺蓝图时先显示降级默认表现，再异步请求蓝图。

这样可以避免每次技能释放都传一大段视觉数据。

### authority 回放

当前项目已有 authority 帧同步回放输入的方向。方圆技能和 VFX 应尽量和 authority tick 对齐。

推荐同步字段：

```text
tick
caster_id
skill_template_id
visual_blueprint_id
position
direction 或 target
seed
```

客户端用 `tick` 和 `seed` 还原视觉生命周期。这样录制、回放、观战和多客户端一致性更容易控制。

## 审核和安全

### 蓝图审核

所有玩家生成和天道自演生成的内容都必须审核。

审核重点：

- 是否只使用 cube / sphere。
- 是否超出 primitive 数量。
- 是否超出总体积。
- 是否超出 bounds。
- 是否有地面以下主体结构。
- 是否有过多透明叠加。
- 是否有过强发光。
- 是否遮挡关键交互。
- 是否隐藏技能真实范围。
- 是否伪装成系统提示、排行榜身份或交易确认。
- 是否包含违规文本或现实图标。
- 是否超出角色、职业、四属性和世界层级的灵构额度。

### 审核失败不应只返回失败

更好的体验是返回替代方案：

- 缩小整体尺寸。
- 减少装饰层。
- 降低发光。
- 移除透明。
- 固定规则边界。
- 替换未解锁材质。
- 降级为合法模板表现。

世界观表达：

```text
天道算力不足，已为你推演稳定版本
```

### 玩家自定义 shader 不进入早期能力

不建议早期允许玩家上传 shader、脚本或任意材质程序。

原因：

- 安全风险高。
- 审核难度高。
- 性能不可控。
- 移动端兼容风险高。
- 会破坏统一方圆风格。

玩家自定义应先限制在：

- primitive 组合。
- 颜色。
- 发光强度。
- 材质 profile。
- 动画 recipe 参数。
- 装饰层密度。

## 调试和验收工具

长期必须建设调试工具，否则预算和降级会很难维护。

### 灵构试炼场

灵构试炼场不仅是玩法，也应是渲染验收工具。

试炼场需要展示：

- primitive 总数。
- cube / sphere 数量。
- 动态 primitive 数量。
- 透明数量。
- 发光预算。
- 材质 profile 数量。
- 当前 LOD 档位。
- 热点降级结果。
- 规则层是否清楚。
- 审核状态。
- 降级建议。

技能试炼场需要验证：

- 单技能表现是否清楚。
- 多技能叠加是否遮挡。
- 自身、队友、敌人、远处对象的 LOD 是否正确。
- authority 回放是否稳定。
- 同一个 seed 和 start tick 是否还原相同表现。

### 开发调试面板

开发面板至少应显示：

- 当前可见 FangyuanPrimitive 数。
- 静态实例数量。
- 动态实例数量。
- cube draw batch 数。
- sphere draw batch 数。
- 材质 batch 数。
- 透明 batch 数。
- GPU buffer 重建次数。
- 蓝图加载数量。
- 蓝图审核失败原因。
- LOD 降级原因。
- 热点灵压等级。

这些指标比单纯 FPS 更有用，因为它们能定位到底是 primitive 过多、透明过多、材质切换过多，还是动态 buffer 更新过多。

## 动态表现模块架构

推荐拆分为这些层。

```text
framework/animation/
  procedural_player
  animation_recipe
  curves
  vfx_instance_buffer
  lod
  budget
  debug

framework/fangyuan/
  blueprint
  validator
  compiler
  runtime_primitive

game/skills/
  skill_template
  skill_visual_mapping
  skill_authority_event
  trial_field

game/equipment/
  equipment_blueprint
  equipment_socket
  equipment_visual_runtime

game/world_events/
  tiandao_manifestation
  manifestation_lifecycle
  object_budget
```

分层职责：

- `fangyuan` 负责蓝图格式、审核和编译。
- `animation` 负责程序动画、曲线、实例数据和渲染提交。
- `skills` 负责规则模板、技能释放、authority 同步和表现映射。
- `equipment` 负责装备外观、挂点和技能附着。
- `world_events` 负责天道生成物生命周期、预算回收和弱互动表现边界。
