# 实时状态预览与开发者监视器

本文档定义 MyBevy 开发期实时状态预览能力的目标架构、数据契约、界面形态和安全边界。该能力用于在游戏持续运行时观察当前界面、玩家数据、场景、网络和性能状态，不用于远程控制游戏。

## 文档状态

本文是设计路线，不代表功能已经完整实现。

当前已经存在的基础能力：

- `project/src/framework/ui/debug.rs` 提供 F3 调试面板、F4 冻结、F5 panel 过滤、F6 panel 高亮、F7 专用调试窗口和 F8 文本复制。
- 当前 F3 面板能够实时读取 viewport、metrics、输入路由、焦点、UI 统计、panel、UI tree、layout bounds 和声明式文档节点摘要。
- `project/src/framework/scene/debug.rs` 已提供只读 `SceneDebugSnapshot`，包括场景、会话、生命周期、layer、实体数量和最近错误。
- `MyServerSession`、主世界 snapshot bus 和各玩法状态中已有角色、属性、房间、连接、authority frame 等事实数据。

当前尚未实现：

- 跨 UI、玩家、场景、网络和性能领域的统一 `LivePreviewSnapshot`。
- 变化驱动的事件时间线和分领域更新版本。
- F3/F7 多页开发者监视器。
- 供未来外部网页或真机观察端复用的稳定序列化协议。

## 目标

交付一个随游戏运行持续刷新的只读开发者监视器：

- F3 打开或关闭监视器，F7 在主窗口覆盖层与桌面专用窗口之间切换。
- 在 `Overview`、`UI`、`Player`、`Scene`、`Network`、`Performance` 和 `Timeline` 页面查看结构化状态。
- 状态采集与界面渲染解耦，所有显示端读取同一份共享快照。
- 同时保留“当前是什么状态”和“最近为什么变成这个状态”两类信息。
- 第一阶段只实现进程内 Rust / Bevy UI 显示端；后续外部网页和真机显示端复用同一快照协议。
- 开发者监视器在业务 `UiDocument` 加载、绑定或布局异常时仍然可用。

## 非目标

第一阶段不包含：

- 从监视器切页面、修改玩家属性、传送、切场景或发送玩法输入。
- 直接遍历、反射或序列化整个 ECS World。
- 高频视频流、远程桌面或把专用调试窗口当作游戏画面镜像。
- 通过现有远程调试 task 模型持续轮询状态。
- 在 Release 或未授权正式环境中默认启用监视器。
- 第一阶段实现浏览器前端、Android 真机面板或公网 telemetry 服务。

## 与远程调试控制的职责边界

实时预览和远程调试控制共享部分安全原则，但运行模型不同：

| 能力 | 实时状态预览 | 远程调试控制 |
| --- | --- | --- |
| 主要目的 | 持续观察当前状态和最近变化 | 对指定 client 下发离散命令 |
| 数据方向 | client 状态持续进入只读快照和显示端 | runner 下发命令，client 回传结果 |
| 运行模型 | 变化驱动 + 限频采样 + heartbeat | `request_id` / `task_id` 异步任务 |
| 典型数据 | 当前页面、角色属性、场景阶段、连接状态 | 页面切换、滚动、截图、进入场景 |
| 第一阶段显示端 | 进程内 F3/F7 Rust View | adminapi runner / task 查询 |
| 写操作 | 不允许 | 仅允许授权白名单命令 |

未来远程显示端可以复用 game-server 连接或开发期本地桥接传输快照，但不能把持续预览实现为重复创建 `system.status` task。

## 总体架构

```text
UI / Player / Scene / Network / Performance ECS state
                         |
                         v
               domain collectors
                         |
                         v
              LivePreviewSnapshot
                |              |
                |              +--> bounded Timeline
                v
         F3/F7 Rust monitor
                |
                +--> future serializer --> web / Android / remote viewer
```

系统分为三层：

1. 领域采集器把 ECS 事实数据转换成稳定、脱敏的只读 DTO。
2. 快照中心维护当前完整状态、section revision、采集健康状态和有界事件时间线。
3. 显示端只消费快照，不直接查询业务 ECS，也不拥有业务状态。

## 模块边界

建议新增 `project/src/framework/devtools/live_preview/`，作为跨领域开发期能力入口：

```text
project/src/framework/devtools/live_preview/
  mod.rs
  model.rs
  schedule.rs
  timeline.rs
  redaction.rs
  collect_ui.rs
  collect_scene.rs
  collect_performance.rs
  view/
    mod.rs
    overview.rs
    ui.rs
    player.rs
    scene.rs
    network.rs
    performance.rs
    timeline.rs
```

游戏层数据通过受控 adapter 写入快照，框架层不得直接依赖 `MyServerSession`、具体玩法组件或业务页面实现。建议的适配入口：

```text
project/src/game/devtools/live_preview/
  player.rs
  network.rs
  authority.rs
```

adapter 负责把游戏层类型转换成共享 DTO。监视器不得绕过 adapter 直接序列化 `MyServerSession`。

如果实现阶段发现通用 core 与游戏 DTO 无法维持单向依赖，可以把最终快照组装放在 `project/src/game/devtools/live_preview/`，但仍须保留框架领域快照、游戏 adapter 和 Rust View 之间的显式边界，不能把跨领域采集继续堆入 `framework/ui/debug.rs`。

## 共享快照契约

“快照”是同一采集周期内的结构化状态，不是 PNG 截图，也不是可恢复存档。

建议的顶层契约：

```rust
struct LivePreviewSnapshot {
    schema_version: u16,
    sequence: u64,
    captured_frame: u64,
    captured_monotonic_ms: u64,
    ui: UiPreviewState,
    player: PlayerPreviewState,
    scene: ScenePreviewState,
    network: NetworkPreviewState,
    performance: PerformancePreviewState,
    source_health: Vec<PreviewSourceHealth>,
}
```

契约要求：

- `schema_version` 明确序列化兼容边界。
- `sequence` 每次发布快照时单调递增，不能使用 Bevy `Entity` 作为跨帧稳定 ID。
- 每个 section 维护独立 revision 或稳定 hash，显示端只刷新发生变化的区域。
- 缺少数据使用明确的 `unavailable`、`not_applicable` 或结构化原因，不能用默认零值冒充真实状态。
- 字段顺序、枚举字符串和集合排序必须稳定，保证 F8 导出、测试和未来远程 diff 可复现。
- DTO 不反向持有 ECS 引用、`Entity` 生命周期或可写命令句柄。

## 领域数据

### Overview

Overview 只显示跨领域最重要的当前状态和异常：

- 当前 canonical screen 和 UI owner。
- 当前角色、房间和 authority 模式。
- active scene、生命周期和 session。
- 登录、选角、game connection 和鉴权状态。
- 当前 frame、authority frame、FPS 和最近 source warning。

### UI

主要数据来源：`State<AppUiMode>`、`UiCurrentOwner`、`UiPanelRoot`、`UiPanelStack`、`UiInputState`、`UiFocusState`、`UiStats` 和声明式文档 audit marker。

至少包含：

- canonical screen、alias 解析后的固定模式和当前 owner。
- 可见 panel、kind、owner、z-index、active 状态和稳定 panel ID。
- 当前阻断原因、焦点 panel、焦点节点和最近输入路由摘要。
- UI 节点、可见节点、文本节点和各类 panel 数量。
- 当前 document ID、schema version、ready/error 状态和安全 source 摘要。

当前 F3 的 UI tree、layout bounds、过滤和 panel 高亮能力继续保留在 UI 页面，不进入 Overview。

### Player

主要数据来源：脱敏后的 `MyServerSession` adapter、当前角色 profile / elements cache，以及当前玩法的本地角色状态。

至少包含：

- 当前 `character_id`、展示名称、world ID 和角色选择状态。
- 当前项目已接入的角色属性、属性快照刷新时间、push sequence 和 revision。
- 当前场景内位置、方向、移动状态和最近 authority frame；不适用时明确标记。
- 属性来源和新鲜度，例如 profile snapshot、game push 或 authority snapshot。

账号 `player_id` 与玩法 `character_id` 必须保持语义分离。房间、移动和玩法主体统一展示 character-bound 身份。

### Scene

优先复用现有 `SceneDebugSnapshot`，不要复制场景生命周期统计逻辑。

至少包含：

- active、pending 和 ready scene/session。
- `SceneLifecycleState`、最近加载阶段、required/optional 资源进度。
- authority mode、content version、seed 和最近错误摘要。
- scene root、runtime root、layer、scene-owned entity 数量。
- layer ID、状态、required 标记和 session 归属。
- 主世界或具体玩法可通过 adapter 增加稳定的领域摘要，但不能污染通用场景 DTO。

### Network

至少包含：

- account login、registration、character selection 和 game connection 状态。
- transport、connected、authenticated、room ID 和 endpoint kind；默认不显示完整内部地址。
- pending request 数量、最近成功收包时间、最近错误分类和重连状态。
- authority endpoint 类型、当前帧、最后活动距今时间和同步健康状态。

### Performance

至少包含：

- FPS、frame time 和采集器自身耗时。
- UI 节点数、场景实体数和当前时间线条目数。
- 各 section 最近更新时间、revision 和 stale 状态。

监视器自身性能必须单独统计，不能把采集或显示成本混入不可解释的总值。

## 采集与刷新策略

实时不等于每帧复制所有数据。建议按数据变化频率分级：

| 数据 | 更新策略 | 初始上限 |
| --- | --- | --- |
| 页面、panel、场景生命周期、连接状态 | 变化驱动，下一次发布周期可见 | 立即标记 dirty |
| 玩家位置、方向、authority frame | 限频采样 | 10 Hz |
| 玩家属性、房间、角色资料 | 变化驱动 | 收到新 snapshot/push 后更新 |
| UI/实体统计、性能 | 周期采样 | 2 Hz |
| source heartbeat | 周期发布 | 2 秒一次 |

采集系统应在相关业务系统完成后运行，发布应保证同一 snapshot 内的 screen、owner、scene 和 player 数据来自可解释的同一帧边界。不能为了显示方便改变玩法系统顺序。

只有 section 内容变化、source health 变化或 heartbeat 到期时才发布新快照。时间线与快照均使用固定容量，达到上限后淘汰最旧条目。

## 变化时间线

快照回答“现在是什么”，时间线回答“刚才发生了什么”。

首批事件类型：

- UI route、owner、panel 和焦点变化。
- 角色选择、属性 revision 和玩法主体变化。
- 场景 enter、ready、active、exit、failure 和 layer 状态变化。
- 连接、鉴权、进房、离房、重连和 authority 健康变化。
- source stale、恢复和采集失败。

每条事件至少包含稳定事件类型、monotonic timestamp、snapshot sequence、severity、摘要和受控详情。不得把完整网络 payload、token、密码输入或任意 binding value 写入时间线。

## Rust 多页监视器

监视器继续使用 Rust 构建 Bevy UI，不使用 `UiDocument`。这是受控开发工具 View，不属于正式业务页面。

原因：

- 它必须在 `UiDocument` 加载、绑定或布局失败时继续诊断。
- 它需要诊断 `UiDocument` 自身，不能依赖被诊断对象才能启动。
- 动态表格、变化高亮、source health 和有界时间线由 Rust View 更直接地表达。
- 它只在开发期或显式授权构建中启用，不进入业务页面审批和远程更新链路。

监视器必须复用 `UiTheme`、字体、通用按钮、滚动和选择控件，不能另建一套视觉 token。禁止把各领域查询直接塞进 View system；View 只能读取 `LivePreviewSnapshot` 和自身显示状态。

首批页面：

- `Overview`：跨领域摘要和 warning。
- `UI`：保留现有 F3 UI 诊断能力。
- `Player`：角色、属性、位置和数据新鲜度。
- `Scene`：生命周期、加载、layer 和实体统计。
- `Network`：连接、房间、pending 和 authority 健康。
- `Performance`：帧率、统计和监视器开销。
- `Timeline`：最近变化、severity 过滤和冻结后的历史查看。

快捷键兼容：

- `F3`：打开或关闭监视器。
- `F4`：冻结显示快照；游戏和采集器继续运行。
- `F5`：在 UI 页面保留 panel 过滤；其他页面不得产生不可预测副作用。
- `F6`：在 UI 页面保留 panel 高亮。
- `F7`：桌面环境切换主窗口与专用调试窗口；Android 保持主窗口。
- `F8`：复制或记录当前页面的脱敏文本/JSON 预览。

页面切换优先使用明确的 Tab 控件，同时保证键盘焦点和滚动位置稳定。显示内容变化不能导致 tab、计数器或工具栏尺寸抖动。

## 安全与隐私

实时预览采用 allowlist DTO，默认拒绝未知字段。

明确禁止进入快照、时间线、日志和 F8 导出的数据：

- 密码、确认密码和受控输入组件内容。
- access token、refresh token、character-bound ticket 和过期凭据原文。
- 任意 Authorization header、cookie 或本地密钥。
- 未经过 allowlist 的普通 binding value、聊天正文、邮件正文和完整网络 payload。
- 本机绝对路径、任意文件内容和内部服务发现配置。

ID 和 endpoint 的展示策略必须按环境定义。第一阶段本地 Debug 可以展示完整 `character_id` 和稳定业务 ID；为未来远程显示端预留掩码或 hash 策略。正式环境即使显式启用，也必须使用更严格的字段集和独立授权。

## 未来显示端协议

第一阶段不实现外部传输，但共享模型应满足后续扩展：

- 快照和时间线可使用稳定 JSON schema 序列化。
- 连接建立后先发送完整 snapshot，后续发送带 base sequence 的 section delta。
- delta 丢失、版本不兼容或 sequence 不连续时，显示端请求或等待新的完整 snapshot。
- 传输层负责鉴权、压缩、限速、heartbeat 和断线恢复，不能改变快照字段语义。
- 桌面本地桥接只能监听 loopback 并由 Debug/显式 feature 启用。
- Android 或远程 client 不开放公网监听端口，应复用受控出站连接或 ADB 开发链路。

远程控制命令和实时预览流可以共享设备身份、鉴权和审计基础设施，但必须使用不同消息类型、权限和速率策略。

## 测试与验收方向

实现阶段至少覆盖：

- 各领域 adapter 的纯数据转换和缺失数据语义。
- 快照 sequence、section revision、稳定排序、dirty 检测和 heartbeat。
- 时间线去重、容量上限、顺序和敏感信息过滤。
- F3-F8 兼容行为、主窗口/专用窗口切换、冻结和页面切换。
- 登录页、角色选择、大厅、主世界、场景切换、断线和无场景状态。
- `2772x1280`、`3.25` device scale、`50%` window scale 下的布局验收。
- 监视器关闭与打开时的 CPU、内存和实体数量开销。
- Release/Android 默认关闭和未来显式授权入口的 fail-closed 行为。

UI 布局验收统一从仓库根目录运行 `scripts/run_fast.ps1`。Rust 改动至少运行 `cargo fmt` 和仓库统一 desktop check；涉及共享模型、场景或 MyServer adapter 时运行对应单元测试和集成测试。

## 完成定义

第一阶段完成时应满足：

- 游戏运行期间可通过 F3/F7 打开多页监视器，不暂停或修改游戏。
- Overview 能同时显示当前页面、角色、场景、房间、连接和性能摘要。
- UI、Player、Scene、Network、Performance 和 Timeline 页面均读取共享快照，不直接拥有业务状态。
- 场景页复用 `SceneDebugSnapshot` 或等价单源逻辑，没有第二套场景统计实现。
- 密码、token、ticket 和未批准 binding 数据不能进入快照、显示、时间线或导出。
- 冻结、切页、独立窗口和错误/缺失数据状态可用且不会遮挡游戏输入。
- 快照模型具有稳定 schema version，可作为未来网页和真机显示端的数据源。
- 监视器开关前后的性能差异有可复现记录，关闭时不执行高频无用采集或渲染。
