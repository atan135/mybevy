# MyBevy 大型游戏业务与框架缺口分析

日期：2026-06-25

## 1. 文档目的

本文记录当前 `mybevy` 项目相对“完整大型游戏客户端 + 大型游戏服务端配套设计”仍缺少的业务逻辑和框架能力，供后续排期、验收和回查使用。

本文不是实现任务清单，也不表示所有条目都必须立刻开发。它的作用是把当前项目边界、已经具备的能力、明显缺口和推荐优先级沉淀下来，避免后续反复重新判断。

## 2. 对照范围

本次判断主要参考以下本地内容：

- `project/src/`：当前 MyBevy 客户端源码。
- `docs/界面/`：UI 框架说明和当前限制。
- `docs/场景/`：场景框架说明和游戏层场景接入说明。
- `docs/音频/`：音频框架说明。
- `docs/玩法/`：Robot Sync 与移动同步设计。
- `project/src/game/myserver/`：MyServer 协议和客户端适配层。
- 相邻仓库 `../MyServer/`：
  - `docs/总览/整体架构.md`
  - `docs/游戏服与接入层/游戏服底层框架路线图.md`
  - `docs/游戏服与接入层/帧同步与房间生命周期设计.md`
  - `docs/游戏服与接入层/战斗ECS设计.md`
  - `packages/proto/game.proto`

## 3. 当前总体结论

当前 `mybevy` 更接近“客户端基础框架 + 若干联机样例”的阶段，还不是完整游戏客户端。

已经具备的能力比较清晰：

- 有 Bevy/Rust 客户端工程骨架。
- 有 UI 框架、Scene 框架、Audio 框架、Network 框架。
- 有 `MyServer` 登录、ticket、game proxy 连接、房间基础协议适配。
- 有本地 / LAN / MyServer 三种 authority 入口。
- 有 Touch Ripple 输入帧同步样例。
- 有 Robot Sync 3D 场景、输入发送、authority frame replay 和双客户端联调闭环。
- 有样板大厅、登录页、设置页、UI Gallery、Audio Gallery、Audio Monitor 等开发期页面。

但相对大型游戏，当前主要缺口在三类：

1. 业务玩法没有形成完整产品闭环。
2. 服务端已有协议和能力，但客户端没有全部接入为可用功能。
3. 框架层已有边界，但很多大型游戏通用能力仍是预留、样例或文档目标。

## 4. 当前已具备能力

### 4.1 客户端插件结构

当前 `GamePlugin` 已集中接入：

- `AudioPlugin`
- `GameAudioPlugin`
- `ScenePlugin`
- `GameScenesPlugin`
- `MyServerPlugin`
- `AuthorityPlugin`
- `ScreensPlugin`
- `TouchRipplePlugin`
- `RobotSyncPlugin`

这说明项目已经不是单文件 demo，而是有明确的横向框架层和游戏层插件边界。

### 4.2 网络与 MyServer 接入

`project/src/framework/network/` 已提供：

- HTTP 请求接口。
- TCP 连接、监听、发送、断开。
- KCP 连接、监听、发送、断开。
- `NetworkCommand` / `NetworkEvent` Bevy message 风格接口。
- 独立 Tokio runtime 封装。

`project/src/game/myserver/` 已提供：

- HTTP guest login。
- game ticket refresh。
- TCP/KCP 连接 game proxy。
- AuthReq / AuthRes。
- Ping keepalive。
- JoinRoom / LeaveRoom / Ready / Start。
- PlayerInput / MoveInput 的发送入口。
- RoomState、FrameBundle、MovementSnapshot、MovementReject、ServerRedirect、SessionKick、AuthorityMigration 等 push 的部分解析事件。

但客户端目前没有把所有协议都上升为稳定业务系统和 UI 体验。

### 4.3 Authority 与同步样例

`project/src/game/authority/` 已提供：

- 本地 Host。
- LAN Host / Client。
- MyServer endpoint。
- authority frame。
- snapshot。
- migration event 形态。
- player input 统一发送入口。

Touch Ripple 和 Robot Sync 已经证明：

- 输入可以通过 authority frame 回放。
- 两个客户端可以观察到一致输入帧。
- Robot Sync 可在 3D 场景中生成、移动和同步可视角色。

但当前 Robot Sync 仍是“客户端确定性 replay 样例”，不是完整服务端权威角色移动系统。

### 4.4 UI 框架

`project/src/framework/ui/` 已具备：

- UI 模式与 panel root。
- layer / panel 管理。
- 输入阻断摘要。
- 焦点管理。
- binding。
- viewport 与响应式 helper。
- widgets。
- modal / loading / toast overlay。
- theme、fonts、i18n。
- UI Gallery 验证页面。

当前 UI 框架足够支撑开发期页面和简单游戏 HUD，但距离正式大型游戏 UI 仍缺复杂输入、无障碍、IME、系统剪贴板、完整表单和动态列表等能力。

### 4.5 Scene 框架

`project/src/framework/scene/` 已具备：

- 场景注册表。
- Enter / Exit / Switch / Reload 命令。
- 场景生命周期状态机。
- RON manifest 首包加载。
- required / optional asset 加载跟踪。
- Loading UI 联动。
- SceneRoot / SceneOwned 清理边界。
- Spawn / Anchor 查询。
- Trigger 事件。
- Streaming 元数据状态。
- 基础 2D/3D 场景相机。
- authority ready 边界。

当前场景框架适合样板场景和小规模玩法接入，但还没有形成完整地图、碰撞、导航、动态资源和大世界 streaming 能力。

### 4.6 Audio 框架

`project/src/framework/audio/` 已具备：

- AudioCommand / AudioEvent。
- clip / cue / group / scope / instance。
- bus 混音和静音暂停。
- music、crossfade、seek、progress。
- UI audio adapter。
- scene audio adapter。
- battle cue helper。
- spatial audio 基础能力。
- audio bank lazy unload。
- Audio Gallery 和 Audio Monitor。

音频框架基础较完整，但仍缺正式大型游戏常见的 voice/ambience 分 bus、玩家设置持久化、音频后续下载、声明式音频区域、战斗音频事件表和复杂空间声学。

## 5. 游戏业务逻辑缺口

### 5.1 账号、登录和进入游戏流程

当前客户端主要支持 guest login 和联调型自动连接。大型游戏还需要补齐：

- 密码账号注册。
- 密码账号登录。
- 游客账号升级为正式账号。
- 注册审核中 `pendingReview` 的客户端提示和流程阻断。
- 账号被封禁、限时封禁、维护模式的明确 UI。
- access token / game ticket 生命周期管理。
- ticket 过期后的自动刷新和重连。
- 登录态本地保存、清理和切换账号。
- 登录响应里的 `services` endpoint 解析和展示。
- 网络异常、登录失败、版本不兼容、服务器维护的统一错误页。
- 生产环境 HTTPS / 证书 / 域名配置入口。

服务端 `MyServer` 已有 `auth-http`、game ticket 和维护模式设计；客户端还没有把这些能力产品化。

### 5.2 大厅、房间和匹配

当前大厅入口偏固定样例，缺少真正游戏大厅业务。

需要补齐：

- 动态读取可进入的玩法列表。
- 房间列表。
- 创建房间。
- 加入房间。
- 离开房间。
- 准备 / 取消准备。
- 房主标记和房主转移展示。
- 房间成员列表、在线 / 离线状态。
- 开局倒计时和开局失败原因。
- 匹配队列入口。
- 匹配中状态、取消匹配、匹配成功确认。
- 匹配失败 / 超时处理。
- 观战入口。
- 重连入口。
- 房间错误码到玩家可读文案的映射。

MyServer 已有 match-service、RoomManager 和多种 room policy。MyBevy 目前主要使用固定 room id / policy id 联调 Robot Sync，还没有完整大厅产品流。

### 5.3 房间生命周期完整适配

服务端已有房间生命周期、断线恢复、观战和帧同步机制，但客户端尚未完整接入。

需要补齐：

- `RoomFrameRatePush` 处理。
- `RoomMemberOfflinePush` 处理。
- `RoomEndReq` / `RoomEndRes` 处理。
- `RoomReconnectReq` / `RoomReconnectRes` 完整客户端流程。
- `RoomJoinAsObserverReq` / `RoomJoinAsObserverRes` 观战流程。
- recent inputs / waiting inputs 恢复 replay。
- room snapshot 到客户端场景状态的恢复。
- 离线后重连倒计时和失败兜底。
- 被踢、封禁、并发登录踢下线的 UI。
- 房间结束结算页。
- 自动从房间返回大厅或重新匹配。

当前 Robot Sync 可以消费 `FrameBundlePush`，但房间完整生命周期还没有产品级闭环。

### 5.4 正式角色移动与位移同步

当前 Robot Sync 的目标是验证 `robot_move` 输入同步和客户端确定性 replay。它不是正式角色移动系统。

正式游戏还需要：

- 玩家输入采样系统。
- 本地表现层预测。
- 服务端权威位移模型接入。
- `MoveInputReq` / `MoveInputRes` 的正式封装。
- `MovementSnapshotPush` 低频校正。
- `MovementRejectPush` 强校正和错误展示。
- 预测回滚或平滑纠偏。
- 网络延迟与 jitter 下的 interpolation buffer。
- AOI 过滤后的实体进入 / 离开处理。
- 场景边界、阻挡、碰撞、传送点。
- 角色朝向、动画状态和移动状态机。
- 移动 checksum 和调试 HUD。

服务端 `movement_demo` 已有输入帧同步为主、权威位置校正为辅的设计；MyBevy 还没把这套能力作为正式移动框架落地。

### 5.5 战斗业务

MyServer 已有 `combat_demo`、战斗 ECS、技能、Buff、快照和事件方向。MyBevy 当前 `framework/fight` 仍是预留模块。

客户端需要补齐：

- 战斗协议适配。
- 战斗状态模型。
- 玩家 / 怪物 / 投射物实体表现。
- 技能栏和技能冷却 UI。
- 技能释放输入。
- 目标选择。
- 范围指示器。
- 伤害 / 治疗飘字。
- Buff / Debuff 图标、层数和剩余时间。
- 血条、资源条、死亡状态。
- 战斗事件到动画、特效、音效的映射。
- 战斗快照恢复。
- 战斗 replay / debug 工具。
- 战斗配置表接入和版本展示。

服务端当前战斗事件仍可能通过 `GameMessagePush` JSON payload 承载，客户端需要先做兼容适配，再评估是否推动专用 Protobuf 战斗消息。

### 5.6 背包、装备、属性和外观

MyServer 协议中已经定义：

- `ItemEquipReq` / `ItemEquipRes`
- `ItemUseReq` / `ItemUseRes`
- `ItemDiscardReq` / `ItemDiscardRes`
- `ItemAddReq` / `ItemAddRes`
- `WarehouseAccessReq` / `WarehouseAccessRes`
- `GetInventoryReq` / `GetInventoryRes`
- `InventoryUpdatePush`
- `AttrChangePush`
- `VisualChangePush`
- `ItemObtainPush`

MyBevy 缺少：

- 背包数据 resource。
- 仓库数据 resource。
- item uid / item id / count / binded 的 typed model。
- 背包 UI。
- 仓库 UI。
- 装备槽 UI。
- 道具使用 UI。
- 道具丢弃确认。
- 道具获得提示。
- 属性面板。
- 外观刷新。
- Buff / 外观变化对角色 visual 的应用。
- 背包错误码文案。
- 与服务端配置表 `ItemTable` 等的客户端展示映射。

这是服务端已有业务协议但客户端明显未接的重点区域。

### 5.7 聊天、邮件和公告

MyServer 架构中已经有：

- `chat-server`
- `mail-service`
- `announce-service`

MyBevy 当前还没有正式接入：

- 世界 / 房间 / 私聊频道。
- 聊天消息列表。
- 输入框、发送、历史加载。
- 聊天敏感词或错误提示。
- 邮件列表。
- 邮件详情。
- 标记已读。
- 领取附件。
- 新邮件通知。
- 公告列表。
- 登录公告 / 活动公告 / 维护公告。

生产模型下这些能力不一定要让客户端直连内部服务，可以通过游戏协议、BFF 或后续统一入口收敛。但客户端业务体验仍需要实现。

### 5.8 任务、NPC、剧情和交互

当前场景框架有 trigger、spawn、anchor，但没有具体任务剧情系统。

缺少：

- NPC 实体和交互。
- 对话系统。
- 任务接取 / 进行 / 完成 / 奖励。
- 任务追踪 UI。
- 剧情播放。
- 过场镜头。
- 场景交互物。
- 传送门业务。
- 触发器到任务 / 剧情 / 战斗的路由。
- 本地化文本和剧情资源管理。

AI 生成边界需要单独约束。基于当前方圆灵构和天道自演世界观，AI 可以参与生成任务表现形式、NPC 外观、对话、场景包装、任务故事理由、弱互动文本，以及系统给定低风险奖励池内的展示方案。但所有影响角色成长、资源经济、战斗强度、世界进度和纪元结算的奖励，必须由系统模板、世界预算、权限、冷却和服务端结算决定，不应由 AI 完全自由生成。

因此任务系统需要补齐：

- 任务表现和奖励结算的分层模型。
- AI 生成内容的审核、追溯和回收流程。
- 低风险奖励池和高价值奖励模板的边界。
- 四属性、称号、纪元档案和世界事件进度的服务端结算规则。
- AI 生成包装与固定任务模板之间的映射。

这类业务应放在 `project/src/game/features/`、`project/src/game/scenes/` 和 `project/src/game/screens/`，不应写入 framework scene 层。

### 5.9 怪物、AI 和 PVE 玩法

当前客户端没有完整怪物或 AI 表现系统。

缺少：

- 怪物 spawn。
- 怪物状态同步。
- 怪物移动表现。
- 怪物攻击表现。
- 仇恨 / 目标展示。
- 死亡和掉落表现。
- NPC / monster / projectile 的统一 entity visual 管理。
- 与战斗 ECS 或服务端快照的映射。

后续如果接 MyServer combat_demo，需要同步补 NPC / Monster 的客户端实体生命周期。

### 5.10 角色、养成和玩家资料

当前没有完整玩家角色业务。

缺少：

- 角色创建。
- 角色选择。
- 昵称、头像、等级、经验。
- 职业、阵营、外观。
- 装备外显。
- 属性成长。
- 技能解锁。
- 成就、称号、排行榜等扩展。

这些可以后置，但需要在大型游戏业务模型中预留。

### 5.11 运营活动与付费周边

当前没有运营系统。

后续大型游戏常见能力包括：

- 活动入口。
- 活动配置。
- 签到。
- 奖励领取。
- 商店。
- 充值和支付。
- 商品展示。
- 兑换码。
- 限时资源包。
- 灰度活动内容。

这些和内容热更、公告、邮件、背包强相关，应等基础业务链路稳定后再推进。

## 6. 游戏框架功能缺口

### 6.1 MyServer 协议客户端框架

当前 `MyServerPlugin` 能发送和解析一部分消息，但大型游戏更需要 typed domain client，而不是所有页面直接发底层命令。

建议补齐：

- `game/myserver` 保留低层协议编解码和连接。
- 新增 domain adapter，例如：
  - `game/services/auth`
  - `game/services/room`
  - `game/services/movement`
  - `game/services/inventory`
  - `game/services/combat`
  - `game/services/social`
- 每个业务服务提供 typed command/event/resource。
- 统一错误码表。
- 统一 request pending、timeout、retry、cancel。
- 统一服务器时间、RTT 和 clock offset。
- 统一协议 trace 和 debug overlay。
- 对 unknown seq、unexpected response、push decode error 做稳定上报。

这样可以避免 UI、玩法、场景直接依赖 `pb::*` 和 message type。

### 6.2 断线重连与会话恢复框架

目前有 keepalive 和部分自动刷新 ticket 能力，但还不是完整 session recovery。

需要补齐：

- 网络状态 resource。
- 登录态状态机。
- game connection 状态机。
- 自动重连策略。
- ticket refresh + reconnect。
- `ServerRedirectPush` 后切换目标并重新鉴权。
- `RoomReconnectReq` 优先恢复房间。
- 恢复失败后的降级路径。
- 重连 UI：连接中、重试中、失败、返回登录。
- 后台 / 前台切换后的重连策略。
- Android 网络切换处理。

大型联机游戏中，这部分是框架核心能力。

### 6.3 同步、预测、回滚和回放框架

当前 Touch Ripple / Robot Sync 证明了输入帧同步可行，但框架还缺通用抽象。

建议补齐：

- 固定 tick 驱动层。
- 输入采样与 target frame 计算。
- 本地预测 buffer。
- authority frame buffer。
- replay 状态基线。
- checksum 生成和对比。
- rollback / resimulate 接口。
- snapshot apply / interpolate 接口。
- late join / reconnect recovery 接口。
- replay debug view。
- 帧历史保留策略。
- 录制和回放文件格式。

Robot Sync 当前的 replay 逻辑可作为第一版经验，但不宜长期只为单一玩法定制。

### 6.4 实体同步与表现层框架

当前 Robot Sync 有机器人 visual，但还没有通用网络实体层。

需要补齐：

- NetworkEntityId / LocalEntity binding。
- player_id -> entity 映射。
- entity spawn / despawn / update。
- entity kind：Player、Npc、Monster、Projectile、Item、Interactable。
- visual prefab / glTF 映射。
- animation state adapter。
- transform smoothing。
- ownership / local player 标识。
- AOI enter / leave。
- entity debug labels。

这部分应连接 Scene、Movement、Combat、Inventory/VisualChange 等系统。

### 6.5 Scene 内容实例化、碰撞和导航

当前 Scene framework 主要负责生命周期和 manifest 资源跟踪，不负责真实地图内容。

缺少：

- 自动实例化 manifest 中声明的 glTF。
- 场景 layout / prefab 描述。
- 碰撞体生成。
- 导航数据加载。
- 可行走区域。
- 阻挡和边界查询。
- 传送门和场景切换业务。
- additive scene / layer 合并。
- 按位置真实加载 / 卸载 chunk。
- chunk 级实体迁移。
- 可视化场景调试面板。

这些是从样板场景走向大型场景或大世界的关键。

### 6.6 后续下载、内容缓存和版本校验

项目文档已经明确首包资源和后续下载资源的边界，但代码层还没有完整闭环。

缺少：

- 内容清单下载。
- 资源版本比较。
- hash 校验。
- CDN 下载。
- 临时文件和原子替换。
- Android 私有缓存路径接入。
- `content_cache://` asset source。
- 缓存清理和容量限制。
- 下载进度 UI。
- 下载失败重试。
- 资源版本与配置版本上报。

大型游戏中，场景、音频、活动图、皮肤、远端关卡、运营配置都依赖这套能力。

### 6.7 配置表与热更新

当前客户端有场景 catalog、audio catalog、i18n、theme 等资源，但没有统一配置表 runtime。

建议补齐：

- 客户端 CSV / RON / JSON 配置加载 registry。
- 配置版本号。
- 配置来源：首包 / 后续下载。
- schema 校验。
- 原子替换。
- 失败保留旧版本。
- 配置查询 API。
- 配置 diff / debug view。
- 和 MyServer 配置版本的兼容检查。

后续背包、技能、Buff、怪物、场景、NPC、任务、商店都需要配置表支撑。

### 6.8 UI 框架正式化

当前 UI 已经能做很多开发页面，但正式游戏还需要：

- 更完整 hit-test / capture / bubble。
- 长按、双击、拖拽、多指手势。
- gameplay input 与 UI 手势仲裁。
- Android safe area 原生接入。
- soft keyboard / IME composition 完整展示。
- 系统剪贴板。
- undo / redo。
- 密码遮罩。
- tooltip 通用系统。
- accessibility bridge。
- typed model binding。
- list binding / diff。
- form dirty/touched/validation。
- 动态列表虚拟化。
- icon atlas 或图标字体。
- UI 动画退出过渡。
- Toast / Loading / Confirm stack 语义增强。

这些不一定全部短期实现，但正式移动端产品通常会遇到。

### 6.9 Audio 正式化

音频框架已经比较完整，但大型游戏还需要：

- Ambience bus。
- Voice bus。
- 玩家音量设置持久化。
- 语言语音资源切换。
- 音频后续下载。
- 远端 catalog 热更新。
- 音频授权检查工具。
- 场景声明式音频区域。
- 自动空间音源。
- 触发器切换音乐。
- 战斗音频事件表。
- 语音抢占和优先级矩阵。
- ducking。
- Audio LOD。
- 混响、遮挡或更高级空间音频。

短期可以先保持现有框架，等战斗和场景业务接入后再扩展。

### 6.10 Fight 框架

`project/src/framework/fight/` 当前是预留边界，缺少真正可复用战斗基础。

建议后续沉淀：

- 战斗事件类型。
- 技能输入抽象。
- 战斗实体基础组件。
- 战斗 UI adapter。
- 战斗音频 adapter。
- 战斗特效 adapter。
- 战斗配置 catalog。
- 战斗 replay / snapshot 接口。

注意：具体角色、数值、技能规则仍应放 game layer 或配置，不应把项目专属规则写死到 framework fight。

### 6.11 工具链、测试和观测

当前有 Rust 单元测试、cargo check、开发脚本和部分双客户端脚本，但大型游戏还需要更多工具。

建议补齐：

- 多客户端自动化联调脚本。
- 网络模拟：延迟、丢包、抖动、断线。
- 协议录制和重放。
- replay checksum 验证。
- 性能 HUD：FPS、frame time、entity count、draw calls、network RTT、packet rate。
- 内存和资源加载统计。
- UI 响应式截图验收。
- Android 真机 smoke test。
- crash / panic 日志收集。
- 资源路径、LFS、manifest、hash 校验工具。
- 配置表 schema 校验工具。
- 文档与实现一致性检查。

### 6.12 安全与风控客户端配合

客户端不能承担权威安全，但要配合服务端安全模型。

缺少：

- 服务端错误码展示策略。
- 被限流、封禁、维护、踢下线的明确提示。
- 非法状态下停止发送输入。
- 高频输入本地限流。
- 调试入口与正式包隔离。
- 敏感日志脱敏。
- 本地 token 安全存储策略。
- 协议版本不匹配提示。

## 8. 推荐优先级

### P0：先把现有联机主链路做稳定

目标：让 mybevy 具备可靠的登录、连接、进房、断线恢复和错误提示。

建议任务：

- 梳理 `MyServerCommand` / `MyServerEvent`，补齐缺少的 typed command。
- 建立统一网络状态 resource。
- 建立登录态和游戏连接状态机。
- 补齐 `ServerRedirectPush` 处理。
- 补齐 `SessionKickPush` UI。
- 补齐 `RoomFrameRatePush` 和 `RoomMemberOfflinePush` 处理。
- 补齐 Room reconnect 最小闭环。
- 统一 MyServer 错误码到 UI 文案。

验收方式：

- 单客户端登录、进房、断线、重连。
- 双客户端其中一个断线后恢复。
- 服务端踢人或并发登录能显示明确提示。
- redirect push 后能重新鉴权并恢复房间。

### P1：正式移动同步框架

目标：从 Robot Sync 样例推进到通用角色移动同步。

建议任务：

- 封装 `MoveInputReq`。
- 消费 `MovementSnapshotPush`。
- 消费 `MovementRejectPush`。
- 建立本地预测和校正接口。
- 建立 entity transform smoothing。
- 接入场景边界和简单阻挡。
- 增加移动调试 HUD。

验收方式：

- 双客户端移动互相可见。
- 高延迟下仍能平滑显示。
- 服务端拒绝或校正时客户端能回到权威位置。
- checksum 或坐标摘要可用于排查不一致。

### P2：背包、属性、外观第一版

目标：接入服务端已有物品和属性协议，形成非战斗业务闭环。

建议任务：

- 增加 Inventory service。
- 增加 Inventory resource。
- 增加背包 UI。
- 增加装备 UI。
- 增加属性面板。
- 消费 `InventoryUpdatePush`、`AttrChangePush`、`VisualChangePush`。
- 道具获得 Toast 或弹窗。

验收方式：

- 登录后拉取背包。
- 服务端 GM 发物品后客户端收到推送。
- 使用、装备、丢弃有 UI 反馈。
- 属性和外观推送能更新 UI 或角色表现。

### P3：战斗 demo 客户端闭环

目标：把 MyServer combat_demo 变成 mybevy 可玩可验收的战斗样例。

建议任务：

- 增加 fight adapter。
- 解析 combat `GameMessagePush`。
- 增加战斗 HUD。
- 增加技能栏。
- 增加战斗 entity visual。
- 增加伤害飘字和 Buff UI。
- 接入战斗音效 cue。

验收方式：

- 双客户端进入 combat_demo。
- 技能释放能被服务端接受。
- 两端看到一致伤害、Buff 和血量变化。
- 断线重连后战斗状态可恢复到服务端快照。

### P4：场景内容和资源系统增强

目标：从样板场景走向可持续制作内容。

建议任务：

- 定义场景 layout / prefab 数据。
- 自动实例化部分 manifest 内容。
- 增加碰撞和可行走区域。
- 增加传送门业务。
- 建立内容清单和 `content_cache://` 最小闭环。
- 增加配置表 runtime。

验收方式：

- 一个场景能由数据声明生成基础内容。
- 角色不能穿越简单阻挡。
- 场景切换后实体和资源清理正确。
- 首包和后续下载资源来源清晰。

### P5：完整产品业务扩展

目标：补齐大型游戏外围业务。

候选方向：

- 聊天。
- 邮件。
- 公告。
- 任务。
- NPC。
- 剧情。
- 商店。
- 活动。
- 好友和组队。
- 角色创建和选择。

这些应在主链路、移动、背包和战斗稳定后分批接入。

## 9. 后续查验清单

后续每次阶段验收时，可以按下面的问题快速判断是否仍停留在样例阶段。

### 9.1 主链路查验

- 是否支持正式账号登录，而不只是 guest login？
- ticket 过期后是否能自动刷新？
- game proxy 断开后是否能自动重连？
- redirect 后是否能切换目标入口？
- 被踢、封禁、维护是否有明确 UI？
- 房间断线后是否能恢复 snapshot 和 frame history？

### 9.2 同步查验

- 客户端是否区分本地预测状态和服务端权威状态？
- 是否能处理 MovementSnapshot 校正？
- 是否能处理 MovementReject 强校正？
- 是否有 checksum 或帧日志帮助排查不同步？
- late join 和 reconnect 是否能重建 replay 基线？

### 9.3 玩法查验

- 是否有真实玩家角色，而不仅是机器人同步样例？
- 是否有可交互 NPC 或怪物？
- 是否有战斗输入、伤害、Buff、血条？
- 是否有背包、装备、属性、外观？
- 是否有任务、奖励或结算？

### 9.4 框架查验

- 新业务是否通过 typed service adapter 接入，而不是 UI 直接操作协议细节？
- 场景实体是否都能通过 `SceneOwned` 正确清理？
- 音频是否通过 cue/scope/bus 管理，而不是散落播放路径？
- UI 是否有响应式和输入阻断验收？
- 资源是否区分首包和后续下载？
- 配置是否有版本、校验和失败回滚？

### 9.5 文档查验

- 如果改变项目结构，是否更新 `CLAUDE.md`？
- 如果改变新成员启动流程，是否更新 `docs/引擎入门使用文档.md`？
- 如果改变 UI、Scene、Audio 框架边界，是否更新对应 docs？
- 如果完成 `summary/` 下 清单，是否按约定归档到 `docs/<领域>/checklists/`？

## 10. 建议的近期落点

如果只选一个最近阶段，建议优先做：

1. MyServer 客户端 service adapter 分层。
2. 房间生命周期完整适配。
3. 断线重连和 redirect。
4. 正式移动同步第一版。

原因：

- 这些是所有后续业务的共同底座。
- 它们能复用当前 MyServer 已有服务端能力。
- 它们能把 Robot Sync 样例经验沉淀成通用客户端框架。
- 它们完成后，背包、战斗、聊天、任务等业务接入会更清晰。

## 11. 一句话总结

`mybevy` 当前已经有不错的客户端框架雏形和联机样例，但还缺“正式游戏业务层”和“服务端协议能力的完整客户端产品化”。短期不宜直接堆新玩法，建议先把 MyServer 主链路、房间生命周期、移动同步和 typed service adapter 做稳，再逐步接背包、战斗、社交和内容系统。
