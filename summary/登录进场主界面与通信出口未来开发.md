# 登录、进场、游戏主界面与通信出口未来开发

## 文档定位

本文记录登录入口、角色选择、游戏主场景、场景内主界面，以及服务端邮件和聊天通信出口的未来开发范围与技术方向。

本文不是开发 清单，不表示其中事项已经实现。本文作为后续登录、进场、主界面和 chat/mail 客户端接线的统一范围基线；进入正式开发时可直接基于本文拆分前端、服务端、联调、部署和验收 清单，不需要再建立一份平行设计计划。

## 目标范围

未来版本需要形成以下完整用户路径：

```text
注册或登录
  -> 获取账号身份
  -> 获取并选择角色
  -> 进入 Lobby
  -> 点击“进入游戏”
  -> 进场调度器加载游戏主场景
  -> 场景就绪后显示游戏主界面
  -> 可打开设置、邮件，或进入家园
  -> 点击返回后退出当前游戏场景并回到 Lobby
```

本期设计范围包含：

- 完善客户端注册入口，并保持现有登录和角色选择链路。
- 新增独立的游戏主场景，不复用方圆家园场景。
- 在 Lobby 增加“进入游戏”按钮。
- 增加统一的进场调度器，管理加载、就绪、失败、退出和重复请求。
- 增加场景内常驻游戏主界面，以及设置、邮件、家园和返回功能。
- 客户端接入邮件服务和聊天服务。
- 将客户端聊天和邮件能力接入 auth 下发的 Caddy 公网 WSS/HTTPS endpoint。
- 同步维护客户端与服务端场景 CSV 配置。

以下内容不在当前文档中展开为具体实现任务：

- 主场景正式美术、地形、角色玩法和战斗内容。
- 邮件运营后台、聊天审核后台和复杂社交系统。
- 场景数值 ID、正式证书签发和生产 DNS/防火墙操作细节；chat/mail 公网域名与协议仍以 MyServer 当前正式文档为准。

## 当前能力与主要缺口

### 账号和角色

服务端已经具备注册和登录能力，客户端网络层也已支持 `MyServerCommand::Register`。当前主要缺口是登录页面没有注册模式、注册按钮和对应的交互反馈。

账号 `player_id` 与玩法角色 `character_id` 继续保持分离。登录、安全、聊天会话和邮件 ownership 使用账号玩家身份；进入房间、场景和邮件附件领取等角色资产操作使用当前角色绑定的 ticket 与 `character_id`。客户端不自行覆盖这两种身份，具体身份由服务端从 ticket 中解析。

### Lobby 和场景

角色选择后进入 Lobby 的现有流程保持不变。Lobby 已具备场景入口，但还需要新增明确的“进入游戏”入口，目标是新的游戏主场景，而不是 `FANGYUAN_HOME_SCENE_ID`。

当前客户端场景表只覆盖现有示例场景 UI 模式。新增游戏主场景后，需要增加对应的场景 UI 模式、注册适配和专属组合逻辑。

### 设置、邮件和聊天

现有音频设置页面是顶层页面，并且返回时直接回到 Lobby。它需要适配为场景内设置面板，或由嵌套 UI 状态承载，关闭设置时应回到游戏主界面而不是退出场景。

服务端已经通过登录和签票响应下发 `services.chat` WSS descriptor 与 `services.mail` HTTPS descriptor。客户端底层已有聊天 WSS runtime，当前工作区也已有邮件 endpoint、HTTP 状态和命令/事件适配的初步实现，但仍缺少实际应用接线：

- `ChatRuntime` 尚未成为应用级资源，没有系统消费连接、断线、packet、ticket 刷新和重连事件。
- `MailNotifyPush` 尚未通过已注册系统转成邮件刷新命令。
- `MailClientCommand` / `MailClientEvent` 尚未由邮箱页面或主界面未读状态消费。
- 登录、选角、环境切换、退出登录和 ticket 更新尚未统一驱动 chat/mail endpoint 与连接生命周期。

后续客户端开发应以本节列出的接线缺口为准，不重复实现底层 WSS 或邮件 HTTP 协议。

## 游戏主场景

### 场景身份

新增独立的游戏主场景，代码常量暂定为 `MAIN_WORLD_SCENE_ID`。它与 `FANGYUAN_HOME_SCENE_ID` 是两个不同场景：

- `MAIN_WORLD_SCENE_ID`：Lobby 中“进入游戏”按钮的默认目标，也是游戏主界面的承载场景。
- `FANGYUAN_HOME_SCENE_ID`：家园场景，只能通过游戏主界面的“家园”按钮等明确入口进入。

最终场景字符串 ID、服务端数值 ID 和场景编码应在正式实现时统一确认，避免客户端 CSV、服务端 CSV 和 Rust 常量各自定义。

### 首版内容

主场景首版只验证场景生命周期和 UI 闭环，不承担正式玩法：

- 一个方形块状平地。
- 一个悬浮在半空中的球体。
- 能清楚观察平地和球体的基础相机。
- 满足可见性要求的基础环境光或方向光。
- 必要的场景根实体、出生点和清理边界。

场景内容可以由 Bevy 基础网格程序化生成，也可以通过场景资源描述后由场景专属插件生成。无论选择哪种方式，场景实体都必须挂接到场景根实体，保证退出或切换时能够完整清理。

### 客户端场景配置

客户端需要修改 `project/assets/game/scenes.csv`，增加游戏主场景记录。记录至少需要描述：

- 场景 ID 和展示名称。
- 场景 manifest 或资源入口。
- 游戏主场景专用 UI 模式。
- 是否需要角色、出生点和网络会话。
- Loading、失败回退和调试展示所需元数据。

建议新增 `project/assets/scenes/main_world/scene.ron` 作为首包 manifest，并在 `project/src/game/scenes/` 增加对应注册模块和场景专属插件。现有 `GameSceneUiMode` 需要新增游戏主场景变体，不能把主界面行为硬塞入示例场景模式。

### 服务端场景配置

服务端需要在 `MYSERVER_ROOT` 指向的 MyServer 工作区同步修改：

- `apps/game-server/csv/SceneTable.csv`
- `apps/game-server/csv/SceneSpawnPoint.csv`

`SceneTable.csv` 增加游戏主场景记录，`SceneSpawnPoint.csv` 增加与其关联的默认出生点。正式开发时还应检查场景权限、传送关系、房间或实例策略所依赖的其他 Scene CSV，确保新场景不仅能被客户端显示，也能被服务端合法进入和恢复。

客户端场景 ID、服务端场景 ID、出生点和 transfer 目标必须在联调前形成一份确定映射。

## Lobby 与游戏主界面

### Lobby 入口

角色选择完成后继续进入 Lobby。Lobby 新增“进入游戏”按钮，点击后向进场调度器发出进入 `MAIN_WORLD_SCENE_ID` 的请求。

按钮在请求进行中应禁用或显示加载状态，避免连续点击创建多次进场请求。失败时保留在 Lobby，展示可重试的错误信息，不进入半完成的场景或主界面。

### 场景内主界面

游戏主界面只在游戏场景完成就绪后显示，并作为场景内常驻 HUD 层存在。首版包含以下入口：

| 入口 | 目标行为 |
| --- | --- |
| 设置 | 打开场景内设置界面；关闭后回到游戏主界面，不退出场景 |
| 邮件 | 打开邮箱列表；支持后续进入详情、标记已读和领取附件 |
| 家园 | 通过进场调度器从主场景切换到 `FANGYUAN_HOME_SCENE_ID` |
| 返回 | 退出当前游戏场景，清理场景与场景内 UI，然后回到 Lobby |

设置和邮件使用覆盖层、面板栈或嵌套 UI 状态承载。它们不应改变顶层导航为 Lobby，也不应各自直接操作场景生命周期。

家园入口需要明确切场景期间的 Loading、失败回退和返回方向。若进入家园失败，应恢复到仍然有效的主场景和主界面；若主场景已经被卸载，则回到 Lobby，不能停留在无场景 HUD 状态。

“返回”表示退出玩法场景，而不是退出账号。当前账号、选中角色和仍然有效的 ticket 可以保留；场景实体、场景内 UI、临时订阅和场景级网络状态必须释放。

## 进场调度器

进场调度器作为游戏层对场景框架的统一适配层，负责页面路由、场景命令、网络许可和场景内 UI 之间的协调。Lobby、家园按钮和返回按钮只提交意图，不直接拼装完整切换流程。

建议状态模型：

```text
IdleInLobby
  -> RequestingEntry
  -> LoadingScene
  -> WaitingForReady
  -> ActiveScene
  -> SwitchingScene / ExitingScene
  -> IdleInLobby 或 ActiveScene

任意进行中状态
  -> EntryFailed
  -> 可恢复的原状态或 IdleInLobby
```

调度器至少需要统一处理：

- 校验当前角色、ticket、目标场景和进入权限。
- 合并或拒绝重复点击和并发切场景请求。
- 驱动 Loading、资源加载、场景根创建、出生点和必要网络握手。
- 以明确的 ready 条件决定何时显示主界面。
- 记录当前场景、来源页面和失败后的可恢复位置。
- 切场景和退出时关闭场景内面板并清理场景级资源。
- 对超时、资源失败、服务端拒绝和连接断开提供统一错误事件。
- 保证错误日志包含关联 ID，但不记录 ticket、密码或其他敏感内容。

主场景与家园场景都应通过同一个调度器进入，避免形成两套不可互相恢复的进场逻辑。

## 注册与登录入口

登录页面需要增加注册入口，可采用“登录 / 注册”模式切换。注册首版应覆盖：

- 账号和密码输入、确认密码及必要的本地校验。
- 提交期间禁用重复操作。
- 服务端字段错误、账号冲突、网络错误和超时提示。
- 注册成功后回到登录并填充账号，或在协议允许时直接建立登录会话。
- 切换本地服和正式服时，继续清空账号、角色、ticket、endpoint 和连接状态。

角色列表、创建或选择角色、获取 character-bound ticket 的现有规则保持不变。后续邮件、聊天、进场和 transfer 都必须使用当前角色身份，不得退回使用 `player_id` 作为玩法主体。

## 邮件与聊天公网出口

### 当前正式拓扑

客户端不直接访问 chat-server 或 mail-service 的内部 listener。正式入口统一为：

| 能力 | auth descriptor | 正式客户端地址 | 内部 listener |
| --- | --- | --- | --- |
| 聊天 | `services.chat`，`protocol=wss` | `wss://chat.game.zergzerg.cn/`，Caddy `443/TCP` | `chat-server:9011/WS`；`9001/TCP` 仅作本地显式 fallback |
| 邮件 | `services.mail`，`protocol=https` | `https://api.game.zergzerg.cn/api/v1/mails`，Caddy `443/TCP` | `mail-service:9003/HTTP` |

生产客户端不得读取 Redis registry internal/admin endpoint，也不得直连 `9001`、`9011` 或 `9003`。development/local 可以通过显式调试参数使用 `9001/TCP` 和 `9003/HTTP`，但不得在 `services.chat/mail=null` 时自动回退到内部地址。

### 会话与 endpoint 生命周期

客户端 `MyServerSession` 需要统一持有 game、chat 和 mail endpoint。后续开发应完成：

- 登录、选角和补发 ticket 响应采用同一套 endpoint 更新逻辑。
- 环境切换和退出登录清空 game/chat/mail endpoint、连接、待处理请求和敏感凭证。
- `services.chat/mail=null` 显示受控不可用状态，不影响登录、Lobby、进场和游戏 KCP 主链路。
- ticket 更新后聊天连接重新鉴权，邮件请求使用最新 character-bound ticket。
- endpoint 变化时关闭旧连接并取消旧地址上的请求，不复用过期 session。

公网 descriptor 来自 MyServer 部署配置，registry 只负责服务端内部发现。客户端不硬编码公网 IP、内部端口、Docker host、service token、admin token 或 game-server 实例。

### 聊天客户端接线

已有 `ChatRuntime` 负责 WSS 建连、首包鉴权、binary packet、前后台状态和退避重连。后续应用接线需要：

- 在 MyServer/游戏应用插件中创建和销毁 `ChatRuntime`，并由登录会话变化驱动 endpoint、ticket 和前后台状态。
- 每帧消费 `ChatRuntimeEvent`，把连接状态、协议错误、ticket 刷新请求、响应和异步 push 转为稳定的 Bevy message/resource。
- 保留 request/response sequence 关联，区分 `ChatPush` 与 `MailNotifyPush` 等 `seq=0` 异步消息。
- 在退出登录、切换环境和应用关闭时有界关闭连接；网络中断按退避策略重连且不阻塞游戏主链路。
- 聊天首版是否提供可见窗口可在正式 清单 中决定，但底层状态必须可被 UI 消费和诊断。

### 邮件客户端接线

已有邮件适配包含 descriptor 解析、分页、详情、已读、领取和结果未知后的幂等重查。后续应用接线需要：

- 注册 `forward_chat_inbound`，仅把 `MailNotifyPush` 转换成“刷新权威邮件列表”的命令，不把 push 摘要当作邮件事实。
- 由游戏主界面邮件入口发送 `MailClientCommand`，由邮箱页面消费 `MailClientEvent` 和 `MailClientState`。
- 邮箱覆盖加载、空列表、分页、详情、未读、领取中、结果未知、重查、错误和重试状态。
- 关闭邮箱只关闭场景内面板，不取消仍需完成的领取 reconciliation，也不退出当前场景。
- 重新登录或重新打开邮箱时总能通过 HTTPS 查询 PostgreSQL 权威列表，通知缺失不造成邮件永久不可见。

邮件 ownership 使用账号玩家 ID；附件发放使用 ticket 绑定的角色 ID。客户端不得提交其他玩家、角色、附件或 game-server 实例来覆盖服务端身份判断。

### 安全和运维边界

生产入口上线必须继续满足：

- 只公开 Caddy `80/443 TCP` 和游戏 `4000/UDP`，原始 chat/mail listener、Redis、NATS、PostgreSQL 和管理口保持内网隔离。
- Caddy 终止 TLS，聊天只接受 WebSocket upgrade，邮件只转发四条玩家白名单 path/method。
- chat/mail 均验证 ticket 签名、过期、Redis ownership 和 ticket version，并实施连接、消息、HTTP 与领取限流。
- 日志、指标和 UI 诊断不记录完整 ticket、邮件正文、附件或聊天正文。
- descriptor、Caddy 路由和客户端功能可以分项灰度、暂停和回滚，不影响内部发信、邮件恢复或游戏 KCP。

## 客户端邮件界面

邮箱列表界面由游戏主界面的“邮件”按钮打开。首版建议包含：

- 邮件标题、发送方、发送时间、未读状态和附件标记。
- 分页或增量加载，以及加载中、空列表、错误和重试状态。
- 邮件详情查看和标记已读。
- 单封邮件附件领取，并准确反馈已领取、过期和失败状态。
- 关闭后回到当前游戏主界面，不切换场景。

邮箱 UI 不直接持有底层 HTTP 客户端，应通过游戏层邮件服务适配器发出命令并消费结果事件。未读数可以显示在主界面邮件入口，但其刷新策略需要在实现阶段确定。

聊天服务的客户端接入属于同一通信出口改造范围。首版是否同时提供可见聊天窗口，留待正式 清单 确认；即使暂不展示聊天 UI，也必须完成 endpoint 保存、鉴权连接、生命周期和错误处理的设计，避免后续再次修改登录会话模型。

## 生命周期与异常处理

关键异常的预期行为如下：

| 场景 | 预期结果 |
| --- | --- |
| 登录或注册失败 | 留在登录页，保留可安全复用的输入并显示明确错误 |
| 角色 ticket 获取失败 | 留在角色选择或回到登录，不进入 Lobby 假成功状态 |
| Lobby 进主场景失败 | 回到可操作的 Lobby，允许重试 |
| 主场景已加载但未 ready | 保持 Loading，不提前显示可操作 HUD |
| 主场景切家园失败 | 优先恢复主场景；无法恢复时回 Lobby |
| 邮件服务不可用 | 邮箱面板显示错误和重试，不影响场景本身 |
| 聊天连接中断 | 后台按退避策略重连，不阻塞设置、邮件或退出场景 |
| ticket 过期 | 停止受保护请求，尝试受控刷新；失败则清理会话并回到登录 |
| 点击返回 | 取消未完成的场景内请求，清理场景和 HUD 后回 Lobby |

## 验证与验收方向

后续 清单 应覆盖单元验证、前端集成、服务端集成、跨端联调和部署验收。至少应验证：

- 注册、登录、选角、Lobby、主场景和退出路径可以连续完成。
- 主场景中方形平地、悬浮球体、相机和光照在桌面与 Android 上均可见。
- 快速重复点击“进入游戏”“家园”和“返回”不会创建重复场景或遗留 HUD。
- 设置和邮箱可以反复打开关闭，关闭后仍停留在原场景。
- 主场景与家园场景切换失败时有确定回退位置。
- 客户端和服务端场景 CSV 的 ID、出生点及 transfer 配置一致。
- 正式环境登录或选角响应返回 `services.chat` WSS 和 `services.mail` HTTPS 公网 endpoint，客户端不访问内部端口。
- 公网网络环境下聊天和邮件能够加密鉴权，并拒绝无 ticket、过期 ticket 和越权角色请求。
- 邮件附件重复领取不会重复发放。
- 环境切换和退出登录会清空 game、chat、mail endpoint 及相关连接。
- 服务不可用、超时、断网和重连过程中不泄漏敏感信息，也不会阻塞场景退出。

服务端集成测试和部署端口验证在正式开发时执行；按照服务端仓库约定，运行集成测试前需要先取得确认。

## 正式开发前待定事项

以下决策需要在拆分 清单 前确定：

- `MAIN_WORLD_SCENE_ID` 的最终字符串、服务端数值 ID、场景编码和默认出生点。
- 主场景采用纯程序化生成，还是使用 RON manifest 加场景专属插件组合。
- 从家园返回时直接回主场景，还是先回 Lobby。
- 设置界面复用现有音频设置的具体 UI 状态方案。
- 邮箱未读数的刷新方式：登录推送、定时拉取或打开邮箱时刷新。
- 聊天首版是否同时交付可见聊天窗口，或只完成底层连接能力。
- chat runtime 在应用中的资源所有权，以及页面、前后台和退出登录触发其生命周期的具体系统。
- 聊天首版可见窗口范围，以及聊天 request/response/push 向 UI message 的映射。
- 邮箱页面状态模型、未读角标位置和领取 reconciliation 在面板关闭后的持有者。
- `services.chat/mail=null` 时的统一功能不可用样式和恢复入口。
- ticket 刷新机制，以及邮件 HTTP 请求和聊天长连接的统一续期策略。

## 未来完成定义

当用户可以完成注册或登录、选择角色、进入 Lobby、进入独立游戏主场景，在主界面打开设置和邮箱、切换到方圆家园，并可靠退出场景回到 Lobby；同时客户端能通过 auth 下发的 Caddy WSS/HTTPS 公网 endpoint 安全使用聊天和邮件，chat/mail runtime、UI、身份、生命周期、异常恢复与灰度不可用状态形成闭环，且前后端场景配置、部署和监控均通过验收时，本功能范围才视为完整交付。
