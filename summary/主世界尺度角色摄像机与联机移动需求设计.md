# 主世界尺度、角色、摄像机与联机移动需求设计

## 文档信息

- 文档类型：需求设计文档
- 文档状态：已确认，可作为后续 清单 拆分依据
- 编写日期：2026-08-11
- 客户端仓库：`mybevy`
- 服务端仓库：`MyServer`
- 目标客户端场景：`world.main`
- 目标服务端场景：`grassland_01 / scene_id=1`

## 1. 背景与问题

当前主世界已经完成登录后加入固定公共房间、权威场景确认、客户端场景加载、Scene Ready、Room Ready、断线恢复和退出清理，但仍只是最小可见场景，尚未形成可玩的角色移动闭环。

当前可见问题包括：

1. 场景整体暗淡，地面、背景和物体之间缺少清晰层次。
2. 摄像机参数或 Transform 的外部调整会被场景摄像机系统覆盖，表现为调整无效。
3. 主世界没有根据权威角色状态生成方圆玩家，只保存了本地角色的权威位置。
4. 客户端地面只有 `32m x 32m`，服务端 `grassland_01` 也只有 `16m x 16m`，不满足目标世界尺度。
5. 主世界尚未采集移动输入、发送 `MoveInputReq`、执行本地预测、消费持续移动快照或显示远端玩家。

本阶段需要把主世界从“可以进入的场景”提升为“可以看见角色、操控视角、自由移动并完成多人位置同步的基础世界”。

## 2. 已确认决策

### 2.1 世界与角色尺度

- 客户端和服务端统一采用米制语义，`1 Bevy unit = 1m`。
- 主世界可活动地面为 `4000m x 4000m`。
- 客户端世界以原点为中心，地面覆盖 `X/Z = -2000..2000`。
- 服务端继续使用非负二维坐标，逻辑范围为 `x/y = 0..4000`，上界按网格规则为排他边界。
- 当前方圆玩家的逻辑占地长宽为 `0.25m x 0.25m`。
- 当前最小方圆玩家 blueprint 声明 bounds 为 `2 x 2 x 3`，因此统一缩放系数为 `0.125`，目标逻辑高度为 `0.375m`。
- 高度随现有方圆玩家比例等比缩放，不单独压缩 Y 轴。

### 2.2 地面参照球

- 在地面上按 X、Z 两个方向每 `100m` 放置一个圆球。
- 圆球位置覆盖 `-2000, -1900, ... 1900, 2000`。
- 总数固定为 `41 x 41 = 1681`。
- 圆球直径为 `1m`，半径为 `0.5m`，球心高度为 `Y=0.5m`，使圆球与地面相切。
- 全部圆球合并为一个静态 Mesh，并由一个 `Mesh3d` 场景实体渲染。
- 不为每个圆球创建独立 ECS Entity，不生成独立材质或碰撞体。
- 参照球只属于客户端视觉表现，不参与 authority、碰撞、存档或联机同步。

### 2.3 当前阶段边界

- 当前阶段复用现有最小方圆玩家外观。
- 同一套运行时结构必须支持多个联网玩家实体，当前可以让所有玩家暂时使用同一种最小方圆外观。
- 包含桌面和触控下的角色移动与摄像机操控。
- 包含 MyServer 权威移动、客户端预测、权威纠正和远端玩家插值。
- 不包含地图分块、客户端 LOD、浮动原点、复杂地形、角色碰撞、战斗、NPC、寻路和正式角色外观下发。
- 不要求玩法摄像机一次显示完整 4000 米世界。

## 3. 当前实现基线

### 3.1 客户端现状

主世界场景组合位于 `project/src/game/scenes/main_world.rs`，当前会在 Scene Entered 后生成：

- 一个 `32 x 0.4 x 32m` 的 Cuboid 地面；
- 一个半径 `1.5m` 的悬浮球；
- 一盏 `7000 lux`、未开启阴影的方向光。

首包布局位于：

- `project/assets/scenes/main_world/layout.ron`
- `project/assets/scenes/main_world/scene.ron`

主世界 manifest 当前使用 `fixed3d` 摄像机，位置为 `(15, 18, 22)`，远裁剪面为 `120m`，目标为场景中心 anchor。

场景框架已经提供：

- `SceneCameraRig`
- `SceneCameraMode::FollowTarget`
- `SceneCameraFollowTargetSource::PrimaryActor`
- `SceneCameraTarget`
- 基于 scene session 的相机和目标隔离
- Scene Owned 生命周期清理

`update_scene_cameras` 每帧都会依据 `SceneCameraRig.config` 重写 Projection 和 Transform。因此，主世界摄像机控制不能直接修改最终 Camera Transform；控制输入必须修改摄像机运行状态或 `SceneCameraRig.config`，再由现有场景摄像机系统统一应用。

现有方圆玩家预览位于 `project/src/game/features/fangyuan_player_preview/`。它已经能够加载 `fangyuan/avatars/minimal_player.ron`、生成 primitive 子实体并同步根 Transform，但生成入口绑定在 `AppUiMode::FangyuanPlayerPreview`，渲染缓存和视觉生成标记也属于预览私有实现，不能直接作为主世界多人运行时使用。

`project/src/game/scenes/main_world_entry.rs` 当前只从 `MovementSnapshotPush` 中找到本地 `character_id`，验证 `scene_id` 和 `0..=16` 坐标后，将位置保存到 `MainWorldEntryState`。它不负责生成玩家，也不持续维护全部联网实体。

### 3.2 服务端现状

MyServer 已经存在完整的基础移动协议和 `movement_demo` 运行时：

- `MoveInputReq / MoveInputRes`
- `MOVE_DIR / MOVE_STOP / FACE_TO`
- `MovementSnapshotPush`
- `MovementRejectPush`
- `MovementRecoveryState`
- 基于 `character_id` 的实体身份
- 20Hz 房间 tick
- 输入延迟帧、移动停止超时、客户端状态回传、漂移检测和纠正
- 断线恢复与 room transfer 的移动状态保存

当前 `grassland_01` 配置为：

- `Width=16`
- `Height=16`
- `CellSize=1.0`
- 默认出生点 `1001=(2,2)`
- 默认移动速度 `4m/s`
- 移动纠正周期 `3` 帧
- 移动纠正阈值 `0.35m`
- 移动 AOI 开启，半径 `16m`

现有协议足以承载本阶段移动闭环，不需要新增另一套主世界移动消息。服务端需要调整场景范围、出生点和适合 `0.25m` 角色的移动策略参数。

## 4. 总体架构

主世界运行时应按以下数据流组织：

```text
桌面键鼠 / 触控输入
        |
        v
MainWorldMovementIntent
        |
        +--> 本地预测状态 --> 本地玩家视觉 Transform
        |
        +--> MyServerCommand::SendMoveInput
                     |
                     v
           movement_demo 20Hz 权威模拟
                     |
                     +--> MovementSnapshotPush
                     |       +--> 本地玩家纠正
                     |       +--> 远端玩家插值
                     |
                     +--> MovementRejectPush
                             +--> 强制纠正 / 停止非法输入

本地玩家视觉 Transform
        |
        v
SceneCameraTarget(local_player / primary_actor)
        |
        v
SceneCameraRig FollowTarget
```

场景进入协调、玩家运行时和场景表现必须保持职责分离：

- `main_world_entry` 继续负责进入、ready、退出、恢复和 gameplay input gate。
- 主世界场景模块负责地面、参照球和灯光等 scene-owned 静态内容。
- 新的主世界玩家运行时负责角色实体、移动输入、预测、快照、纠正和远端插值。
- 方圆玩家共享渲染模块只负责根据 blueprint/primitive set 创建角色视觉，不感知 MyServer 房间流程。
- 场景摄像机框架继续拥有最终 Camera Transform，主世界控制器只提供目标和运行参数。

## 5. 坐标系统与跨端映射

### 5.1 坐标定义

服务端继续使用二维 `x/y` 表示地面坐标；客户端使用 Bevy 的 `X/Z` 平面，`Y` 为高度。

固定映射如下：

```text
bevy_x = server_x - 2000
bevy_y = 0
bevy_z = server_y - 2000

server_x = bevy_x + 2000
server_y = bevy_z + 2000
```

方向向量不做中心偏移：

```text
bevy_dir_x = server_dir_x
bevy_dir_z = server_dir_y
```

客户端向 `MoveInputReq.client_x/client_y` 回传预测位置时，必须先转换回服务端非负坐标，不得直接发送 Bevy 居中坐标。

### 5.2 出生点

服务端默认出生点 `1001` 从 `(2,2)` 调整为 `(2002,2002)`，映射到客户端后仍为 `(2,0,2)`。这样可以：

- 保留当前客户端 manifest 的出生位置语义；
- 让角色出生在大地面中心附近，而不是地图角落；
- 避开位于客户端原点 `(0,0,0)` 的参照球。

### 5.3 合法值

- 所有网络坐标和方向分量必须为有限 `f32`。
- 服务端位置必须位于 `0 <= x < 4000`、`0 <= y < 4000` 的可行走网格中。
- 客户端权威坐标转换必须拒绝非有限值、越界值和错误 `scene_id`。
- 预测位置可以在渲染帧内临时接近边界，但发送给服务端前必须按同一逻辑范围约束。
- 世界中心在 `2000m` 偏移附近时，`f32` 精度仍显著小于 `0.25m` 玩家尺度，本阶段无需浮动原点。

## 6. 客户端功能设计

### 6.1 主世界静态场景

客户端地面继续使用一个 scene-owned Cuboid：

- 尺寸：`4000 x 0.4 x 4000m`
- Transform：`(0, -0.2, 0)`，使顶面保持在 `Y=0`
- 材质：非金属、高粗糙度、具有足够中间调明度
- 不生成客户端地形碰撞体；本阶段移动合法性由服务端网格负责

`layout.ron` 应从单个 `landmark` 配置改为明确的 `distance_markers` 配置，至少包含：

- 世界半尺寸或起止坐标
- 间隔 `100m`
- 半径 `0.5m`
- 颜色
- 低模球细分级别或稳定质量档位

参照球 Mesh 的生成要求：

- 只创建一份低模基础球顶点和索引模板；
- 将模板复制到 1681 个世界偏移后合并成一个 Mesh；
- 使用 `u32` 索引，不能依赖 `u16` 顶点上限；
- 只创建一个 Mesh asset、一个材质和一个 `Mesh3d` 实体；
- 该实体挂在当前 `MainWorldContent` 或 scene runtime root 下，并带当前 `SceneOwned(session_id)`；
- 退出、失败和重新进入时由 scene session 统一清理，不能残留旧 Mesh 实体；
- 不创建 1681 个子实体，也不加入网络实体注册表。

建议使用每球约 80 至 160 个三角形的低模球。按 1681 个球计算，总量约 13 万至 27 万三角形，单次静态绘制对当前阶段可接受。由于合并 Mesh 的 AABB 覆盖整个世界，它会作为整体提交；本阶段不再引入局部裁剪或 LOD。

### 6.2 场景亮度与可读性

主世界照明需要形成稳定的日间基础环境：

- 保留一盏主方向光，默认强度提高到适合日间 PBR 的可调范围；
- 增加环境补光，避免方向光背面和地面落入近黑；
- 地面、玩家和参照球在默认曝光下必须具有可区分的色相和明度；
- 参照球可以使用轻微 emissive 保持识别度，但不能依靠全自发光掩盖照明错误；
- 摄像机曝光、色调映射、clear color 与主世界照明配置配套；
- 如环境光使用全局 Resource，进入主世界时必须保存旧值，退出 scene session 时恢复，不能污染其他页面和场景；
- 阴影只需服务玩家附近的视觉层次，不要求覆盖完整 4000 米范围。

光照、地面颜色、参照球颜色和主方向光角度继续集中在首包 RON 或场景主题配置中，避免散落硬编码。

### 6.3 方圆玩家共享渲染能力

现有 `fangyuan_player_preview` 应拆出可复用的方圆玩家运行时渲染能力：

- 方圆玩家组件、primitive 视觉生成、Mesh/Material 缓存和根 Transform 同步成为共享能力；
- Preview 页面只保留预览生命周期 adapter、预览摄像机和预览灯光；
- 主世界 adapter 使用同一方圆玩家生成能力，但挂接 `SceneOwned(session_id)` 和联网身份组件；
- 共享生成 API 必须允许创建多个玩家，不能使用“全局已有一个玩家就返回”的单例判断；
- 每个玩家根实体保存 `character_id`、服务端 `entity_id`、本地/远端归属、最近权威帧和显示状态；
- 当前所有玩家可以复用 `minimal_player.ron`，后续再按角色外观数据选择不同 blueprint。

缩放规则以 blueprint 声明 bounds 为准：

```text
uniform_scale = 0.25 / max(bounds.width, bounds.depth)
```

对当前 `2 x 2 x 3` bounds，结果为：

```text
scale = 0.125
logical_size = 0.25 x 0.25 x 0.375m
```

玩家根节点的脚底基准必须落在 `Y=0`。primitive 子实体保留 blueprint 内部相对位置和比例，不逐个写入世界坐标。

### 6.4 玩家实体注册与生命周期

主世界需要建立按联网身份索引的玩家实体注册表：

- `character_id` 是玩法主体和主要查找键；
- 服务端 `entity_id` 用于检测实体重建或 room recovery 后的身份变化；
- 本地玩家由当前 character-bound ticket 对应的 `character_id` 标记；
- 一个 `character_id` 在一个 scene session 中最多对应一个玩家根实体；
- 初始快照到达早于 Scene Ready 时先缓存，不提前生成到未就绪的世界根；
- Scene Ready 且 entry 达到可运行门槛后，根据最新权威快照生成本地和远端玩家；
- 增量快照只更新其中列出的实体；
- full sync 在 AOI 关闭时代表房间完整实体集合，可清理不再存在的玩家；
- Room Leave、scene exit、不可恢复鉴权失败和 session generation 变化时清空对应注册表和插值缓存；
- 短线恢复期间保留可恢复视觉但冻结输入，恢复快照到达后重建权威基线。

本地玩家根实体还需要挂接当前 scene session 的 `SceneCameraTarget`，tag 使用 `local_player` 或 `primary_actor`。远端玩家不能抢占本地摄像机目标。

### 6.5 移动输入

桌面基础操作：

- `W/S/A/D` 和方向键产生二维移动意图；
- 多键组合归一化，斜向移动不能获得额外速度；
- 移动方向相对于摄像机在 XZ 平面的 forward/right 计算；
- 所有按键释放、窗口失焦、打开阻断 gameplay 的 UI、断线或离开 Active 状态时发送或排队一次 `MOVE_STOP`；
- 不直接由输入系统修改权威 Transform。

触控基础操作：

- 左侧 gameplay 区域提供虚拟摇杆或等价的连续二维移动输入；
- 右侧未被 UI 占用区域用于摄像机环绕；
- 双指缩放用于摄像机距离；
- 指针必须按职责锁定，移动摇杆、摄像机拖动和 UI 点击不能争用同一触点；
- 设置、邮件、Loading、Modal 等阻断层打开时停止采集主世界 gameplay 输入。

输入发送规则复用 `MyServerCommand::SendMoveInput`：

- 移动期间按 authority 的 20Hz 帧持续发送 `MOVE_DIR`，满足当前 `movement_control_stop_frames=3` 的控制保活要求；
- 方向变化时立即更新下一可用输入帧；
- 停止时发送 `MOVE_STOP`；
- 仅改变朝向且不移动时可以使用现有 `FACE_TO`；
- 每个请求携带当前预测位置和对应预测帧，供服务端漂移判断；
- 不复用 `ui_touch` action 表达角色移动，也不新增平行 JSON 移动协议。

### 6.6 本地预测与权威纠正

本地预测应使用与服务端一致的基础规则：

- authority tick 为 `20Hz`；
- 本阶段保持服务端现有基础速度 `4m/s`；
- 每固定帧按归一化方向推进；
- 预测只处理平面移动和世界边界，不实现客户端碰撞或寻路；
- 渲染可以在固定预测状态之间平滑，但网络帧号和预测状态必须可追踪。

客户端收到本地玩家的 `MovementSnapshotPush` 时：

- 丢弃旧于已应用权威帧的快照；
- 将对应帧的权威位置与预测历史对比；
- 小误差使用短时平滑纠正；
- full sync、recovery、scene change 或明显大误差直接建立新基线；
- 纠正后重放尚未被 authority 确认的本地输入；
- 不把视觉插值结果回写为下一次预测的权威起点。

收到 `MovementRejectPush` 时：

- 校验 room、character、scene generation 和 reference frame；
- 应用服务端 corrected transform；
- 对非法方向、越界或碰撞拒绝停止当前预测；
- 记录稳定诊断信息，但不得记录 ticket、密码或其他敏感字段。

### 6.7 远端玩家插值

远端玩家不执行本地输入预测，而是在有序权威快照之间插值：

- 按 `frame_id` 排序并设置有界缓存；
- 对重复或旧快照幂等处理；
- 普通移动使用插值，避免直接逐快照跳变；
- recovery、full sync、entity_id 变化和超出最大纠正距离时允许重置位置；
- `moving=false` 时收敛到最终权威位置并停止残余滑动；
- 朝向使用服务端 `dir_x/dir_y`，零向量不得生成非法旋转。

### 6.8 摄像机操控

主世界使用现有 scene camera，不创建第二个竞争的世界摄像机。场景 manifest 的默认模式应从 `fixed3d` 调整为适合本地玩家的 `FollowTarget`，target source 为 `PrimaryActor`。

主世界摄像机控制器维护：

- yaw
- pitch
- distance
- look-at height offset
- position/rotation smoothing
- 当前 scene session 和目标 generation

推荐首版参数：

- 默认距离：约 `2m`
- 可调距离：`1.5..12m`
- 默认俯仰：约 `45` 度
- 俯仰范围：`20..75` 度
- yaw：可连续环绕
- FOV：沿用当前约 `0.82 rad` 作为起点
- near：约 `0.02m`
- far：约 `800m`

桌面摄像机操作：

- 右键拖动调整 yaw/pitch；
- 滚轮调整 distance；
- UI 正在捕获鼠标或存在 gameplay 阻断层时不响应。

触控摄像机操作：

- 右侧单指拖动调整 yaw/pitch；
- 双指缩放调整 distance；
- 触点起始于 UI 控件时不转交给摄像机。

控制器根据 yaw、pitch、distance 计算 FollowTarget offset，并写入当前 session 的 `SceneCameraRig.config`。不得直接修改最终 Camera Transform，因为 `update_scene_cameras` 会在同帧或下一帧重新应用 rig 配置。

自由飞行 Debug Camera 不属于本阶段验收目标。若保留调试切换，也必须切换同一个 `SceneCameraRig` 的 mode，不能额外生成未受 scene session 管理的相机。

## 7. 服务端功能设计

### 7.1 扩大 grassland_01 逻辑地图

服务端当前网格是直接数组格式。为避免生成 `4000 x 4000` 个 1 米单元，本阶段采用粗粒度、全可行走的逻辑网格：

- `Width=40`
- `Height=40`
- `CellSize=100.0`
- 逻辑世界尺寸为 `4000m x 4000m`
- `walkable` 共 1600 项，全部为 `1`
- `block` 共 1600 项，全部为 `0`

该网格只承担世界边界和“整片平地可行走”的服务端判定，不能表达 100 米单元内部的障碍。复杂障碍、精细碰撞和压缩网格格式属于后续阶段。

需要同步调整并验证：

- `apps/game-server/csv/SceneTable.csv`
- `apps/game-server/scene/grassland_01.grid.json`
- `apps/game-server/csv/SceneSpawnPoint.csv` 中主世界玩家出生点
- SceneCatalog 加载和 grid 长度校验
- movement demo 的边界与出生测试

不在本阶段批量迁移草原上的 NPC、怪物、区域或交互配置；它们不属于当前主世界客户端表现范围。若相关配置测试要求位置一致，应单独记录兼容处理，不能顺带扩展为 NPC 玩法开发。

### 7.2 出生与多人实体

- 默认出生点 `1001` 调整为 `(2002,2002)`。
- 当前可以继续由 `movement_demo` 在角色加入时创建权威移动实体。
- 每个实体继续绑定 ticket 中的 `character_id`，不得退回账号 `player_id`。
- 多个玩家使用独立 `entity_id` 和移动状态。
- 本阶段不实现玩家之间的实体碰撞；重叠不影响移动合法性。
- 如需要避免所有玩家完全重叠，服务端可以在出生点半径内提供确定性小偏移，但偏移必须经过同一 SceneQuery 校验，且不能由客户端自行选择权威出生点。

### 7.3 movement_demo 参数

本阶段继续复用 `movement_demo`，不新建另一个主世界 room policy。

参数要求：

- `active_room_fps` 保持 `20`。
- 默认移动速度保持 `4m/s`，客户端预测以此为当前冻结契约。
- `movement_correction_interval_frames` 保持 `3` 作为起点。
- `movement_correction_threshold` 应从当前 `0.35m` 下调到适合 `0.25m` 角色的范围，推荐初值 `0.05m`，最终以双客户端联调稳定性为准。
- 本阶段关闭 movement AOI，使用全房间实体快照语义，使最多 32 个公共房间玩家无需地图分块也能完成同步验收。
- `movement_control_stop_frames` 保持 `3`，客户端移动期间必须按帧保活。
- 已有断线恢复、离线停止、强纠正和 room transfer 行为继续有效。

关闭 AOI 是当前阶段的明确简化：最多 32 个玩家时可以接受全房间移动状态；后续引入地图分区、AOI 或可见性裁剪时再重新设计大世界兴趣管理。

### 7.4 服务端安全与校验

服务端继续作为最终移动 authority：

- 验证输入 frame、输入类型、方向有限性和非零方向；
- 对方向归一化或限幅，客户端输入幅度不能改变权威速度；
- 使用 SceneQuery 限制目标位置；
- 拒绝越界、非法状态和错误房间输入；
- 不接受客户端直接指定最终权威位置；
- `client_state` 只用于漂移检测和纠正，不作为权威写入；
- 保持 character-bound ticket、room membership 和 connection generation 校验；
- 服务端日志只记录必要的 room、character、frame、reason 和误差，不记录 ticket 原文。

## 8. 协议与兼容性

### 8.1 复用的现有协议

本阶段直接复用以下 Protobuf 类型：

| 类型 | 用途 |
|------|------|
| `MoveInputReq` | 客户端提交方向、停止、朝向和预测位置 |
| `MoveInputRes` | 输入请求接收结果 |
| `EntityTransform` | 权威玩家身份、场景、位置、方向和移动状态 |
| `MovementSnapshotPush` | 普通增量、全量和恢复位置同步 |
| `MovementRejectPush` | 拒绝输入并返回纠正状态 |
| `MovementRecoveryState` | 重连、观察者或迁移后的移动恢复 |

本阶段不新增消息号，不修改 `EntityTransform` 字段，不用通用 `PlayerInputReq` 复制一套移动 JSON，也不把移动挂到 `ui_touch` action。

### 8.2 跨仓库冻结契约

虽然当前协议不下发移动速度，客户端预测和服务端模拟必须在本阶段共同冻结以下规则：

- movement policy：`movement_demo`
- tick：`20Hz`
- speed：`4m/s`
- 坐标范围：`0..4000`
- 坐标中心偏移：`2000m`
- 输入方向归一化规则
- `MOVE_DIR` 保活和 `MOVE_STOP` 语义

客户端和服务端都需要契约测试。后续如果出现角色属性影响速度、Buff、坐骑或不同移动模式，应再通过显式权威状态字段或玩法配置版本扩展，不能继续依赖两端散落常量。

## 9. 状态与异常处理

### 9.1 正常进入

1. 客户端完成登录、选角和 game proxy 鉴权。
2. 加入 `main-world-public / movement_demo`。
3. 服务端生成角色移动实体并下发初始 `MovementSnapshotPush`。
4. entry coordinator 验证 scene 和本地角色权威位置后加载 `world.main`。
5. Scene Ready、Room Ready 和初始快照门槛满足。
6. 主世界玩家运行时根据最新快照生成玩家实体。
7. 本地玩家被标记为摄像机 PrimaryActor。
8. 进入 Active 后开放移动和摄像机 gameplay 输入。

### 9.2 断线恢复

- 断线后立即冻结移动输入并停止继续增长未确认预测。
- 场景和玩家视觉可以暂时保留，但不能继续声称本地预测是权威状态。
- RoomReconnect 成功后等待 recovery/full snapshot。
- 以恢复快照重建所有玩家权威基线、预测历史和插值缓存。
- 恢复完成后重新开放输入，摄像机继续跟随同一 character 对应的新或复用实体。

### 9.3 退出与清理

- 返回 Lobby、进入家园、切换环境、退出登录或不可恢复 session kick 时停止移动输入。
- 发送必要的 `MOVE_STOP` 不能阻塞既有 Room Leave 和 scene exit 超时策略。
- 玩家实体、参照球 Mesh 实体、地面、灯光、相机目标和运行时缓存都归当前 scene session 清理。
- 全局环境光或其他全局渲染状态必须恢复进入主世界之前的值。
- 旧 generation 的迟到快照不得重新生成已退出场景的玩家。

## 12. 测试与验收标准

### 12.1 静态世界验收

- 客户端主世界地面尺寸确认为 `4000 x 4000m`，顶面位于 `Y=0`。
- 参照球逻辑数量严格为 `1681`，间隔严格为 `100m`。
- 所有参照球由一个 Mesh、一个材质和一个 `Mesh3d` Entity 渲染。
- 参照球不带 collider、网络身份或独立子实体。
- 默认出生位置附近能看到玩家、地面和原点参照球。
- 使用仓库根 `scripts/run_fast.ps1` 的固定窗口配置进行主世界视觉验收。
- 默认画面不再接近纯黑，玩家轮廓、地面和参照球清晰可分。

### 12.2 角色验收

- 进入 Active 主世界后，本地 character 对应的方圆玩家只生成一次。
- 当前最小方圆玩家逻辑 bounds 为 `0.25 x 0.25 x 0.375m`。
- 玩家脚底落在地面，不悬浮、不穿入地面。
- 同一场景内可以同时生成多个不同 `character_id` 的玩家根实体。
- Preview 页面和主世界复用同一方圆玩家视觉生成能力，不出现两套 primitive 解释结果。
- 离开和重新进入主世界不会残留旧玩家或重复视觉子树。

### 12.3 摄像机验收

- 摄像机默认跟随本地玩家，而不是固定看向场景原点。
- 鼠标/触控调整 yaw、pitch 和 distance 后，结果不会在下一帧恢复默认值。
- 摄像机可以环绕、俯仰和缩放，并持续以本地玩家为目标。
- 玩家移动时摄像机平滑跟随，不修改玩家 authority 坐标。
- UI 面板、Loading 或 Modal 捕获输入时，摄像机不会误转动或缩放。
- 场景中不存在两个同时竞争主世界画面的活动 3D 摄像机。

### 12.4 移动验收

- 桌面方向输入和触控移动输入都能产生摄像机相对的标准化移动方向。
- 本地操作具有即时视觉响应，不需要等待下一次远端快照才开始移动。
- 松开输入、失焦、打开阻断 UI、断线和退出时角色可靠停止。
- 服务端拒绝非法方向、非有限数值和越界移动。
- 客户端能够在 4000 米逻辑范围内移动，并能通过测试或调试定位验证中心和四个边界，无需人工步行穿越全图。
- 权威纠正不会造成持续振荡；正常网络条件下的小误差采用平滑纠正。

### 12.5 联机验收

- 两个不同 character 可以加入同一 `main-world-public` 房间并生成两个玩家实体。
- 任一客户端移动时，另一客户端能看到对应角色连续位移和停止。
- 本地玩家使用预测和纠正，远端玩家使用插值，不能混用同一显示策略。
- 旧帧、重复快照和旧 scene generation 不会回退当前角色位置。
- `MovementRejectPush` 能把对应本地角色恢复到 corrected transform。
- 短线重连后，角色位置、方向、moving 状态和实体集合与服务端恢复快照一致。
- Room Leave、家园切换和返回 Lobby 后不再发送主世界移动输入。

### 12.6 服务端验收

- `grassland_01` 的配置和 grid 均表达 `4000 x 4000m` 范围。
- `(2002,2002)` 默认出生点通过 SceneCatalog validator。
- 0 附近、中心附近和 4000 边界附近的合法/非法落点测试覆盖完整。
- `movement_demo` 对两个以上 character 保持独立位置、方向和 last input frame。
- 纠正阈值调整后，正常预测不会产生每帧强纠正，明显漂移仍能收敛。
- AOI 关闭后的全房间同步在最大 32 人策略上具有明确的消息量和性能记录。
- 既有 reconnect recovery 和 room transfer movement state 测试继续通过。

## 13. 性能与质量约束

- 1681 个参照球不得产生 1681 个 ECS Entity。
- 参照球静态 Mesh 生成一次，不得每帧重建或修改顶点。
- 方圆 unit Mesh 和相同材质继续缓存复用，多个玩家不得重复创建相同 Mesh asset。
- 玩家插值和预测历史使用有界队列，断线和 scene exit 时释放。
- 输入发送频率受 authority 20Hz 控制，渲染帧率不能直接放大网络发送量。
- 普通日志不逐帧打印每个玩家位置；诊断应采用采样、计数或显式 debug 开关。
- 客户端常规验证至少包含 `cargo fmt`、`cargo check` 和相关定向测试。
- 服务端测试需要按 MyServer 仓库规则先确认依赖和执行范围，再运行定向测试或多服务联调。

## 15. 完成定义

本需求整体完成时，应达到以下产品结果：

- 主世界呈现清晰可读的日间 `4000m x 4000m` 地面。
- 地面每隔 100 米显示一个参照球，全部参照球由单一场景 Mesh 实体承载。
- 当前登录 character 在主世界生成尺寸正确的方圆玩家。

- MyServer 对 4000 米范围内的位置和移动保持权威，客户端提供本地预测和纠正。
- 同一房间的多个客户端能够看到彼此的角色移动和停止。
- 断线恢复、退出清理、家园切换和旧 generation 隔离不因新增移动运行时而回退。
- 本阶段没有引入地图分块、LOD、浮动原点或另一套重复移动协议。
